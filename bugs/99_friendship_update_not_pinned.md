# Bug 99 — Принятие дружбы не закрепляет `created` и не ограничивает набор полей

**Статус:** 🔧 ПОЧИНЕНО В MAIN (2026-07-31) · ⚠️ выкат правил — ТОЛЬКО по слову владельца ·
**Когда/контекст:** найден 2026-07-31 аудитом Fable 5 после сессий слабых моделей (ревизия кода +
состязательная проверка) · **Серьёзность:** minor

## Симптом

Комментарий над правилом обновления дружбы (`firestore.rules:195`) декларирует инвариант:
«Стороны и отправитель неизменны: иначе принявший мог бы переписать историю». Ожидаемое —
принявший запрос **не может** переписать историю документа. Наблюдаемое — инвариант реализован
частично: закреплены только `status/a/b/requestedBy`, а дата создания запроса (`created`)
переписывается свободно, и в документ дружбы можно вложить произвольные посторонние поля.

## Воспроизведение (детерминированное)

1. Боб отправляет Алисе запрос дружбы — появляется `friendships/alice_bob` со `status: 'pending'`.
2. Адресат Алиса выполняет прямой вызов (в обход клиентского кода приложения):
   ```js
   updateDoc(doc(db, 'friendships', 'alice_bob'), {
     status: 'accepted', acceptedAt: 2, created: 0, extra: 'мусор'
   });
   ```
3. Правило пропускает запись: дата создания запроса переписана (`created: 0`), в документе
   лежит постороннее поле `extra`.

Тест «принявший не может переписать, кто отправлял запрос» (`rules.test.ts:381–404`) это не
ловит — он проверяет только `requestedBy`.

## Криминалистика

Фактический код правила (`firestore.rules:194–203`):

```
// Принять может ТОЛЬКО адресат, ТОЛЬКО из статуса pending, и никогда — отправитель.
// Стороны и отправитель неизменны: иначе принявший мог бы переписать историю.
allow update: if verified()
              && participant()
              && resource.data.status == 'pending'
              && request.auth.uid != resource.data.requestedBy
              && request.resource.data.status == 'accepted'
              && request.resource.data.a == resource.data.a
              && request.resource.data.b == resource.data.b
              && request.resource.data.requestedBy == resource.data.requestedBy;
```

Ни закрепления `created`, ни `keys().hasOnly([...])` / `diff().affectedKeys()`. При `update`
`request.resource.data` — документ **после слияния**, поэтому `updateDoc` адресата с
посторонними полями проходит все условия.

Факты состязательной проверки (закрытые линии опровержения):

- `created` — реальное поле модели: `FriendshipDoc.created` (`src/lib/data/schema.ts:166`).
- Тесты правил (`rules.test.ts:381–404`) закрепляют только `requestedBy` — дыру не покрывают.
- `canAcceptFriendship()` в `schema.ts` — клиентская проверка; злонамеренный клиент её обходит.
- Документированного решения владельца об ослаблении нет; при этом проект **сам** применяет
  `hasOnly` там, где пишет недоверенная сторона (suggestions: строка 336, funnel: строка 309).
  То есть пропуск — не паттерн, а упущение.
- `git log -S hasOnly`: правило дружбы в исходном виде с коммита `59d3c69`, сознательного
  ослабления в истории не было.

Смягчение (подтверждает severity=minor): документ дружбы читают только двое участников и админ
(`allow read: if participant() || isAdmin()`, строка 182), а `created`/`acceptedAt` сегодня не
используются ни в UI, ни в сервере синхронизации — вред ограничен целостностью документа.

Дополнительно: `allow create` (строки 186–192) тоже без `hasOnly` — посторонние поля можно
вложить уже при создании запроса.

## Корневая причина

Правило писалось от перечня полей, которые **очевидно** нельзя менять (стороны, отправитель,
статус), а не от белого списка того, что менять **можно**. Инвариант из комментария («принявший
не может переписать историю») закрыт наполовину: `created` — тоже история, но в перечень не
попал, а без `hasOnly` открыт и весь остальной документ. По git-истории (см. вердикт) правило
в таком виде с самого рождения (`59d3c69`) — это первоначальное упущение, не регрессия.

## План фикса

Всё ниже — [NOT-TESTED], предложено без прогона эмулятора правил:

1. В `allow update` дружбы добавить закрепление даты создания:
   `request.resource.data.created == resource.data.created`.
2. Там же ограничить состав полей:
   `request.resource.data.keys().hasOnly(['a','b','requestedBy','status','created','acceptedAt'])`.
3. В `allow create` — тот же `hasOnly` на тот же состав полей.
4. Тесты правил (`rules.test.ts`, рядом с 381–404): «принявший не переписывает `created`»,
   «посторонние поля отвергаются при create», «посторонние поля отвергаются при update».
5. Прогнать весь набор тестов правил на эмуляторе — убедиться, что легитимные сценарии
   (запрос, принятие, расторжение) не сломаны.

**ВАЖНО:** правка правил НЕ выкатывается без слова владельца — лежит в `main` до ближайшего
санкционированного выката правил.
