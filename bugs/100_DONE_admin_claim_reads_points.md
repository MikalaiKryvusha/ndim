# Bug 100 — клиент с claim admin читает чужие points и points/dims вопреки декларации «только владелец и сервер синхронизации»

**Статус:** ✅ ПОЧИНЕНО И ПОДТВЕРЖДЕНО В БОЮ 2026-07-31 — выкат состоялся выкатом правил (ruleset 06:11 UTC, бой == репо)
**Когда/контекст:** найден 2026-07-31 аудитом Fable 5 после сессий слабых моделей (ревизия кода +
состязательная проверка) · **Серьёзность:** minor

## Симптом

Правила Firestore разрешают аккаунту с custom claim `admin=true` читать `points/{любой uid}` и
`points/{любой uid}/dims/{dimId}` прямо из клиента — то есть пооценочные (интимные) данные любого
человека. Ожидаемое поведение, зафиксированное и в комментарии самого блока правил, и в решениях
владельца: оценки не видит **никто**, кроме самого владельца точки и сервера синхронизации
(тот ходит через Admin SDK мимо правил и в правилах не нуждается).

## Воспроизведение (детерминированное)

1. Взять аккаунт с custom claim `admin=true` (таких два — выданы при cutover скриптом
   `tools/migrate/04-admin-claim.mjs`, см. `plans/04_DONE_cutover.md`).
2. В браузере под этим аккаунтом выполнить `getDoc(doc(db, 'points', <чужой uid>))` и
   `getDocs(collection(db, 'points', <чужой uid>, 'dims'))`.
3. Ожидаемо по декларации: `permission-denied`. Фактически: данные отдаются — правило
   `isAdmin()` пропускает чтение.

Тестов на поведение админа в `points` нет, поэтому расхождение никакой прогон не ловит.

## Криминалистика

Комментарий блока (`firestore.rules:210-211`) декларирует одно:

```
// Оценки не видит никто, кроме владельца и сервера синхронизации. Сервер синхронизации работает через
// Admin SDK, а он правила не применяет, — поэтому здесь его упоминать не нужно.
```

А правила тут же (`firestore.rules:214` и `:224`) разрешают другое:

```
match /points/{ownerId} {
  allow read: if isSelf(ownerId) || isAdmin();
  ...
  match /dims/{dimId} {
    allow read: if isSelf(ownerId) || isAdmin();
```

Состязательная проверка находку подтвердила; все линии опровержения провалились:

1. **Канон 1.x не оправдание.** Там «ndimids читал владелец или админ» (`researches/02:69`),
   но в 1.x браузер админа **сам был вычислительной частью**; в 2.0 сервер синхронизации ходит
   через Admin SDK мимо правил, и клиентскому админу это чтение не нужно.
2. **Решения владельца прямо противоположны.** Интервью №002 В4 — вариант A: «оценки не видит
   никто, кроме тебя и сервера синхронизации»; требование Т6 (`researches/04:23,215`);
   `ideas/13:61-63,70-71` — дважды явно: «админ не исключение», «Админ не получает доступа к
   оценкам людей по измерениям».
3. **Дыра в тестах.** Блок «Оценки по осям» в `rules.test.ts` админа не проверяет вовсе.
4. **Происхождение.** `isAdmin()` в `points` есть с первого же коммита правил `59d3c69`, чьё
   собственное описание гласит «оценки видит только владелец» — противоречие заложено изначально
   и нигде не легитимизировано.
5. **Сценарий реален.** Claim `admin=true` действительно выдан двум uid при cutover.

Смягчение (почему minor, а не хуже): оба текущих админ-uid принадлежат самому владельцу, поэтому
боевой утечки оценок посторонним людям не было.

## Корневая причина

Правило написано по инерции канона 1.x («владелец или админ») в том самом первом коммите правил
`59d3c69`, хотя архитектура 2.0 уже другая: сервер синхронизации обходит правила через Admin SDK,
и клиентскому админ-аккаунту доступ к оценкам не нужен ни для чего. Комментарий блока написали
верно, код под него не привели, а тест на отказ админу не завели — вот дефект и дожил до аудита.

## План фикса

Всё ниже предложено без прогона — `[NOT-TESTED]`:

1. `[NOT-TESTED]` Убрать `|| isAdmin()` из `allow read` на обоих уровнях: `points/{ownerId}`
   (`firestore.rules:214`) и `points/{ownerId}/dims/{dimId}` (`firestore.rules:224`) — по прямым
   решениям владельца (интервью №002 В4, `ideas/13` «админ не исключение»).
2. `[NOT-TESTED]` Добавить в `rules.test.ts` тесты-отказы: «админ НЕ читает чужой
   `points/{uid}`» и «админ НЕ читает чужие `points/{uid}/dims/*`».
3. **ВАЖНО:** правка правил НЕ выкатывается без слова владельца — лежит в main до ближайшего
   санкционированного выката правил.
