# Bug 84 — Из-под гостя нельзя войти в свой аккаунт: продукт умеет только «превратить гостя», а выйти гостю нечем

**Статус:** 🔴 ОТКРЫТ · **Приоритет: 🔴 БЛОКИРУЮЩИЙ** — владелец не может войти в свой основной
аккаунт, и тот же капкан открыт для любого из 331 человека 1.x, кто перед входом заглянул гостем ·
**Когда/контекст:** 2026-07-29, волна владельца ideas/21 (п. 13)

## Симптом

Слово владельца дословно (`ideas/21_mikalai_tests_bugs_29_07.md:112-118`):

> запросил авторизацию по ссылке из письма через браузер и через браузер прошёл по ней — мой
> основной аккаунт kotkrinik@yandex.ru — не пустило. Одновременно пишет «Сейчас Вы гость — Ваши
> результаты не сохранены» и «Этот способ входа уже связан с другим профилем NDim. Чтобы сохранить
> текущие результаты, создайте аккаунт на другую почту». Две проблемы: а) не могу авторизоваться;
> б) неконсистентное состояние, не понимает разницы между гостем и попыткой использовать чужой
> email — это разные состояния, и должны быть разные поведения приложения, а не всё смешивать в
> кучу.

## Замер / воспроизведение

**Живого замера нет.** Прибор волны `tools/probe-ideas21.mjs` этот пункт не трогает — в
`test-results/ideas21/report.txt` секций про вход и аккаунт нет вовсе (измерены пп. 1, 2, 4, 5, 6,
7, 9, 10, 11, 14, 15, 16). Вход требует настоящего письма и второго занятого аккаунта, поэтому всё
ниже — **чтение кода** плюс слово владельца. Разведка по этому пункту
(`test-results/ideas21/recon.txt:157-161`) стоит с вердиктом **ПОДТВЕРЖДЁН_КОДОМ**, и сверка не
опровергла в нём ничего (единственная правка адреса — см. «Причина», замок 2).

Цепочка, пройденная чтением (не браузером), — ровно та, что описывает владелец:

1. `/profile` без сессии → карточка входа, кнопка «Осмотреться гостем»
   (`src/routes/profile/+page.svelte:828` → `continueAsGuest()` :216-218 → `/profile?guest=1`);
2. `onMount` видит `?guest=1` → `signInGuest()` (:172-177), `guest = true`;
3. гость жмёт «Сохранить результаты», вводит **свою** почту → `requestLink()` (:290-305) →
   `sendLoginLink()` (`src/lib/data/account.ts:173-185`), почта легла в
   `localStorage['ndim-pending-email']` (:179);
4. переход по ссылке из письма → `onMount`: `if (isLoginLink()) uid = await finishEmailLink();`
   (`profile/+page.svelte:170-171`) → `finishEmailLink()` (:225-259), где первыми строками
   `guest = true; guestCard = true;` (:226-227);
5. `completeLoginLink()` (`account.ts:220-241`) идёт в **гостевую** ветку
   `if (user && user.isAnonymous)` (:227) →
   `await linkWithCredential(user, EmailAuthProvider.credentialWithLink(email, href));` (:228);
6. Firebase отвечает отказом (почта уже принадлежит существующему аккаунту) → `classify()` :88-101,
   строки 90-91: `if (code === 'auth/credential-already-in-use' || code === 'auth/email-already-in-use')
   return 'already-in-use';`
7. экран: `signupError = t.account.errors[result.reason][lang]; signupStep = 'choose';`
   (`profile/+page.svelte:251-252`), а `guest` остался `true` (:226) — **и карточка гостя рисует обе
   фразы разом**: заголовок `<h2>{t.guest.title[lang]}</h2>` (:866 → текст :339 «Сейчас Вы гость —
   Ваши результаты не сохранены») и ниже, в той же карточке, `{#if signupError}<p class="err">…`
   (:895 → текст :409 «Этот способ входа уже связан с другим профилем NDim…»).

Вывод, а не факт кода: раз владелец увидел именно `already-in-use`, а не `expired-link`, то
`localStorage['ndim-pending-email']` был на месте (`account.ts:221-222` — при пустом ключе
`completeLoginLink` возвращает `expired-link`, не дойдя до Firebase). То есть письмо запрошено и
открыто в одном и том же хранилище браузера — как владелец и описывает. Какой именно код вернул
Firebase (`email-already-in-use` или `credential-already-in-use`), по коду не определить: оба
схлопываются в одну причину (:90-91).

## Причина

Продукт умеет **превратить гостя в аккаунт** и не умеет **войти в существующий аккаунт из-под
гостя**. Замков три, и они держат друг друга.

**Замок 1 — ветка входа недостижима, пока жива гостевая сессия.** `completeLoginLink`
(`src/lib/data/account.ts:220-241`) выбирает путь по сессии: `if (user && user.isAnonymous)` (:227)
— `linkWithCredential` (:228); и только `else` — `signInWithEmailLink(devAuth(), email, href)`
(:233), то есть настоящий вход. Та же развилка у Google: `continueWithGoogle` (:149-163) —
`linkWithPopup` при анонимной сессии (:153-154) против `signInWithPopup` (:158) без неё. Комментарий
модуля (:213-218) описывает это как замысел: «сессии НЕТ → `signInWithEmailLink`: обычный вход. Для
331 человека из 1.x это и есть их дверь». Дверь есть — она просто заперта изнутри, пока человек
гость.

**Замок 2 — у гостя в «Меню» нет «Выйти».** Разведка (`recon.txt:159-161`) даёт адреса:
`src/routes/menu/+page.svelte:238-246` — `{:else if stand === 'ready' && guest}`: внутри пилюля
«◌ гость» (:242), пояснение (:243) и одна кнопка «Сохранить результаты» → `/profile` (:246).
Строка «Выйти» стоит на **:259-261** и лежит в ветке `{:else if stand === 'ready'}` (**:247**), то
есть показывается только НЕ-гостю. Грепы разведки по всему `src`: `signOut(` — единственное
вхождение (`src/lib/data/profile.ts:115`), `signOutUser` зовут ровно из одного места
(`menu/+page.svelte:120`, внутри `leave()` **:119-122**), строка «Выйти» существует ровно одна
(`menu/+page.svelte:153`). Сверка разведки: «подтверждено, строки на месте. Мелочь в адресах:
`leave()` занимает 119-122, а не 118-121 (на 118 пустая строка) — на вывод не влияет». Сам
`signOutUser` исправен — `signOut` + `forgetAll()` + `forgetAvatars()` (`profile.ts:114-120`);
проблема ровно в отсутствии кнопки.

**Замок 3 — карточку входа гостю не показать.** `onMount` профиля: `uid = await currentSession();
if (uid === null) { stand = 'signedout'; return; }` (`profile/+page.svelte:181-185`), дальше
`guest = isGuestSession();` (:186). При живой гостевой сессии `currentSession()` возвращает uid,
значит `stand = 'signedout'` (единственное состояние с кнопками «Войти через Google» / «Войти по
ссылке на почту», :826-828) не наступает никогда, а `/profile?guest=1` гостя только заводит
(:172-177). Разведка проверила и обход: «обходных выходов в продукте нет вовсе… и лендинг тоже не
даёт двери». Лендинг это подтверждает: обе его кнопки ведут на `/profile`
(`src/routes/+page.svelte:233-234`, `APP_URL = '/profile'` :28).

**Итог замков.** Единственный путь наружу, оставленный продуктом, разведка называет прямо:
«создать аккаунт на ДРУГУЮ почту, стать не-гостем и только тогда выйти, то есть завести мусорный
профиль». Ровно это и советует текст ошибки (`profile/+page.svelte:409`) — продукт предлагает
человеку намусорить в собственной базе, чтобы попасть домой.

**Четвёртая, отдельная половина жалобы — состояния в одной карточке.** Блок `{#if guestCard &&
(guest || signupStep === 'done')}` (:839-899) отвечает сразу за всё: пилюлю гостя, факты, форму
почты, «отправлено», «подтверждаем», «профиль сохранён» и ошибку. Провал связывания не переводит
экран в другое состояние — он просто дописывает красную строку под заголовком «Сейчас Вы гость»
(:866 + :895). Владелец увидел не два экрана, а один, который не решил, что он такое.

## Два состояния, которые владелец требует различать

**(а) Гость хочет сохранить свой труд под новой почтой.** Это то, что продукт уже делает и делает
правильно, ломать нечего: `linkWithCredential`/`linkWithPopup` сохраняют UID, дальше
`finishUpgrade()` (`account.ts:130-136`) обновляет токен и зовёт `promoteGuestPoint()` (:110-116) —
снимает `guest: false, dirty: true`, иначе человек остался бы невидимым и через месяц лишился данных
(шапка модуля, :12-16). Экран заканчивает поздравлением «Профиль сохранён»
(`profile/+page.svelte:844-852`). **Признак состояния:** почта свободна.

**(б) Человек хочет войти в СВОЙ уже существующий аккаунт.** Продукта для этого случая нет — есть
только ошибка. Как должно быть:

- продукт **не должен** называть это ошибкой связывания: почта не «чужая», она **его**;
- труд гостя при этом придётся отпустить — слить два профиля нельзя, и это записано в самом коде
  (`account.ts:80-81`: «этот Google-аккаунт или почта уже принадлежат другому профилю NDim. Молча
  слить два профиля нельзя: чьи-то оценки пришлось бы выбросить»);
- значит человека надо **честно предупредить до входа**, а не после: «в этом браузере есть
  несохранённые результаты гостя. Если Вы войдёте в свой аккаунт, они с Вами не переедут»;
- правда, которую предупреждение обязано сохранить: гостевые данные не стираются в этот момент —
  гостевая точка живёт до автоочистки (шапка `account.ts:12-16`; текст «Меню» о том же —
  `menu/+page.svelte:147`: «без входа его данные удаляются через 30 дней»). Но вернуться в
  анонимную сессию после выхода нельзя, поэтому для человека это потеря. Слово «навсегда» продукт
  не употребляет (правила текста продукта);
- после подтверждения — выход из гостевой сессии и обычный вход (`signInWithEmailLink` /
  `signInWithPopup`), человек попадает домой, к своим измерениям и связям.

## Что делать

1. **Дать гостю «Выйти» (снимает блокировку, минимальный шаг).** Перенести/переиспользовать строку
   `menu/+page.svelte:259-261` в гостевую ветку :238-246. Оговорка разведки дословно: «сама
   кнопка — очевидное переиспользование готовой строки 259-261 и потому в зоне агента, НО выход
   гостя безвозвратно отрезает его несохранённый труд, поэтому текст и форма подтверждения — уже
   UX, их на глаз не сочиняем; если подтверждение становится отдельным элементом экрана, это макеты
   и владелец».
2. **Развести два состояния ДО отправки письма.** В карточке гостя — две двери вместо одной:
   «Сохранить мои результаты» (нынешний путь) и «У меня уже есть аккаунт». Вторая: предупреждение
   (см. выше) → подтверждение → `signOutUser()` → отправка ссылки уже из состояния без сессии →
   `completeLoginLink` уходит в ветку :233 и человек дома. Технически это работает без новых
   механизмов: `PENDING_EMAIL_KEY` переживает выход — `signOutUser` трогает только сессию и кэш
   (`profile.ts:114-120`), а ключ снимается лишь при успехе (`account.ts:229` и `:234`). *Проверено
   чтением, живьём не проверялось.*
3. **Спасти уже случившийся отказ.** На месте ошибки `already-in-use` дать действие «Это мой
   аккаунт — войти в него» с тем же предупреждением. **Ловушка, которую надо снять первой:**
   годится ли тот же одноразовый код из ссылки после неудачного `linkWithCredential` — **не знаем**,
   кодом это не определяется (гипотеза; проверять живым прогоном на стенде и по документации
   Firebase). Если код уже сожжён — честно предложить новое письмо, а не молчать.
4. **Переписать текст ошибки** `profile/+page.svelte:409` (и английский :410): сегодня он ведёт
   ровно в один выход — «создайте аккаунт на другую почту». Текст — лицо продукта, к владельцу
   (см. «Ждёт владельца»).
5. **Не держать оба состояния в одной карточке.** Отказ связывания обязан переводить карточку в
   собственный вид (развилка «войти / другая почта»), а не дописываться строкой под заголовком
   «Сейчас Вы гость…» (:866 + :895).

## Чего НЕ делать

- **Не менять `link*` на `signIn*`, «чтобы пускало».** Это осиротит труд гостя — прямой запрет в
  шапке модуля (`account.ts:7-10`): «ГЛАВНОЕ ПРАВИЛО: строго `link*`, а не `signIn*`… Любой
  `signIn*` создал бы нового пользователя и осиротил бы данные гостя».
- **Не сливать два профиля молча** — «чьи-то оценки пришлось бы выбросить» (`account.ts:80-81`).
- **Не считать пункт закрытым одной кнопкой «Выйти».** Разведка дословно: «одна кнопка „Выйти“
  снимает блокировку, но не чинит саму невозможность войти в свой аккаунт из-под гостя».
- **Не сочинять на глаз текст подтверждения выхода и предупреждения о потере труда** — это UX и
  правила текста продукта, а не догадка агента.
- **Не строить фикс на `fetchSignInMethodsForEmail`** («узнать заранее, занята ли почта»): защита от
  перебора почт может возвращать пустой список. Это **гипотеза**, кодом репозитория не
  подтверждённая, — проверять живьём, прежде чем закладывать в решение.
- **Не трогать `promoteGuestPoint`** (`account.ts:110-116`) при правках апгрейда: без него аккаунт —
  косметика, человек остаётся невидимым и через месяц теряет данные (:12-16).
- **Не выкатывать в обход `bugs/19`**: там открыта развилка «вход — отдельный экран в стиле
  лендинга», и дверь «У меня уже есть аккаунт» живёт ровно в ней.

   результаты. Вариант А: кнопка + короткое подтверждение в той же карточке. Вариант Б: отдельный

2. **Где живёт дверь «У меня уже есть аккаунт»** — в карточке гостя на `/profile` (быстро, но

3. **Какими словами предупреждать о потере труда гостя?** Правда такова: данные не удаляются в

4. **Нужно ли когда-нибудь ПЕРЕНОСИТЬ труд гостя в существующий аккаунт (слияние профилей)?**
   Сегодня продукт этого не умеет и, по мнению агента, уметь не должен: слияние требует выбрасывать
   чьи-то оценки. Если владелец хочет иначе — это отдельная большая работа по модели данных, и
   решать её надо до текстов.

## Проверка

Чем судить, что починено (наблюдениями, живым Chrome — обе темы, 390/1440, память
«владелец — QA-инженер», `plans/06`):

1. Под гостем в «Меню» **есть** «Выйти»; после неё сессии нет и продукт показывает карточку входа
   (`stand === 'signedout'`), а не гостевой профиль.
2. Гость, идущий по ссылке на почту, **уже занятую другим аккаунтом**, в итоге оказывается ВНУТРИ
   этого аккаунта — uid после входа равен uid аккаунта, а не гостя, — и до входа он видел честное
   предупреждение о судьбе гостевых результатов.
3. На экране **никогда** не соседствуют «Сейчас Вы гость — Ваши результаты не сохранены» и «Этот
   способ входа уже связан с другим профилем NDim».
4. Путь (а) не сломан: гость с **свободной** почтой по-прежнему получает «Профиль сохранён», его uid
   не меняется, а `points/{uid}.guest` становится `false`.

Чем доказать самого стража — **мутацией**: тот же прогон на СЕГОДНЯШНЕМ коде обязан упасть на
наблюдениях 1-3 (это и есть мутант — сам дефект); после фикса вернуть гостевую ветку
`account.ts:227-231` (link вместо входа) — страж обязан упасть снова. Данные для прогона: **не**
боевой `kotkrinik@yandex.ru` — нужен свой второй аккаунт с занятой почтой, боевой аккаунт владельца
прогонами не трогаем. Есть ли на стенде эмулятор Firebase Auth, позволяющий гонять письма
автоматически, — **не проверено**, выяснить до написания стража.

### Страж `node tools/verify-bug84.mjs` — 28/28 (светлая 390 + тёмная 1440)

Стережёт не кнопку, а **весь путь владельца целиком**, потому что звенья запирали друг друга:
гость → «Меню» → «Выйти» → признак сессии снят → карточка входа → запрос ссылки на почту →
проход по ссылке (oob-код берётся у эмулятора Auth по REST, без письма — EXP-0045) → **человек в
СВОЁМ аккаунте**. Ключевые проверки: «у ГОСТЯ есть Выйти», «НЕТ ошибки *уже связан с другим
профилем*», «экран больше не считает человека гостем», «в „Меню“ стоит почта именно того
аккаунта».

**Доказан мутацией:** убрал гостевую кнопку «Выйти» → прогон падает ровно на этом звене
(`waiting for locator('button.row').filter({ hasText: /Выйти/ })`).

**Прибор врал дважды и был исправлен:**
· искал сессию в `localStorage` — **Firebase держит её в IndexedDB**, и на исправном продукте
  получал `null`; теперь спрашивает признак сессии продукта (`ndim-session`) и **сам экран**
  («Меню» печатает почту вошедшего) — так же это видит владелец;
· ждал `button[type=submit]` — кнопка запроса ссылки обычная, с обработчиком.

### Что осталось и ждёт владельца

**⛔ 1. Форма подтверждения при выходе гостя.** Выход необратим: несохранённый труд пропадает.
Сейчас человека предупреждает только текст выше («Ваши результаты пока не сохранены…»).
Отдельной ступени подтверждения в продукте НЕТ ни для чего — то есть это новый приём, а значит
**макеты и слово владельца**. Вопрос: нужна ли ступень подтверждения и в какой форме?
**Рекомендация агента:** нужна, в виде врезки прямо в карточке (без модального окна) — но
решение за владельцем.

**⛔ 2. Две двери вместо одной** («Сохранить мои результаты» / «У меня уже есть аккаунт»).
Это правильное лечение половины (б): сегодня отказ связывания не переводит карточку в другое
состояние, а лишь дописывает красную строку под заголовком «Сейчас Вы гость» — владелец увидел
один экран, который не решил, что он такое. Новая дверь = новый видимый элемент = **4 макета**.

**⛔ 3. Текст ошибки** `profile/+page.svelte:409-410` ведёт ровно в один выход — «создайте аккаунт
на другую почту», то есть предлагает намусорить в базе, чтобы попасть домой. Текст — лицо
продукта, переписывать его агенту нельзя без вычитки владельцем.

**❓ 4. Непроверенная ловушка (гипотеза, кодом не определяется):** годится ли ТОТ ЖЕ одноразовый
код из ссылки после неудачного `linkWithCredential`, или он уже сожжён. От ответа зависит, можно
ли спасать уже случившийся отказ на месте или придётся честно предлагать новое письмо.
