# Баг 133 — стейдж не повторяет боевые переадресации: 10 адресов отвечают 404 вместо 301

> **Заведён:** 2026-08-16 · **Нашёл:** агент (фаза 4 `plans/53`, первым же прогоном
> `verify-prod-lang-redirects --base` по стейджу) · **Статус:** ✅ **ПОЧИНЕН 2026-08-16**,
> проверен наблюдением в живом контуре: `verify-prod-lang-redirects --base https://ndim-stage.web.app`
> → **16/0** (было 16 · 10 провалов); проверка встроена в дверь ·
> **Серьёзность:** предрелизный рубеж не воспроизводит поведение боя ·
> **Родитель:** `plans/53_DONE_EPIC_stage_environment.md` фаза 4

## Симптом

`node tools/verify-prod-lang-redirects.mjs --base https://ndim-stage.web.app` → **16 проверок,
10 провалов**. Все десять одинаковые: старый адрес, который в бою отдаёт **301** на `/ru/…`, на
стейдже отдаёт **404**.

```
❌ /delete-account — HTTP 404      ❌ /menu/about   — HTTP 404
❌ /menu/manual    — HTTP 404      ❌ /menu/author  — HTTP 404
❌ /menu/terms     — HTTP 404      ❌ /menu/support — HTTP 404
❌ /menu/privacy   — HTTP 404      ❌ /menu/donate  — HTTP 404
❌ /menu/disclaimer— HTTP 404      ❌ /menu/share   — HTTP 404
```

## Причина

Переадресации — свойство ХОСТИНГА, а не сборки: они перечислены в `firebase.json` у боевого
таргета `landing` и в `firebase.stage.json` отсутствуют вовсе. Когда конфигурацию стейджа писали
(фаза 1), в неё скопировали то, что было нужно немедленно, — `public`, `cleanUrls`, заголовки, —
а блок `redirects` не заметили.

🔑 **Почему это дефект, хотя на стейдже индексировать нечего.** Ценность переадресаций в бою —
сохранить заработок проиндексированных адресов; на стейдже этой ценности нет. Но у стейджа своя
работа, названная владельцем дословно: «*стейдж, который **повторяет прод***». Контур, который
отвечает иначе, чем бой, не может отрепетировать правку — а фаза 5 только что сделала прогон по
стейджу ОБЯЗАТЕЛЬНЫМ перед каждым выкатом. То есть с этого дня расхождение стоит дорого: правка
переадресаций поедет в бой, ни разу не проверенная.

⚠️ Второй таргет боя (`app` — старый адрес `ndim-space.web.app` с семью междоменными 301) на
стейдж НЕ переносится: это дверь со старого домена на купленный, у стейджа такой двери нет и быть
не должно.

## Лечение

1. Десять поимённых переадресаций перенесены в `firebase.stage.json`.
2. 🔒 **Страж расхождения `tools/verify-contour-parity.mjs`** — потому что копия без стража
   разъезжается молча, и это ровно тот класс, ради которого в проекте живёт
   `tools/lib/contours.mjs`. Страж сверяет ХОСТИНГ обоих конфигов: список переадресаций (источник →
   цель → тип), `cleanUrls`, набор правил кеширования. Различия, которые ЗАКОННЫ, перечислены в нём
   поимённо и с причиной — иначе страж пришлось бы отключать при каждом честном отличии контуров.

- `verify-contour-parity` зелен, а его самопроверка краснеет на подложенном расхождении.
