# Bug 75 — Панель «Все / Мой NDim ID» прячется при переключении вкладок

**Статус:** 🔴 ОТКРЫТ · **Когда/контекст:** 2026-07-29, волна владельца ideas/21 (п. 2)

## Симптом

Слово владельца дословно (`ideas/21_mikalai_tests_bugs_29_07.md:39-42`):

> при переключении между Все и Мой NDim ID иногда закрывается эта панель с кнопками Все и Мой
> NDim ID, словно разные глубины скрола на этих суб страницах вынуждают панель скрыться (она
> думает, что страницу листали) — я это уже чинил в старом NDim, не понимаю, как так можно было
> NDim 2.0 писать, что не учтены мои наработки...

Владелец здесь не только сообщил дефект, но и **поставил диагноз**: «она думает, что страницу
листали». Диагноз верен построчно — см. «Причина».

## Замер / воспроизведение

Живой прогон стенда `http://localhost:5173`, прибор `tools/probe-ideas21.mjs` (секция «П. 2»,
строки 150-184), сырой вывод — `test-results/ideas21/report.txt:32-41`, кадры
`test-results/ideas21/02-bar-mine.png` и `02-bar-all.png`. Мерилась **видимость панели в окне**
(`getBoundingClientRect` у `.segs`), а не наличие узла — узел есть всегда.

| Шаг | Замер |
|---|---|
| «Все», прокрутка на 1200 | `{"top":-32,"bottom":-1,"inView":false,"scrollY":1200}` |
| переключили на «Мой NDim ID» | `{"top":70,"bottom":101,"inView":true,"scrollY":0}` |
| вернулись на «Все» | `{"top":-32,"bottom":-1,"inView":false,"scrollY":793}` |

То есть: на «Мой NDim ID» (там ещё не были, целевая позиция 0) панель **видна**, на возврате
во «Все» (восстановление на глубину 793) — **невидима**. Это дословно совпадает со словами
владельца про «разные глубины скрола».

Оговорки честности:

- Первый вердикт прибора («панель держится при прокрутке» — ❌, `top=-32` после ручной прокрутки
  на 1200) **дефектом не является**: прятание панели при листании ВНИЗ — утверждённое поведение
  (канон 1.x, макет V3, `bugs/52_DONE`). Ожидание прибора здесь строже канона; чинить надо только
  смену вкладки. Прибор в этой части стоит поправить вместе с фиксом.
- Воспроизводимость «3 круга из 3» получена агентом-ведущим прибором; в `report.txt` зафиксирован
  один круг, цикла повторов в `tools/probe-ideas21.mjs` нет. Считать доказанным одним кругом,
  трёхкратность — со слов.
- Замер снят десктопным Chrome на стенде. **Телефоном не проверялось** — владелец ловил дефект на
  Android.

## Причина

Обработчик прокрутки не отличает **программную** прокрутку (восстановление позиции вкладки) от
руки человека, а `switchTab()` не сбрасывает признак спрятанности.

**1. Смена вкладки делает программный прыжок.** `src/routes/dims/+page.svelte:666-675`:

```
  function switchTab(next: Tab): void {
    if (tab !== next) tabScroll[tab] = window.scrollY;
    const target = tabScroll[next];
    …
    void tick().then(() => restoreScroll(target));
  }
```

Память позиций — `const tabScroll: Record<Tab, number> = { all: 0, mine: 0 };`
(`dims/+page.svelte:664`). Восстановление — `restoreScroll()` (`:689-721`), rAF-цикл до
`DEADLINE_MS = 1200` (`:703`) с `window.scrollTo({ top: target, behavior: 'instant' })` (`:716`);
при `target <= 0` — один такой же `scrollTo` в 0 (`:690-692`).

**2. Обработчик читает этот прыжок как «листают вниз».** `dims/+page.svelte:776-818`:

```
      const down = y > last;
      last = y;
      if (!down) { toolbarHidden = false; return; }
```
(`:786`, `:787`, `:788-791`) — и ниже, после guard'ов, `toolbarHidden = true;` (`:814`).
Пороги на месте и каноничны: `TOOLBAR_ALWAYS_BELOW = 40` (`:772`), `TOOLBAR_SCROLL_STEP = 20`
(`:774`), уезд `translateY(-200%)` за 0.3s (`:1351`, `:1354`), разметка `class:hidden={toolbarHidden}`
(`:1004`).

**3. Сброса нет.** Все присваивания `toolbarHidden` живут ТОЛЬКО внутри `onScroll` (`:781`, `:789`,
`:814`; объявление — `:766`). `switchTab` чистит `search`/`submitted` (`:670-671`), но
`toolbarHidden` не трогает.

**4. Guard «прячем только прилипшую» прыжку не мешает.** `:809-812` требует
`el.getBoundingClientRect().top <= barHeight() + 1`; панель — прямой ребёнок `.screen`
(`:1001-1007`, `.screen { min-height: 100dvh }` на `:1289-1292`), `position: sticky` (`:1343-1344`),
значит на глубокой позиции она прилипшая и условие выполняется.

**Отсюда «иногда»:** знак программного прыжка определяет исход. Прыжок ВНИЗ (возврат на «Все», 0 →
793) → `down === true` → панель прячется. Прыжок ВВЕРХ или в 0 (первый заход на «Мой NDim ID») →
ветка `y < TOOLBAR_ALWAYS_BELOW` (`:780-784`) → панель показывается. Ровно «разные глубины скрола».

**Второй источник «иногда»** (найден сверкой, владельцем не назван): guard `:794` —
`if (searchOpen || search.trim() !== '' || suggestOpen) return;`. `switchTab` чистит текст запроса,
но `searchOpen` НЕ сбрасывает, поэтому при открытом ящике поиска панель не прячется вовсе.

### Канон фикса — как это чинил сам владелец в 1.x

Разведка (сверенная построчно) нашла в 1.x **не два, а три** форса показа панели на навигации —
это и есть «я это уже чинил в старом NDim»:

1. `ndim_old/public/scripts/app.js:1156-1161` — в `scrollToLastPagePosition()`, СРАЗУ ПОСЛЕ
   восстановления прокрутки:

```
  // если скролим сегменты, то открыть верхний навбар переключателя сегментов
  setTimeout(() => {
    if (["dimensions_page_all_segment", "dimensions_page_my_segment"].includes(page_id)) {
      showTopStickyToolbar();
    }
  }, 10);
```

2. `ndim_old/public/scripts/app.js:1235-1236` — в `openPage()`:
   `showTopStickyToolbar();` строкой выше `openPageSegment();`
3. `ndim_old/public/scripts/app.js:1477-1478` — в `openPageSegment()`:
   `openTheSelectedSegment(); showTopStickyToolbar();`

Плюс два форса в самом обработчике: `app.js:2879-2891` (`if (current_scroll_position < 40) {
showTopStickyToolbar(); return true; }` и `showTopStickyToolbar()` при движении вверх) — эту часть
2.0 уже повторяет. Сами `showTopStickyToolbar()`/`hideTopStickyToolbar()` — `app.js:2931-2948`, обе
отложены на **одинаковые** 200 мс.

Уточнение из сверки (важно, чтобы не скопировать не то): порядок в 1.x давала НЕ разница задержек
show/hide (они равны), а `setTimeout(…, 10)` вокруг форса (`app.js:1157-1161`) — его таймер
стартует позже, значит и истекает позже. Копировать эту гонку таймеров не надо, нужен её смысл:
**после программного восстановления прокрутки панель принудительно показана**.

## Что делать

1. **Признак программной прокрутки.** На всё время работы `restoreScroll()` (включая ранний путь
   `target <= 0`, `:690-692`) держать флаг; в `onScroll` при поднятом флаге только переприсваивать
   `last = y` и выходить, ничего не решая. Снимать флаг в `stop()` (`:710-712`) и на отмене рукой
   пользователя (`giveUp`, `:706-708`).
2. **Форс показа после восстановления** — смысл `app.js:1157-1161`: по завершении `restoreScroll`
   (в `stop()`) выставить `toolbarHidden = false`. Это и есть три вызова владельца, сведённые в
   одно место: у нас смена вкладки — единственный вход, где позиция восстанавливается программно.
3. **Решить судьбу `searchOpen` при смене вкладки** (второй источник «иногда»): `switchTab`
   очищает запрос, но оставляет ящик открытым — либо закрывать его вместе с запросом, либо
   сознательно оставить. Правка на одну строку, но это изменение видимого поведения — если
   сомнение, вынести владельцу отдельно, к основному дефекту она не относится.
4. **Прибор** `tools/probe-ideas21.mjs:172` — ожидание «панель прибита под шапкой и видна всегда»
   противоречит канону 1.x; при фиксе переформулировать на «видна после смены вкладки».
5. Тот же корень отравит пп. 1 и 9 волны (память прокрутки при навигации между экранами): когда
   там появится общее восстановление позиции, признак «идёт программная прокрутка» должен жить
   рядом с ним, а не только внутри `/dims`. Чинить одним приёмом.

## Чего НЕ делать

- **Не «лечить» строкой `toolbarHidden = false` в начале `switchTab`** — программный прыжок
  случится ПОСЛЕ неё (`:674`, через `tick()`), и панель снова спрячется. Это первый и самый
  соблазнительный тупик.
- **Не копировать гонку таймеров 1.x** (10 мс + 200 мс): по ПРОСТОТЕ честнее явный флаг, чем
  подгонка задержек друг под друга.
- **Не прибивать панель навсегда** «чтобы не пряталась»: прятание при листании ВНИЗ рукой —
  утверждённое поведение (канон 1.x `app.js:2870-2893`, макет V3, `bugs/52_DONE`, комментарии
  `dims/+page.svelte:753-763`). Владелец жалуется на смену вкладки, а не на листание.
- **Не трогать guard `:809-812`** («прячем только прилипшую») — он закрывает ДЫРУ, найденную
  владельцем в бою (`:796-808`), к этому дефекту отношения не имеет.
- Не менять пороги 40/20 и 0.3s — это числа из 1.x (`researches/12`).

## Проверка

Наблюдением на живом браузере, страж вида `tools/verify-bug75.mjs` (тот же приём замера, что в
`probe-ideas21.mjs:157-164` — видимость `.segs` в окне):

1. «Измерения» → пролистать «Все» вниз (≥1200), убедиться, что панель уехала (это норма);
2. переключить на «Мой NDim ID» → панель видна;
3. вернуться на «Все» → **панель видна** (`inView === true`, `top ≈ barHeight()`), а прокрутка
   при этом восстановлена на прежнюю глубину (`scrollY > 0` — обе цели сразу, иначе «фикс»
   мог просто сломать восстановление позиции);
4. контроль канона: после этого пролистать вниз рукой → панель снова прячется;
5. обе темы × 390/1440, ≥3 круга, консоль чиста.

**Чем доказать самого стража (мутация):** сегодняшний код и есть готовый мутант — на нём шаг 3
обязан краснеть (замер выше: `inView=false`, `top=-32`). После фикса — временно снять флаг
программной прокрутки и убедиться, что страж снова красный; вернуть.
