## 🔵 РЕШЕНИЕ ВЛАДЕЛЬЦА 2026-08-21 — интервью №041, В2 = A, с уточнением его словами

> «*часть клиент удаляет сам, всё помечается для сервера синхронизации — остатки вычищает
> сервер синхронизации*»

Форма — ДВА плеча, но без открытия листинга клиенту: клиент при удалении аккаунта чистит то,
до чего дотягивается своими правами, и ПОМЕЧАЕТ удаление для сервера; суточный проход сервера
синхронизации вычищает остатки (половины пар умершего участника — симметрично гигиене
`suggestions`). Хвосты ПРОШЛЫХ удалений добирает тот же суточный проход.
⚠️ Проектная деталь на исполнение: метка «аккаунт умер» у сервера уже есть по факту —
исчезновение `points/{uid}`; отдельный маркер заводить только если проход не сможет дёшево
узнавать умерших по этому признаку.

## Симптом

Человек прошёл «Тест для двоих» (оценки легли в `testPairs/{pairId}` вместе с его uid), затем
удалил аккаунт. Продукт говорит ему: удаляется всё. На деле его `aUid` и `aAnswers` (оценки
0…10 по названным измерениям) живут в документе пары, пока жив ВТОРОЙ участник, — то есть
потенциально годами, и читаются вторым участником по ссылке.

## Почему это дефект, а не замысел

- Оценки — самая приватная величина продукта (интервью №002, В4). `testPairs` — исключение ПО
  СОГЛАСИЮ (человек сам нажал кнопку в рамках теста), но удаление аккаунта — это ОТЗЫВ согласия;
  после него хранить нечем оправдать.
- Канон удаления (`plans/20`, шапка `erase.ts`): «не удалилось — учётную запись не трогаем и
  честно говорим, что осталось». Про пары теста человек не слышит ни слова — они не названы ни
  в перечне удаляемого, ни в перечне «вычистит сервер за сутки».

## Форензика (чтение кода, подтверждено построчно)

1. `erase.ts` — `testPairs` в перечне удаления НЕТ (шаги 1–5, снятые «с firestore.rules
   построчно» в `plans/20` шаг 0 — ДО появления коллекции).
2. Клиент и не может их найти: `firestore.rules:567` — `allow list: if false;` у `testPairs`
   перечисление запрещено всем; запросом «мои пары» их не достать.
3. Сервер синхронизации удаляет пару только когда мертвы ОБА:
   `sync-server/index.mjs:945` — `if (members.some((uid) => alive.has(uid))) continue;`.
   Живой второй участник консервирует ответы удалившегося навсегда.

## Корневая причина (класс)

Перечень «что удаляется» снят с правил в момент написания (`plans/20`, закрыт 2026-08-01), а
коллекция `testPairs` появилась ПОЗЖЕ (`plans/42`, 2026-08-14) — и никто не был обязан вернуться
к старому перечню. Класс тот же, что `bugs/129`: «всё, что не X, — это Y» живёт ровно до
появления Z. Инвентарь удаления — ровно такая бинарная развилка.

## Направление починки (эскиз, решение формы — интервью №041, В2)

Удалить по правилам человек может пару, только зная её id (`allow delete` есть). Значит либо:
- **А** — клиент запоминает id своих пар (локально или в `users/{uid}` приватно) и `erase.ts`
  удаляет их шагом 3б; у старых пар id не восстановить — их добирает Б;
- **Б** — сервер синхронизации в суточном проходе ОБЕЗЛИЧИВАЕТ половину умершего участника
  (`aUid: null, aAnswers: null`) у пар, где второй жив, — симметрично обезличиванию
  `suggestions` (решение владельца В11 = А: вклад остаётся, связка с человеком уходит).
  Цена: чтение пар уже оплачено существующей уборкой, дозапись только по факту смерти.

Вариант Б закрывает и гостей (гость исчезает через TTL — его половина тоже обезличивается).

## Приёмка фикса (наблюдаемый критерий)

На стенде: пара с ответами двоих → первый удаляет аккаунт → после суточного прохода в документе
пары нет ни `aUid` удалившегося, ни его `aAnswers` (либо пары нет целиком — по выбранной форме);
у второго участника его собственная половина цела. Сегодняшнее состояние ЗАМЕРЕНО чтением кода:
ответы остаются — критерий сегодня красный, чинить есть что.

## Чего НЕ трогать

- `cleanupStalePairs` в части «пара, где жив хоть один, не удаляется ЦЕЛИКОМ» — это правильно:
  второй вправе вернуться за СВОИМИ ответами.
- Обезличивание `suggestions` — образец, а не место правки.
