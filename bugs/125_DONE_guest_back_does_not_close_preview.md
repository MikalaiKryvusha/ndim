# Баг 125 — у ГОСТЯ в бою «Назад» не закрывает «Как меня видят»

**Заведён:** 2026-08-15 (найден смоуком под сессией `verify-prod-signed-in`, первый же прогон) ·
**Класс:** навигация, неглубокое маршрутирование · **Состояние:** ✅ ЗАКРЫТ 2026-08-15 — причина найдена, класс вылечен в 6 местах, выкачено и проверено в бою

## Что наблюдалось (бой, `https://ndimspace.app`, гость)

Прогон: `/profile` → «Осмотреться гостем» → «Как меня видят» → системная «Назад».

```
history.length до открытия предпросмотра : 3
history.length после открытия            : 4
history.state после открытия             : {"sveltekit:pageurl":"https://ndimspace.app/profile?guest=1",
                                            "sveltekit:states":{"seeMe":true}}
── history.back() ──
.seeme в DOM                             : 1   ← предпросмотр ОСТАЛСЯ
дети main.body                           : ['seeme']  ← профиля нет вовсе
history.state                            : null ← ушли на запись БЕЗ состояния SvelteKit
```

Человек нажимает «Назад» — и НИЧЕГО не происходит: он остаётся в предпросмотре. Повторное
нажатие уводит его из приложения.

## Ключевая улика — `?guest=1` в записи истории и `history.state: null`

Адрес записи, к которой мы вернулись, — `…/profile?guest=1`, а её `history.state` пуст. То есть
у гостя между «Профилем» и предпросмотром лежит ЛИШНЯЯ запись истории, которую SvelteKit своей
не считает: `popstate` на ней не переводит `page.state.seeMe` в `false`, и ветка предпросмотра
продолжает рисоваться.

⚠️ Это ГИПОТЕЗА о причине (улика сильная, но механика не прослежена по коду). Проверяется на
стенде через дверь `?as=guest` и сравнением с ВОШЕДШИМ пользователем, у которого тот же переход
работает — на стенде он снят кадрами при починке `bugs/117`.

## Почему это не поймали раньше

Инвариант «системная „Назад“ закрывает предпросмотр и оставляет в Профиле» стережёт
`verify-bug105` — но **на стенде и ВОШЕДШИМ пользователем**. Гостевой путь в бою не проверял
никто: боевые смоуки ходили только по публичным страницам. Дефект нашёл первый же прогон
`verify-prod-signed-in`, написанного по требованию владельца («после каждого деплоя залогинься и
пройди смоук»).

## Что делать дальше

1. Воспроизвести на стенде: `npm run stand`, `…/profile?as=guest` → предпросмотр → «Назад».
   Если воспроизводится — дефект не боевой, а общий для гостя, и чинится там же.
2. Найти, кто заводит запись `?guest=1` (`continueAsGuest` в `src/routes/profile/+page.svelte`) и
   почему она попадает в историю: `goto` с параметром вместо `replaceState` — вероятный корень.
3. Лечение проверять ОБЕИМИ ролями: гость и вошедший, иначе починка одной роли снова оставит
   вторую (ровно этот класс и породил баг).
4. Инвариант добавить в `verify-bug105` для ГОСТЯ (сейчас он покрыт только для вошедшего) —
   и в `verify-prod-signed-in`, где он уже стоит парной проверкой «есть что мерить».

## ✅ ПРИЧИНА И ПОЧИНКА (2026-08-15)

**Корень — один символ, и он же класс.** Очистка одноразового параметра делалась голым

```js
history.replaceState(null, '', '/profile');   // ← null стирает состояние роутера
```

Первый аргумент `replaceState` — это НЕ «ничего не менять», а новое состояние записи. `null`
затирал объект, который держит в записи SvelteKit (`sveltekit:history`, `sveltekit:states`).
Дальше запись выглядела для роутера чужой: `popstate` на ней не восстанавливал `page.state`,
предпросмотр не закрывался, а второе нажатие «Назад» уносило человека ИЗ ПРИЛОЖЕНИЯ — ровно как
описал владелец: «переход назад из „как меня видят“ выполнил выход из приложения. Значит ты
неправильно в стек начальное положение приложения записываешь».

**Лечение — `src/lib/ui/history.ts` → `replaceUrl(url)`**: сохраняет `history.state` вместо
затирания. Заменены ВСЕ шесть мест класса (`profile` ×2, `account`, `delete-account` ×2,
`test/[slug]`); голый `history.replaceState` в коде продукта больше не встречается.

**Проверено наблюдением** (стенд, гость): после входа `history.state` не пуст, «Назад» закрывает
предпросмотр, `main.body` содержит `card · intro · col · col`. В бою после выката —
`verify-prod-signed-in` **24/0**, включая «возврат закрыл предпросмотр» на 390 и 1440.

## Как этот дефект вообще нашёлся

Его нашёл ПЕРВЫЙ ЖЕ прогон нового смоука `verify-prod-signed-in`, написанного по требованию
владельца после аварии `bugs/124`. До этого гостевой путь в бою не проверял никто: боевые смоуки
ходили только по публичным страницам. Цена промедления — владелец ловил это руками.
