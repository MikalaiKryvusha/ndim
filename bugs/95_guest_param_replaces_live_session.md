# Bug 95 — `?guest=` в бою молча заменяет живую сессию настоящего аккаунта новым гостем

**Статус:** 🔴 OPEN · **Когда/контекст:** найден 2026-07-31 аудитом Fable 5 после сессий слабых
моделей (ревизия кода + состязательная проверка) · **Серьёзность:** major

## Симптом

Человек с живой сессией НАСТОЯЩЕГО аккаунта открывает `/profile?guest=1` — и вместо своего
пространства получает **свежезаведённого анонимного гостя**: сессия аккаунта выброшена, заведён
пустой `users/{anonUid}`, воронка засчитала ложный `guest_start`. Ожидаемое поведение — как у
обычного входа: живая сессия уважается, параметр игнорируется.

Особенно больно это бьёт сразу после апгрейда: гость только что создал аккаунт — и первое же
обновление страницы отбирает его обратно. Человек, не заметив подмены, ставит оценки по
измерениям уже во **вторую** (гостевую) точку — труд расщепляется между двумя UID.

## Воспроизведение (детерминированное)

1. Войти гостем через `/profile?guest=1` (боевая гостевая дверь, plans/03).
2. Апгрейдиться в аккаунт через Google-попап (`startGoogle` → `linkWithPopup`) — URL при этом
   **не меняется**, в адресной строке остаётся `/profile?guest=1`.
3. Нажать F5.
4. `onMount` снова видит `?guest` → `signInAnonymously` при НЕ-анонимном `currentUser` создаёт
   НОВОГО анонима → только что созданный аккаунт выкинут из сессии.

Тот же отказ без всякого апгрейда: любой вошедший человек с закладкой `/profile?guest=1`.

## Криминалистика

Порядок веток в `src/routes/profile/+page.svelte` (onMount, :235): ветка `?guest` выполняется
**раньше** любой проверки существующей сессии — `currentSession()` стоит только в `else` (:244):

```ts
} else if (new URLSearchParams(location.search).has('guest')) {
  uid = await signInGuest();
  await ensureSpaceExists(uid, lang);
  guest = true;
  guestCard = localStorage.getItem(GUEST_CARD_KEY) !== 'later';
  void track('guest_start'); // третий шаг воронки (plans/03 этап 4)
} else {
  // Стенд входит сам; в бою — только существующая сессия. …
  uid = await currentSession();
```

`signInGuest` (`src/lib/data/profile.ts:138-141`) — голый `signInAnonymously`; Firebase SDK
переиспользует пользователя только при `currentUser?.isAnonymous`, а при живой НЕ-анонимной
сессии заводит нового анонима и **подменяет сессию**:

```ts
export async function signInGuest(): Promise<Uid> {
  const credentials = await signInAnonymously(devAuth());
  return credentials.user.uid;
}
```

Факты состязательной проверки (закрытые линии опровержения):

- **Стендовая дверь умеет правильно, боевая — нет.** `?as=guest` (`profile.ts:102-105`) сначала
  зовёт `waitForSession()` и переиспользует анонима (`if (user?.isAnonymous) return user.uid;`),
  и лишь потом `signInGuest()`. Боевая ветка `?guest` этой защиты лишена.
- **URL не чистится.** Единственный `history.replaceState` в файле — :314 (почтовая ссылка,
  `finishEmailLink`); `startGoogle` (:412) через `linkWithPopup` (`account.ts:188`) адрес не
  меняет — F5 воспроизводит отказ детерминированно.
- **Это не решение владельца.** `bugs/84` разбирает обратную ловушку и не упоминает
  перезагрузку/закладку; `bugs/87` и интервью №007 В4 сценарий не покрывают.
- **Премисса «в бою» верна.** 2.0 в проде с 2026-07-30, гостевая воронка живая.

## Корневая причина

Гостевая ветка написана из премиссы «`?guest` открывает только человек без сессии» — премисса
молча ломается перезагрузкой после апгрейда и закладкой. Защита «живая сессия настоящего аккаунта
уважается» уже была выстрадана в этом же классе дефектов (`bugs/89`, EXP-0087) и встроена в
стендовый автовход, но на боевую ветку `?guest` перенесена не была. Гипотеза о происхождении:
ветки писались в разное время (гостевая — plans/03 этап 4), git-историей не проверялось.

## План фикса

Симметрия со стендовой дверью `?as=guest` — всё [NOT-TESTED]:

1. В ветке `?guest` сначала дождаться существующей сессии (`waitForSession`/`currentSession`).
2. Есть НЕ-анонимная сессия → вести себя как обычный вход: параметр игнорируется, человек в своём
   пространстве.
3. Есть анонимная → переиспользовать её (тот же UID, труд гостя цел).
4. Сессии нет вовсе → только тогда `signInGuest()` и `guest_start`.
5. После обработки параметра — `history.replaceState(null, '', '/profile')`, чтобы F5 и закладка
   не несли `?guest` дальше (как уже делает `finishEmailLink`, :314).
6. Страж — расширение `verify-bug84`: «апгрейд гостя → F5 по `/profile?guest=1` → сессия аккаунта
   ЖИВА, нового гостя не заведено». Мутация — вернуть старый порядок веток, страж обязан
   покраснеть.
