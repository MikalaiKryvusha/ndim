# Баг 155 — Область чтения `relations` шире, чем описано в комментарии и схеме

> **Контекст:** находка защитного аудита собственного кода (идея `ideas/39`), направление —
> приватность. Это не описание чужой уязвимости, а сверка нашей же конфигурации прав доступа с
> нашими же документами, которые её описывают.

**Заведён:** 2026-08-21, аудит · **Родитель:** `firestore.rules` ·
**Статус:** ✅ **ЗАКРЫТ 2026-08-21 решением владельца** (№041 В1: «*Админ может всё*») —
расхождение устранено В СТОРОНУ ОПИСАНИЙ, право закреплено тестом; см. раздел закрытия ·
**Исходящее:** `reports/KAIF_AUDIT/2026-08-21_full_SUMMARY.md` · интервью №041 В1

## Суть расхождения

Правило `relations/{ownerId}` даёт право чтения двум ролям — владельцу и админ-клейму. Три
документа проекта описывают это правило как «чтение доступно только владельцу», и ни один модуль
приложения вторым правом не пользуется. То есть конфигурация и её описание разошлись.

## Улики (цитаты, байт в байт)

`firestore.rules:275-281`:

```
// ── relations/{uid} — посчитанные связи ─────────────────────────────────
// Похожесть — величина приватная. Читает только владелец.
…
match /relations/{ownerId} {
  allow read: if isSelf(ownerId) || isAdmin();
```

`src/lib/model/schema.ts:211`:

```
/** `relations/{uid}` — топ похожих. Читает **только владелец**, пишет **только сервер синхронизации**. */
```

Комментарий самого правила и схема говорят одно, правило разрешает больше — расхождение
«истина ↔ зеркало» внутри одного файла.

## Подтверждено проверкой, а не только чтением (метод `EXP-0172`)

Временный тест правил на эмуляторе (2026-08-21) показал: с админ-клеймом документ
`relations/alice` читается — то есть право реально действует, а не только записано. Контрольный
случай (обычный подтверждённый пользователь) в чтении отказано — значит инструмент проверки
исправен и не красит всё зелёным. Тест снят после прогона. Воспроизведение: добавить в
`tests/rules/rules.test.ts` временный случай и прогнать `npm run test:rules`.

## Почему это стоит поправить

- Прецедент `bugs/100` (закрыт): тот же клейм у коллекции `points` стоял «с первого коммита
  правил вопреки собственному описанию того коммита» и был снят аудитом. Основание —
  интервью №002 В4 и `ideas/13`: доступ админа к личным оценкам не предусмотрен. Похожесть —
  производная тех же оценок.
- Правом никто не пользуется: грепом по `src/` обращений к чужим `relations/` нет; в наборе
  тестов правил проверки на это разрешение тоже нет — оно существует, но нигде не закреплено.
- Тот же админ-хвост есть у `users/{uid}` (rules:111, при комментарии строкой выше «никто, кроме
  владельца, не читает даже факт существования документа»), у бакетов профиля (rules:143) и у
  `friendships` (rules:182). Это отдельные случаи одной семьи; у них возможна законная нужда
  будущей админ-панели (`ideas/13`), поэтому судьба каждого — решение владельца (интервью №041 В1),
  а не общий снос «до кучи».

## Направление приведения в соответствие

Для `relations`: снять `|| isAdmin()` — по прецеденту `bugs/100`, так как описание и схема уже
объявляют «только владелец», а потребителя в коде нет. Если владелец решит сохранить право за
будущей панелью — тогда обновить оба комментария и закрепить разрешение явным тестом, чтобы оно
перестало быть незадокументированным.

## Приёмка (наблюдаемый критерий)

`npm run test:rules`: добавленный тест «админ не читает чужой `relations`» зелёный, набор целиком
зелёный; греп `isAdmin` внутри блока `match /relations` пуст. Сегодняшнее состояние замерено
проверкой — право действует, критерий сегодня красный.

## Границы (что не трогать)

- `allow read: if isSelf(ownerId)` и `allow write: if false` — верны, это и есть приватность.
- Админ-чтение `users/`, `profile/`, `friendships/` не снимать заодно: судьба каждого решается
  владельцем в №041 В1.

## ✅ ЗАКРЫТИЕ 2026-08-21 — решением владельца, в сторону описаний

**Слово владельца (интервью №041, В1, дословно):** «*не понимаю вопрос. Админ может всё.
О чём вопрос?*» — то есть широкое чтение админ-клейма по всем четырём коллекциям —
**замысел**, а дефектом было то, что замысел нигде не записан и не закреплён.

Исполнена ветка, предусмотренная разделом «Направление» выше («если владелец решит сохранить
право — обновить оба комментария и закрепить разрешение явным тестом»):

1. **Комментарии правил** названы по замыслу у всех четырёх мест: `users/{uid}`,
   `users/{uid}/profile/{bucketId}`, `friendships/{pairId}`, `relations/{ownerId}` — каждое
   ссылается на №041 В1 и потребителя (панель, `ideas/13`).
2. **`schema.ts`** приведён: строки о `users/{uid}` и `relations/{uid}` называют оба
   права чтения.
3. **Тест-закрепление** — `tests/rules/rules.test.ts`, блок «Админ-чтение — замысел
   владельца»: четыре чтения админом зелёные + контроль прибора (обычному подтверждённому
   те же четыре отказаны). Набор правил: **148/148**.
4. **Страж доказан мутацией:** временно снятое право в `relations` окрасило ровно новый
   тест (147/1), после возврата — снова 148/0. Право перестало быть незакреплённым.

⚠️ Приёмка, записанная при заведении («греп `isAdmin` внутри `relations` пуст»), писалась
под ДРУГУЮ ветку решения и владельцем отменена — действующий критерий: замысел записан в
комментариях, схеме и закреплён тестом. Поведение правил НЕ менялось ни на бит; выкат
правок комментариев уедет вместе с ближайшим выкатом правил (белый список эпика 60).

🔑 **Границы замысла «админ может всё» это закрытие НЕ двигает:** оценки (`points`) админ
по-прежнему не читает — «админ не исключение» (`bugs/100`, интервью №002 В4); обе стороны
границы стоят под тестами.
