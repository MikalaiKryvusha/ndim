## Симптом (предсказанный, не наблюдённый)

Человек оценил, зашёл на «Связи» — и до конца сессии видит топ, посчитанный ДО его оценки.
Внешне неотличимо от дефекта Ф2, который фаза 3 закрыла: жест обновления показывает правильные
числа, сам экран — нет.

## Механизм — из кода обеих сторон

**Сервер синхронизации пишет в двух шагах** (`sync-server/index.mjs`, порядок сознательный,
`bugs/93`): сначала батчем коммитятся топы (`relations/{uid}`, ~строка 1475), и только ПОСЛЕ
этого транзакцией снимается `dirty` (`{ dirty: false, lastSync: now … }`, ~строка 1647).

**Клиент читает оба документа ОДНОВРЕМЕННО** (`src/lib/data/relations.ts` → `fetchRelations`):

```ts
const [snapshot, point] = await Promise.all([
  getDoc(doc(store, 'relations', uid)),
  waiting ? getDoc(doc(store, 'points', uid)).catch(() => null) : Promise.resolve(null),
]);
if (point !== null) settleSyncWait(point.exists() ? (point.data() as PointDoc) : null);
```

Порядок прилёта двух параллельных чтений не определён. Плохая раскладка:

| момент | что происходит |
|---|---|
| `R_топ` | чтение топа застаёт СТАРЫЙ `relations/{uid}` (сервер ещё не закоммитил) |
| `T_топ` | сервер коммитит новый топ |
| `T_dirty` | сервер снимает `dirty` |
| `R_точка` | чтение точки видит `dirty === false` → **окно закрывается** |

Результат: в кэш легла СТАРАЯ запись топа, а окно закрыто. Дальше `loadRelations` берёт
`FRESH.server = ∞`, и `cached()` отдаёт эту запись **до конца сессии** — новых чтений не будет
(`cache.ts` → `cached`: свежесть считается в момент чтения, запись живёт вечно).

Условие ошибки: `R_точка − R_топ > T_dirty − T_топ`. То есть разброс двух параллельных чтений
должен перекрыть паузу сервера между коммитом топов и снятием флага. Оба числа малы — поэтому
вероятность низкая, но нулевой она не становится, а последствие ровно то, что фаза лечила.

## Почему это НЕ ловится существующими проверками

- Юниты `cache.test.ts` проверяют жизнь ключа окна, а не порядок двух сетевых чтений.
- Зонд `tools/probe-guest-screen.mjs` заморозку значений не видит вовсе (`bugs/160`).
- В `fetchRelationsSummary` — та же пара в одном `Promise.all` и та же гонка.

## Предлагаемая починка (одна строка порядка, без новой механики)

Читать **точку ПЕРВОЙ**, топ — после неё. Тогда `dirty === false` в точке гарантирует, что
коммит топа уже случился ДО начала чтения топа, и закрытие окна не может лечь на устаревший
снимок. Цена — одно последовательное чтение вместо параллельного, и только пока окно открыто.

Альтернатива, если параллельность дорога терять: закрывать окно не по `dirty`, а по сверке
`relations.computedAt >= points.lastSync` — тогда устаревший топ окно не закроет.

## Критерий приёмки починки

1. В окне ожидания подтверждение `dirty === false` **не может** относиться к топу, прочитанному
   раньше коммита сервера (порядком чтений или сверкой `computedAt`/`lastSync`).
2. Проверка, доказанная мутацией: тест слоя данных с подставным чтением, где точка «чистая», а
   топ старый, — на нынешнем коде окно закрывается (красный), на починенном остаётся открытым.
3. Вне окна ожидания число чтений не выросло (контракт экономии №005 В4 не тронут).
