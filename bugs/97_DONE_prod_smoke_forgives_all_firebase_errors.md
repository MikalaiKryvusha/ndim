# Bug 97 — боевой смоук прощает ВЕСЬ класс FirebaseError, а не только отказы правил гостю

**Статус:** ✅ ПОЧИНЕНО 2026-07-31 · **Когда/контекст:** найден 2026-07-31 аудитом Fable 5 после
сессий слабых моделей (ревизия кода + состязательная проверка) · **Серьёзность:** major

## Симптом

Шапка стража `tools/verify-prod-b4.mjs` обещает: «консоль чиста (отказы правил Firestore гостю —
ожидаемы и отфильтрованы)». Фактический же фильтр прощает **любую** ошибку Firebase: битый
API-ключ, недоступный Firestore, любой код `auth/…`. Выкат со сломанным слоем данных или
авторизации сыплет ошибки на всех 20 комбинациях экран×тема×ширина — а страж печатает
«консоль чиста…» и зелёный итог 81/81.

Наблюдаемое отличие от ожидаемого: единственная чувствительная к слою данных проверка боевого
смоука нейтрализована — сломанный Firebase-конфиг уезжает в бой с зелёным вердиктом.

## Воспроизведение (детерминированное)

1. Мутация без выката: подсунуть в поток консоли страницы строку вида
   `FirebaseError: [code=unavailable]` или `FirebaseError: auth/invalid-api-key`
   (например, `addInitScript` с `console.error(...)` в копии стража).
2. Запустить `node tools/verify-prod-b4.mjs`.
3. Ожидаемое от честного стража: провал «консоль чиста». Фактическое: `EXPECTED` матчит строку
   по альтернативам `FirebaseError` и `auth/` — шум не копится, все проверки зелёные. [NOT-TESTED]

## Криминалистика

Фильтр (`tools/verify-prod-b4.mjs:30–31`), под комментарием, обещающим узкое:

```js
/** Отказы правил гостю — ожидаемое поведение, а не дефект. */
const EXPECTED = /permission|insufficient|Missing or insufficient|FirebaseError|auth\/|unauthenticated/i;
```

Применение (строки 51–52 и 80):

```js
page.on('console', (m) => {
  if (m.type() === 'error' && !EXPECTED.test(m.text())) noise.push(m.text());
});
…
ok(noise.length === 0, `${tag}: консоль чиста${…}`);
```

Факты состязательной проверки (закрытые линии опровержения):

- **«Это конвенция проекта»** — нет. Сёстры-стражи фильтруют только узко:
  `verify-bug84.mjs:149,243` и `verify-bug87.mjs:76` — `permission|insufficient|Missing or
  insufficient`. Широк уникально `verify-prod-b4`.
- **«Остальные проверки скрипта поймают»** — нет. Контент-проверки (высота > 300, текст > 50
  символов, фон темы, строки 68–78) проходят у гостя даже при полностью отваленном слое данных:
  скрипт УЖЕ проходит 81/81 при живых `permission-denied` в консоли. Проверка контракта свежести
  (строки 89–102) грепает статический JS-чанк, который раздаётся независимо от работоспособности
  Firebase-конфига.
- **«Одноразовый скрипт»** — нет. `STATUS.md` ссылается на `verify-prod-b4` как на постоянный
  смоук боя после ~дюжины выкатов.
- **«Так решил владелец»** — задокументированного решения о широком фильтре нет.

Заявленная цель (шапка, строки 7 и 30 — «отказы правил Firestore гостю») покрывается уже узкими
альтернативами `permission|insufficient`; остальные три альтернативы — чистый перебор.

## Корневая причина

Фильтр писался «чтобы зелёнело» на реальном шуме гостевой сессии и был расширен до целого класса
вместо конкретных наблюдаемых текстов. Обещание в комментарии и регэксп разошлись: комментарий
описывает отказы правил, регэксп прощает всю платформу Firebase. Точный коммит-виновник в
git-истории не устанавливался — гипотеза, требующая `git log -p` по файлу. [NOT-TESTED]

## План фикса

1. Сузить фильтр до канона сестёр: `/permission|insufficient|Missing or insufficient/i`.
   [NOT-TESTED]
2. `unauthenticated` вернуть только точечно, ЕСЛИ гостевой Auth-отказ реально наблюдается в бою —
   сначала снять фактический текст ошибки живым прогоном, потом решать. [NOT-TESTED]
3. Мутация: подсунуть `FirebaseError: [code=unavailable]` в поток консоли (или временно вернуть
   широкий фильтр) → страж обязан покраснеть на «консоль чиста». [NOT-TESTED]
4. Перечитать шапку — обещание и фильтр должны совпадать дословно.
5. Контрольный прогон `node tools/verify-prod-b4.mjs` на живом бое: 81/81 при узком фильтре —
   доказательство, что реальный гостевой шум узким фильтром покрыт. [NOT-TESTED]
