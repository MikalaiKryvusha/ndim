# Bug 173 — [Одобрить] в комнате «Измерения» выбрасывает комментарий владельца

**Статус:** 🟢 ПОЧИНЕН 2026-08-22 (`dev-2`, ветка `ndim_dev2`) — ждёт вердикта QA и мержа ·
**Заведён:** 2026-08-22, Менеджером со слов владельца (чат, дословно ниже) · **Нашёл:** владелец,
проверкой «виден ли мой комментарий агенту» · **Территория:** комната «Измерения» (админ-панель),
контур вычитки кандидатов · **Родня:** `bugs/142` (круг возврата — там комментарий ЖИВЁТ),
`tools/read-returned-candidates.mjs` (обратное плечо)

## Слова владельца (2026-08-22, чат)

> «нет, на кобре "реестр" — это старый комментарий, с которым она возвращалась в работу.
> А сейчас я написал похвалу, что написано по объекту культуры принятие и реакция сообщества —
> я сам такое писал, и такое одобряю в описании объектов культуры. И с таким комментом я нажал
> одобрить — видимо, одобрение не сохраняет комментарий для ИИ агента».

## Симптом

Владелец набирает комментарий и нажимает **[Одобрить]** — комментарий не сохраняется никуда.
Поле `ownerNote` документа держит СТАРЫЙ текст прошлого возврата («Реестр.»).

## Улика — снята с боевой базы до заведения бага

Дамп ВСЕХ полей `dim_candidates/wikidata-Q637290` после одобрения: `tags · source · time ·
description · type · year · title · agentNote · ownerNote · status · approvedDimId`. Поля с
новым комментарием НЕТ; `ownerNote: "Реестр."` — след возврата прошлого цикла. То есть текст
не «не показывается» — он **не записан**.

## Класс

Асимметрия контура: кнопка «Вернуть на доработку» комментарий требует (пустой не пропускает —
`bugs/142`), кнопка «Одобрить» его молча выбрасывает. Внимание владельца, потраченное на текст,
оседает в никуда — ровно тот класс, против которого заведено обратное плечо: «замечание, которое
некому прочитать, равносильно ненаписанному» (шапка `read-returned-candidates.mjs`).

## Ожидание

1. [Одобрить] с непустым комментарием сохраняет его (пустой — законен: одобрение без слов).
2. След возврата НЕ затирается: история «Реестр.» и похвала одобрения — разные события; хранить
   так, чтобы читались оба (отдельное поле или журнал — решает исполнитель по простоте).
3. `read-returned-candidates.mjs` печатает комментарий одобрения (сейчас печатает только
   `ownerNote`) — иначе запись без чтения снова разомкнёт контур.
4. Косметика той же правкой: для статуса `approved` подпись «(пусто — но кнопка возврата пустого
   не пропускает)» вводит в заблуждение — у одобрения пустой комментарий норма.

## Приёмка

На стенде: одобрить тестовую карточку с комментарием → прибор печатает его дословно; вернуть
другую с комментарием → прежнее поведение целό (11 проверок `verify-candidate-return-loop`
зелёные); одобрить без комментария → законно, без следа. Мутация: сломать сохранение → прибор
обязан показать потерю.

## Потерянный текст — восстановлен из чата, в базу не вернулся

Похвала владельца (по «Кобре», абзац о приёме фильма): **описание объекта культуры МОЖЕТ и
ДОЛЖНО нести принятие и реакцию сообщества — «я сам такое писал, и такое одобряю»**. Разнесено:
канон мастерской (Дизайнер) и граница класса для прибора доли меты (dev-3): **реакция
сообщества — НЕ производственная мета**, её прибор не штрафует.

## Починка — 2026-08-22, `dev-2` (ветка `ndim_dev2`)

**Причина, названная воротами намерения.** Код писал в документ тело кандидата плюс статус и
ссылку на рождённое измерение; поле комментария из формы он не читал ВОВСЕ — его читал только
возврат. Поэтому `ownerNote` оставался старым следом прошлого возврата, а новый текст не
существовал нигде. Спецификация (шапка `DimCandidate`, решение владельца 2026-08-02) знала ДВА
поля комментария, а событий в контуре оказалось ТРИ. Расхождение и есть находка: лечится третьим
полем, а не перегрузкой существующего.

**Что сделано** (коммиты `58a5536`, `e58510c`):

1. `ownerApprovalNote` — новое поле: что владелец написал, ОДОБРЯЯ карточку. Запись вынесена
   чистой функцией `approvedRecord` — дефект жил в одной строке того, что пишется в документ, и
   виден был только глазами в браузере; теперь его судит юнит.
2. Экран передаёт комментарий в одобрение, чистит поле после успеха и **подтверждает сохранение
   строкой ответа** — владелец обнаружил потерю сам, проверяя, дошёл ли текст, и экран обязан
   отвечать на этот вопрос сразу. Подсказка в поле называет оба применения.
3. Пустой комментарий законен — поля тогда нет вовсе. Совместимость назад: карточки без нового
   поля читаются как раньше. Правила Firestore не менялись: они судят статус, а не список полей.
4. `read-returned-candidates` печатает слово одобрения отдельной строкой и подписывает пустоту
   ПО СТАТУСУ (у возврата пусто — поломка, у одобрения — норма). `seed-dim-candidates` бережёт
   новое поле наравне со старым.
