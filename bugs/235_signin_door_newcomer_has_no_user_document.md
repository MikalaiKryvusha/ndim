## Симптом

Человек, которого у нас ещё не было, вводит свою почту на двери входа «У меня уже есть аккаунт»,
получает письмо, переходит по ссылке — и попадает на экран **«не удалось загрузить»**
(`stand = 'down'`), а не в свой профиль. Аккаунт при этом **создан**: Firebase завёл его молча.

## Причина — чтением кода

Документ `users/{uid}` заводит **только** `ensureSpaceExists`, и зовут её только на ГОСТЕВОМ
пути (`/profile?guest=1`, стендовая дверь `?as=guest`, ветка `already-in-use`). Путь
«вошёл ссылкой, гостем никогда не был» её не зовёт **вообще**:

```
дверь signedout → requestLink → письмо → возврат по ссылке
  → completeLoginLink: сессии нет → signInWithEmailLink → created: true
  → loadScreen(uid) → ProfileMissingError
  → catch: isGuestSession() ложно → stand = 'down'
```

`profile/+page.svelte`, ветка `catch`: обработка `ProfileMissingError` написана **только для
гостя** («у гостя документа может не быть, и это норма» — `bugs/87`). У не-гостя тот же симптом
уводит на технический экран отказа.

🔑 **Класс тот же, что у `bugs/233`: продукт ставит человеку ЛОЖНЫЙ ДИАГНОЗ.** Там живую ссылку
объявляли мёртвой, здесь отсутствие документа объявляют поломкой базы. И там и там настоящая
причина («мы не знаем почту», «документ ещё не заведён») подменяется выдуманной.

## Кого это задевает на самом деле — граница названа честно

- **331 человека из 1.x это НЕ задевает:** их документы приехали миграцией.
- **Гостя это НЕ задевает:** документ заводится в момент рождения гостя.
- **Задевает того, кто вошёл почтой, НИ РАЗУ не побыв гостем.** Дверь «У меня уже есть аккаунт»
  не спрашивает, есть ли он: Firebase заводит аккаунт по первой же ссылке.

⚠️ **Сколько таких людей приходит — НЕ ЗАМЕРЕНО, и выдумывать это число запрещено.** Замер
достижим: события воронки в PostHog плюс сверка `users/` с Auth. До замера тяжесть держится на
S2 (потерян путь человека), а не на S1.

## План фикса (не начат)

1. **Завести документ там, где рождается аккаунт, а не там, где рождается гость.** Кандидат —
   вызвать `ensureSpaceExists` на успешном возврате по ссылке при `created: true`, рядом с
   `track('account_created')`. Проверить, не задевает ли это путь апгрейда гостя (там документ
   уже есть, а `ensureSpaceExists` идемпотентна по построению).
2. **Обработку `ProfileMissingError` развести по СОСТОЯНИЯМ, а не по «гость / не гость».**
   «Документа ещё нет у только что созданного аккаунта» и «база недоступна» — разные вещи, и
   технический экран отказа положен только второй.
3. **Страж:** прогон «новый человек входит ссылкой, гостем не был» обязан доходить до профиля.
   Доказать мутацией — снять вызов `ensureSpaceExists` и увидеть красное.

## Приёмка

1. Чистый браузер, почта, которой у нас не было → дверь «У меня уже есть аккаунт» → ссылка →
   человек видит СВОЙ профиль, а не «не удалось загрузить». Ручной функциональный прогон, кадры.
2. Путь апгрейда гостя не задет: UID и труд сохраняются, поздравление показывается как прежде.
3. Настоящая недоступность базы по-прежнему уводит на технический экран — контроль, который
   обязан остаться красным-честным.
4. 🔴 Ручной функциональный прогон живым браузером, отчёт в `qa/reports/`.
