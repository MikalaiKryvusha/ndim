## Симптом

Документ суток воронки называется ключом, вычисленным в **UTC**:

```ts
/** Ключ дня в UTC — `2026-07-12`. Один документ на сутки. */
function today(): string {
  return new Date().toISOString().slice(0, 10);
}
```
`src/lib/data/funnel.ts:56-59` · тот же ключ читает `readFunnelDay()` (строка 93).

Пока числа читались из консоли раз в жизни (`bugs/202`, дефект 3), сдвиг ключа никого не
трогал. Фаза 1 строит **экран** этих суток для владельца — и с этого момента строка «сегодня»
на экране обязана означать те же сутки, которые владелец видит на своих часах.

## Замер, а не рассуждение

Прогон на машине проекта (`Europe/Moscow`, UTC+3), 2026-08-28 15:50:

| Момент (локальный) | Ключ UTC | Ключ по локальным часам |
|---|---|---|
| Fri Aug 28 2026 15:50 | `2026-08-28` | `2026-08-28` |
| Fri Aug 28 2026 01:30 | **`2026-08-27`** | `2026-08-28` |

**Направление ошибки при UTC+3 одно:** первые три часа локальных суток (00:00–02:59) падают в
документ ПРЕДЫДУЩЕГО дня. Вечер не задет.

⚠️ **Поправка к соседнему уроку, снятая этим замером.** `EXP-0208` и `bugs/195` описывают класс
формулой «вечером прибор судил ЗАВТРАШНИМ днём, ночью — вчерашним». Для UTC+3 верна только
вторая половина: `toISOString()` вечером отдаёт СЕГОДНЯШНЮЮ дату (21:00 локально = 18:00 UTC).
«Завтрашним днём» UTC-ключ судит при ОТРИЦАТЕЛЬНОМ смещении. Класс тот же, формула в уроке шире
правды — правится строкой, факты не трогаются.

## Чем это бьёт по фазе 1 конкретно

1. **Ворота фазы `plans/74` неисполнимы, как заданы.** Их формулировка: «в день боевого смоука
   `guest_start` не прыгает — чтение дня против журнала двери выката». Журнал выката ведётся по
   локальным часам, документ дня — по UTC. Ночной выкат (в этом проекте они бывают: миграция
   00:54, работа «до полуночи») ляжет во вчерашний документ, и сверка «день против журнала» даст
   расхождение, которого в продукте нет. То есть прибор врал бы о СВОЕЙ ЖЕ приёмке.
2. **Экран, построенный на кривом ключе, перестраивается после.** Таблица дней и «сумма недели»
   считаются по границам суток; менять границу после того, как экран сдан, — двойная работа
   (довод Менеджера в постановке смены 7).

## Корневая причина

`new Date().toISOString()` переводит момент в UTC ПО ОПРЕДЕЛЕНИЮ, а `.slice(0, 10)` берёт от
этого UTC-момента календарную дату. Комментарий над функцией честен («Ключ дня в UTC») — дефект
не в том, что код обманывает, а в том, что **выбранная граница суток не совпадает с границей
суток у того, кто эти числа читает**.

## Лечение

Ключ считается **по часовому поясу владельца** — одна именованная константа, а не «часы того,
кто пишет».

🔑 **Почему НЕ «локальные сутки браузера пишущего», хотя так проще.** `track()` исполняется в
браузере ПОСЕТИТЕЛЯ, и посетители живут по всему миру. Ключ по часам посетителя превращает
строку «2026-08-29» в смесь двух с лишним десятков разных 24-часовых интервалов: событие из
Японии попадает в неё за 15 часов до события из Калифорнии. Такой ряд определён ХУЖЕ, чем
UTC-ряд, — то есть лечение частично било бы по собственной цели. Фиксированный пояс владельца
даёт и постоянный 24-часовой интервал у каждой строки, и совпадение с его часами.

Реализация — `Intl.DateTimeFormat('en-CA', { timeZone: … })`: отдаёт `YYYY-MM-DD` штатно, без
своей арифметики смещений и без таблицы переходов (best practice вместо велосипеда).

## Шов ряда — назван честно, задним числом ничего не переписывается

`plans/74`: «*не чистит прошлые числа воронки задним числом — разрыв ряда честно помечается
датой*».

- Дни с `2026-08-01` (снятие предохранителя) по день выката — ключ **UTC**.
- Со дня выката — ключ **по часам владельца**.
- **Шов — ровно один день, и он двойной по трём часам:** события 00:00–02:59 локального дня
  выката уже записаны в предыдущий UTC-документ, а всё, что после правки, — в свой.
- **Цена шва при наших числах ≈ ноль:** `landing_view` 154 за 25 дней (~6/сут), `guest_start` 77
  за 25 дней (~3/сут; из них всплески — свои же смоуки, `bugs/202` дефект 2). Три ночных часа
  суток, где сутки дают единицы, — это доли события. Экран обязан показать сноску о шве, а не
  прятать его.
- ⛔ Старые документы НЕ переименовываются и НЕ пересчитываются: имя документа — это факт о том,
  как считали тогда.

## Наблюдаемый критерий приёмки

1. Юнит: при заданном моменте `2026-08-28T22:30:00Z` ключ равен **`2026-08-29`** (для пояса
   владельца UTC+3), а не `2026-08-28`. Юнит принимает момент аргументом — иначе он проверяет
   часы машины прогона, а не функцию.
2. Юнит: полдень остаётся собой — `2026-08-28T12:00:00Z` → `2026-08-28`.
3. Экран воронки показывает день с историческими UTC-данными и НЕ падает (ключей, которых нет,
   он не требует).
4. Мутация: вернуть `toISOString().slice(0,10)` → юнит 1 краснеет адресно.

## Решения, принятые без владельца

- **Пояс владельца зашит константой, а не читается из его профиля.** У проекта нет поля «часовой
  пояс владельца», заводить его ради ключа дня — новая сущность против Оккама. Константа названа
  и стоит в одном месте; смена пояса — правка одной строки.
- **Ряд не пересчитывается.** Прямое требование `plans/74`; альтернатива (перенести три ночных
  часа в соседние документы) требует поминутных отметок, которых воронка не хранит ПО ЗАМЫСЛУ
  (в документе только числа, ничего персонального) — то есть невыполнима по построению.
- 🔴 **Расхождение с буквой постановки Менеджера, названное вслух:** он написал «ключ — локальные
  сутки машины/браузера пишущего». Исполнено «сутки по поясу владельца» — довод выше (ряд по
  часам посетителя определён хуже UTC). Цена несогласия — одна константа; строка ждёт его слова.
