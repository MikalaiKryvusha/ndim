# Bug 93 — гонка: `dirty:false` сервера синхронизации затирает свежий `dirty:true` человека

**Статус:** ✅ ПОЧИНЕНО И ПОДТВЕРЖДЕНО В БОЮ 2026-07-31 — выкат состоялся пересборкой образа (билд 20 в бою с 09:15)
**Когда/контекст:** найден 2026-07-31 аудитом Fable 5 после сессий слабых моделей (ревизия кода +
состязательная проверка) · **Серьёзность:** minor

## Симптом

Человек ставит оценку по измерению — а его собственный топ Связей её не отражает. Ни через
минуту (обещанный контракт «свой топ — быстро»), ни через час. Оценка сама сохранена честно,
но точка перестаёт числиться «грязной», и сервер синхронизации не пересчитывает её до ночного
полного прохода — то есть до ~24 часов. Особенно больно новичку: `ideas/05` обещает ему первую
ценность ближайшим циклом, а гонка ломает именно это обещание. Самолечится только следующей
оценкой (она снова ставит `dirty:true`).

## Воспроизведение (детерминированное)

1. Новичок оценивает измерения — окно новичка активно, тихий период его не защищает, точка
   попадает в каждый 60-секундный цикл.
2. Цикл сервера синхронизации снимает выборку грязных точек и дочитывает `dims` точки
   (`calculator/index.mjs:534`).
3. **В эти секунды** — между чтением `dims` и коммитом батча (`:613`) — человек ставит ещё
   одну оценку: клиент атомарным батчем пишет `dims/<dimId>` и `dirty:true, updated: Date.now()`.
4. Цикл коммитит свой батч: `dirty:false` перезаписывает свежий `dirty:true`.
5. Итог: последняя оценка есть в `dims`, но в кэше процесса её нет (дочитка уже прошла), а из
   dirty-выборки точка выпала. Топ человека не включает эту оценку до ночного прохода.

Тест-эмуляция: записать оценку между чтением и коммитом цикла → `dirty` обязан пережить цикл.

## Криминалистика

Выборка готовых снимается запросом в начале цикла (`calculator/index.mjs:491`):

```js
const dirtySnap = await db.collection('points').where('dirty', '==', true).get();
```

Их `dims` дочитываются в `:534`, а флаг снимается **безусловным** `batch.set` с `merge`
(`:581–585`), коммит — `:613`:

```js
for (const uid of readyUids) {
  const firstSeen = pointsCache.get(uid)?.firstSeen ?? now;
  writes.push((batch) =>
    batch.set(db.doc(`points/${uid}`), { dirty: false, lastSync: now, firstSeen }, { merge: true }),
  );
}
```

Клиент ставит флаг собственным батчем (`src/lib/data/profile.ts:192–195, 261–270`):

```ts
function dirtyStamp(): Record<string, unknown> {
  const stamp = { dirty: true, updated: Date.now(), lastSync: null };
  ...
}
// saveRating: batch.set(doc(store, 'points', uid), dirtyStamp(), { merge: true });
```

Линии опровержения, закрытые состязательной проверкой:

- **Транзакции/precondition нет.** Firestore-батчи между собой не конфликтуют — по каждому полю
  побеждает последняя запись. Снятие `dirty:false` не проверяет, что `updated` не изменился с
  момента чтения.
- **Тихий период НЕ защищает.** `young` (`firstSeen` пуст или моложе `NEWCOMER_MS`, `:504`)
  обходит `resting` — точка новичка обрабатывается каждым циклом всю первую сессию, окно гонки
  повторяется каждые 60 секунд.
- **Самолечения на клиенте нет.** Лечит только новая оценка или ночной полный проход.
- **Грep по `bugs/`, `ideas/`, `researches/`, `interviews/`, `STATUS.md`:** гонка нигде не
  описана и владельцем не принята как компромисс.

Опасное окно — между чтением `dims` точки (`:534`) и коммитом батча (`:613`).

## Корневая причина

В 1.x цикл пересчёта и клиент жили в одной вкладке браузера (`researches/13`) — межпроцессной
гонки существовать не могло, поэтому у снятия флага и не было защиты. В 2.0 сервер синхронизации
стал отдельным процессом (устройство цикла — `ideas/14`), а снятие `dirty` перенесено как есть:
безусловной записью, без условия «данные не изменились с момента чтения».

## План фикса

1. При дочитке `dims` точки запоминать её `updated` на момент чтения. [NOT-TESTED]
2. Снимать `dirty` не батчем, а **транзакцией** с условием «`updated` не изменился»; изменился —
   оставить `dirty:true`, точка честно пересчитается следующим циклом. [NOT-TESTED]
3. Альтернатива без транзакций: писать `syncedUpdated = прочитанный updated` вместо
   `dirty:false` и выбирать грязных сравнением `updated > syncedUpdated`. Это смена модели
   данных — взвешивать отдельно; по Оккаму точечнее транзакция на снятие. [NOT-TESTED]
4. Тест: эмулировать запись оценки между чтением и коммитом цикла и проверить, что `dirty`
   пережил цикл (до фикса — падает, после — зелёный). [NOT-TESTED]
