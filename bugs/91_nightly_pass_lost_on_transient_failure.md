# Bug 91 — транзиентный сбой Firestore во время ночного прохода теряет суточную сверку на 24 часа

**Статус:** 🔴 OPEN · **Когда/контекст:** найден 2026-07-31 аудитом Fable 5 после сессий слабых
моделей (ревизия кода + состязательная проверка) · **Серьёзность:** major

## Симптом

Если посреди ночного полного прохода сервер синхронизации ловит транзиентную ошибку Firestore
(например, `14 UNAVAILABLE`), проход **не повторяется до следующей полуночи UTC**. Последствия:

- «ленивые» чужие топы не дописаны — разрыв между полными проходами вырастает до ~48 часов,
  нарушен суточный контракт свежести 1.x (комментарий в самом коде: «Чужие топы между полными
  проходами отстают не больше чем на сутки»);
- блок `fullSync` в отчёте сервера остаётся вчерашним, и виджет «Пространства» целые сутки
  показывает «Запланированная» датой **в прошлом** — ровно тот симптом, который владелец в
  `ideas/21` п. 14 читает как поломку.

Ожидаемое поведение: упавший проход должен повториться ближайшим 60-секундным циклом.

## Воспроизведение (детерминированное)

1. Служба `calculator/` работает, ночной проход назначен на 00:00 UTC.
2. В 00:00:30 UTC стартует цикл: `nightly = true`, в памяти ставится `lastFullPassAt = startedAt`.
3. `commitInChunks(writes)` получает от Firestore транзиентный `UNAVAILABLE` и бросает исключение.
4. Исключение доходит до `tick()`, там пишется `ошибка цикла: 14 UNAVAILABLE` — и всё; процесс
   жив, рестарта нет.
5. Следующий цикл (00:01:30): `lastFullPassAt` (00:00:30) ≥ `lastScheduledFullPass` (00:00:00) →
   `nightly = false`; кэш прогрет → `warmup = false`. Полный проход считается выполненным.
6. До следующей полуночи UTC суточной сверки не будет; `fullSync.at` / `nextAt` в базе — вчерашние.

## Криминалистика

`calculator/index.mjs`, строки 481–485: отметка «проход сделан» ставится в памяти **до** всей
опасной работы —

```js
if (fullPass) {
  if (nightly) await cleanupStaleGuests(startedAt); // до перечитки: сироты не должны попасть в кэш
  pointsCache = await loadAllPoints();
  if (writtenTops === null) writtenTops = await seedWrittenTops();
  if (nightly) lastFullPassAt = startedAt;
```

После этой строки идут выборка dirty (строка 491), `commitInChunks(writes)` (613) и запись
отчёта `fullSync` через `reportServer` (640). Исключение из любого из этих шагов ловится только
в `tick()` (строка 691) простым логом:

```js
} catch (error) {
  log(`ошибка цикла: ${error.message}`);
}
```

Повторной попытки нет: `nightly` в следующем цикле уже `false`.

Состязательная проверка закрыла линии опровержения:

1. Это **не задокументированное решение** — `bugs/85` (дизайн-док этой самой фичи) про отказ
   посреди прохода молчит.
2. Автор защитил от ровно этой опасности параллельное состояние `writtenTops` — строки 554 и
   615–617: «писать в writtenTops можно только после успешного коммита… Раньше нельзя: упади
   коммит, кэш считал бы топ записанным и не повторил бы запись никогда». `lastFullPassAt` такой
   защиты не получил — асимметрия доказывает недосмотр, а не выбор.
3. Сценарий реалистичен: `bugs/33` фиксирует реальный ночной 6-часовой сетевой сбой с падающими
   циклами, `bugs/73` — живой лог «ошибка цикла: 14 UNAVAILABLE».
4. Тестов на отказ посреди прохода в `calculator/` нет.

Уточнение: отказы **до** строки 485 (`cleanupStaleGuests`, `loadAllPoints`, `seedWrittenTops`)
безопасны — флаг ещё не выставлен, следующий цикл повторит проход.

## Корневая причина

Флаг успеха выставляется до самого успеха. Отметка `lastFullPassAt` живёт по правилу «начали —
значит сделали», тогда как соседний `writtenTops` в том же файле живёт по правильному правилу
«сделали — значит запомнили». Дефект — незамеченный разрыв между двумя дисциплинами в одной
функции; происхождение по git-истории досье не называет (гипотеза: флаг поставлен рядом с
загрузкой кэша ради читаемости блока `fullPass`, до того как ниже появилась опасная запись).

## План фикса

1. Перенести `lastFullPassAt = startedAt` на место **после** успешной записи отчёта `fullSync`
   (после `reportServer` на строке 640) — симметрично `writtenTops`. Упавший посреди ночного
   прохода цикл оставит отметку старой, и следующий 60-секундный цикл повторит проход целиком.
   [NOT-TESTED]
2. Тест в calc-сюиту: инъекция сбоя записи посреди ночного прохода → следующий цикл обязан
   повторить полный проход и записать `fullSync`. [NOT-TESTED]
3. Граница: при стабильно лежащем Firestore проход будет пробоваться каждый цикл — это приемлемо
   и самолечится, но стоит отметить в логе, что повтор именно ночного прохода. Проверить, что
   зацикливание не порождает лишних записей (все записи и так идут одним упавшим коммитом).
   [NOT-TESTED]
