# Баг 137 — дверь выката закрылась КРАСНЫМ на исправном выкате: замер попадания без повторов

> **Заведён:** 2026-08-17 (пойман первым же прогоном стейджа после закрытия русских правок) ·
> **Родитель:** `plans/53` фаза 3 (замер попадания в контур, критерий П8) ·
> **Статус:** ✅ **ПОЧИНЕН 2026-08-17** — повторы добавлены, «не прочитан» отделён от «отдаётся
> другое»; ⏳ проверка боем — на следующем прогоне двери · **Класс:** ложный КРАСНЫЙ ворот

## Симптом

`npm run deploy -- --stage` прошёл все шаги, Firebase отчитался `+ Deploy complete!`, и дверь
закрылась кодом 1 на последнем замере:

```
══ 🔑 замер попадания в контур (П8) ══
  цель  СТЕЙДЖ: сборка feh4jj · сайт отдаёт  не прочитан
  сосед БОЙ: было 3ak94l · стало 3ak94l

🔴 СТЕЙДЖ отдаёт НЕ ту сборку, которую мы собрали. Выкат не дошёл до цели.
```

**А выкат дошёл.** Проверено руками через минуту после отказа:

| Адрес | HTTP | Хеш рантайма |
|---|---|---|
| `https://ndim-stage.web.app/ru` | 200 | **`feh4jj`** — ровно наша сборка |
| `https://ndim-stage.web.app/en` | 200 | **`feh4jj`** |
| `https://ndim-stage.web.app/` | 200 | нет хеша — это распознаватель языка, не приложение |

То есть дверь покрасила красным исправную работу и НЕ выписала расписку стейджа.

## Почему это дорого

1. **Без расписки заперт выкат в бой.** Замок требует расписку с ТЕМ ЖЕ коммитом; ложный красный
   означает, что бой откладывается на целую пересборку (у нас это 20 645 файлов) из-за одного
   сетевого чиха.
2. **Ложный красный портит доверие к воротам ровно так же, как ложный зелёный.** Ворота, которые
   врут в одну сторону, начинают отключать — а этими воротами держится весь порядок «стейдж → бой».
3. **Формулировка отправляла искать не ту поломку.** Сессия прочла бы «отдаёт НЕ ту сборку» и пошла
   бы разбираться с хостингом и кешами, тогда как проблема была в приборе.

## Причина

`tools/deploy.mjs`, функция `liveHash`: **один запрос, без повторов**, и любая осечка сводится к
`null`.

```js
async function liveHash(site) {
	try {
		const response = await fetch(`${site}/ru`, { redirect: 'follow' });
		const html = await response.text();
		return html.match(/__sveltekit_([a-z0-9]+)/)?.[1] ?? null;
	} catch {
		return null;               // ← и сеть, и отсутствие хеша, и 500 — всё одним `null`
	}
}
```

Вызывается **сразу** после релиза хостинга, а Firebase Hosting раскатывает релиз не мгновенно.
Дальше сравнение `targetAfter !== builtHash` трактует `null` как «там ДРУГАЯ сборка».

🔑 **И это второй, менее заметный дефект в той же строке:** `null` означает «я не смог прочитать» —
утверждение о ПОИСКЕ. Оно подано как утверждение о МИРЕ («отдаёт не ту сборку»). Ровно класс
`EXP-0165`, за который проект уже платил: судья обвинил выкат в самоуправстве, поискав разрешение
не там, где оно лежало.

⚠️ **Что НЕ является причиной, хотя выглядит похоже.** Дверь читает `/ru`, а не корень, и это
верно: корень — распознаватель языка и хеша не несёт. Урок про корень в приборе уже записан
(шапка `smokeGate`) и был учтён. Здесь дело не в адресе.

## Лечение

1. ✅ **Повторы:** 6 попыток с паузой 2,5 с (до 15 с ожидания). Пауза здесь не «на всякий случай»,
   а единственная разница между исправным выкатом и ложным красным.
2. ✅ **`liveHash` возвращает `{ hash, why }`** — и причину неудачи печатает вызывающий.
3. ✅ **Две РАЗНЫЕ ветки отказа** вместо одной:
   · `hash === null` → «ХЕШ НЕ ПРОЧИТАН после N попыток — причина: …», с прямым указанием проверить
     руками и с оговоркой «выкат мог дойти, а замер — нет»;
   · `hash !== builtHash` → «отдаёт НЕ ту сборку (X вместо Y)» — с ОБОИМИ числами, чтобы не гадать.
4. ✅ `node tools/deploy.mjs --selftest` — **8 проверок, 0 провалов** (стоп-правило контура цело).

## Чего в лечении НЕТ и почему

⛔ **Повторы не превращены в «ждать, пока сойдётся».** Число попыток конечно, и при подлинном
расхождении дверь по-прежнему краснеет — иначе лечение ложного красного родило бы ложный зелёный,
что строго хуже. Порог выбран из наблюдения: живой стейдж отдал верный хеш меньше чем через минуту.

## Проверка боем — что именно проверено, а что нет

✅ **Повторный прогон `npm run deploy -- --stage` прошёл замер П8 успешно** (2026-08-17, сборка
`1g0erkt`): «✅ сборка легла в заявленный контур, соседний не тронут». Дальше дверь прошла заголовки
кеширования (16/0) и невидимость стейджа роботам (11/0).

⚠️ **Но этот прогон НЕ доказывает, что сработали именно повторы.** Он мог прочитать хеш с первой же
попытки — раскатка хостинга не обязана запаздывать дважды. Наблюдение здесь подтверждает только то,
что дверь больше не краснеет; механизм лечения остаётся недоказанным.

🔑 **Отсюда доделка, без которой починка была бы неулиточной:** при успехе с попытки > 1 замер теперь
**печатает номер попытки** — «хеш прочитан с попытки 3 из 6, раскатка запаздывала». Прогон,
прошедший сразу, и прогон, спасённый третьей попыткой, до этой строки выглядели одинаково, и
следующая сессия поверила бы зелёному, не зная, работает ли повтор вообще. Это тот же принцип, по
которому в проекте не доверяют молчащим воротам.

⏳ **Что остаётся `[NOT-TESTED: медленная раскатка]`:** сама ветка повтора и ветка «ХЕШ НЕ ПРОЧИТАН
после N попыток». Обе воспроизводятся только настоящей медленной раскаткой, подделывать её
подменой окружения нельзя (`EXP-0159`: ломать надо КОД, а не окружение) — а временный `throw` внутри
двери выката стоил бы дороже, чем ждёт этот класс. Улика теперь появится сама, в первом же прогоне,
где раскатка запоздает.
