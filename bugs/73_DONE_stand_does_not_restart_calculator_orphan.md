# Bug 73 — `npm run stand` молча не поднимается после предыдущей остановки: сирота-сервер синхронизации держит стенд

наблюдениями · **Заведён и закрыт:** 2026-07-29 агентом, попутно при работе над `bugs/72` и
`bugs/40` · ⚠️ **в бой не относится** (это оснастка разработчика, продукта не касается)

## ✅ ФИКС (2026-07-29) `[TESTED: 2026-07-29 · три наблюдения, см. таблицу]`

`tools/stand.mjs`, три правки:

1. **Убийство по ДЕРЕВУ.** `child.kill()` на Windows убивал только обёртку `cmd.exe` (мы запускаем
   с `shell: true`, иначе не стартуют `.cmd` от npm/npx), а внук-`node` выживал. Теперь на win32
   — `taskkill /pid <pid> /T /F`, который гасит процесс вместе с потомками.
2. **`process.on('exit')` как последний рубеж** + защита `stopOnce` от двойного гашения.
3. **Ворота громкости:** перед запуском сервера синхронизации стенд ЖДЁТ, пока эмулятор
   действительно начнёт слушать (30 с), и при отказе **падает с кодом 1 и инструкцией**, вместо
   того чтобы поднять сервер, который будет бесконечно капать `ECONNREFUSED` в лог.

**Доказательство — три наблюдения:**

| Проверка | До фикса | После фикса |
|---|---|---|
| запуск без эмулятора | сервер стартовал и бесконечно капал `ECONNREFUSED` в лог, наверх — ничего | **выход 1 за 30 с** с текстом причины; сервер вообще не стартует |
| остановка стенда (упал `vite`) | сирота `sync-server/index.mjs` оставалась жить | сервер синхронизации **1 → 0**, эмуляторы гасятся штатно |
| **перезапуск `npm run stand`** (сам симптом) | эмулятор не поднимался, портов 0 | **2 порта из 2** |

### ⚠️ Чего фикс НЕ покрывает (названо честно, а не умолчано)

Если **сам `stand.mjs` убит принудительно** (`Stop-Process -Force` / `TerminateProcess`, как это
делает автоматика, включая мою), обработчики выхода не исполняются в принципе — и сирота остаётся.
Проверено: после такого убийства сирот оказалось 1. Это предел ОС, а не недоделка.

Именно поэтому третья правка (ворота громкости) не менее важна первой: **остаточный случай теперь
диагностирует себя сам** — следующий запуск падает за 30 с и печатает готовую команду поиска
сироты, вместо того чтобы молча съесть двадцать минут.

## Симптом

После остановки стенда повторный `npm run stand` **не поднимает эмуляторы**, при этом:

- порт **8181 никем не слушается**, `/dims` и любой экран под логином недоступны;
- **никакой ошибки наверх не выходит** — команда выглядит работающей;
- в `stand.log` бесконечно капает от сервера синхронизации:

```
[sync] предыдущий цикл ещё идёт — тик пропущен
[sync] ошибка цикла: 14 UNAVAILABLE: No connection established.
       Last error: Error: connect ECONNREFUSED 127.0.0.1:8181
```

То есть **сервер синхронизации от ПРОШЛОГО запуска жив**, крутит цикл каждые 15 с и стучится в
несуществующий эмулятор, а новый стенд поднять эмулятор уже не может.

Цена: три потерянных попытки и ~20 минут за сессию, каждый раз с диагностикой с нуля.

## Воспроизведение

1. `npm run stand`, дождаться подъёма.
2. Погасить стенд (закрыть окно / убить процесс обёртки).
3. `npm run stand` ещё раз → эмулятор не поднимается, лог капает `ECONNREFUSED 8181`.

## Криминалистика

Сирота — **`node  sync-server/index.mjs`**. Он переживает остановку обёртки, потому что стенд
запускает его отдельным процессом (`tools/stand.mjs` → «сервер синхронизации СЛУЖБОЙ»).

⚠️ **Ловушка при уборке, которая стоила мне двух неудачных заходов:**

1. У сироты **командная строка не содержит пути проекта** — она буквально
   `node  sync-server/index.mjs`. Фильтр `CommandLine -like "*ai_sandbox\ndim*"` его **не находит**
   и честно печатает «найдено сирот: 0», хотя сирота жив.
2. Фильтр по подстроке `*sync-server/index.mjs*` находит **собственный PowerShell**: искомая строка
   лежит в командной строке самой команды поиска. Попытка убить «сироту» убивает свою же оболочку.
   Безопасная форма — фильтровать по имени процесса И только затем по строке:
   `Get-CimInstance Win32_Process -Filter "Name='node.exe'" | Where-Object { $_.CommandLine -match 'sync-server' }`.

Косвенный признак, что сироты живы: **`stand.log` не удаляется** (`Remove-Item` молча не срабатывает —
файл держит процесс). Это самая дешёвая проверка «чисто ли».

## Гипотезы фикса (по возрастанию сложности)

1. **Стенд убивает своих детей при выходе.** В `tools/stand.mjs` повесить обработчик выхода
   (`process.on('exit' | 'SIGINT' | 'SIGTERM')`), который гасит порождённые процессы по дереву.
   Простейшее и, вероятно, достаточное.
2. **Стенд начинает с уборки.** Перед подъёмом проверять порты 8181/9099/9199/5173 и живые
   `sync-server/index.mjs`; нашёл — гасить и говорить об этом вслух.
3. **Стенд падает громко.** Если эмулятор не занял 8181 за N секунд — выходить с ненулевым кодом и
   внятным сообщением, а не оставлять сервер синхронизации капать в лог. Это лечит не причину, а
   немоту, но немота здесь и есть половина цены (ср. EXP-0067: «гейт, краснеющий не по своей теме,
   опаснее отсутствующего» — а тут гейт молчит вовсе).

Рекомендация: 1 + 3 (причина + громкость), 2 как страховка. **Сделаны 1 и 3** — см. секцию фикса
выше; 2 (уборка перед подъёмом) не понадобилась: ворота громкости дают тот же эффект, но не
трогают чужие процессы, а это на машине владельца существенно (EXP-0081).

## Решения, принятые без владельца

- **Гипотеза 2 (стенд сам убивает чужие процессы перед подъёмом) отвергнута.** Соблазнительно и
  опасно: на этой машине живут процессы других сессий, и стенд не вправе их ронять. Ворота
  громкости решают ту же задачу, оставляя решение человеку.
- **Таймаут ворот — 30 с.** Достаточно для холодного подъёма эмулятора на этой машине (наблюдал
  ~45 с для всего стенда, но эмулятор поднимается раньше сида и `stand.mjs`), и достаточно мало,
  чтобы отказ не выглядел зависанием.
- **`taskkill` вместо `tree-kill`-зависимости** — новых пакетов не заводим ради одной команды.
