## Симптом

`node tools/review.mjs queue <новый документ>` ответил «всего накоплено: 10», хотя ждущих владельца
интервью на тот момент был ОДИН. В `interviews/decisions/queue.json` лежали девять документов,
отвеченных владельцем 4–5 сентября: №060, 061, 068, 070, 071, 072, 074, 076, 077.

Подними я пачку не глядя — владелец открыл бы страницу «Накопилось: 11», где девять вопросов он уже
закрыл своей рукой. Для человека, который дважды за час ругался на сломанный контур вычитки, это
выглядело бы третьей поломкой подряд.

## Причина

Очередь — простой список в `interviews/decisions/queue.json`. `queue` в него ДОПИСЫВАЕТ
(`tools/review.mjs:1300`), а вынимает из него только успешный проход пачки. Ответ, данный ЛЮБЫМ
другим путём — страницей одного документа, правкой файла руками, ответом в чате с последующим
разносом — очередь не трогает вовсе. Признак «отвечено» у проекта есть и надёжен (его читает
`npm run questions`), но очередь его не спрашивает.

## Обход, применённый сейчас

Девять записей вычищены руками, в очереди осталось два настоящих вопроса; страница поднята и
отвечает 200. **Это обход, а не починка:** следующий агент наступит на то же.

## Лечение (не начато)

Одна строка смысла: **пачка обязана спрашивать признак «отвечено» перед показом**, а не доверять
списку. То есть `batch` фильтрует очередь тем же способом, каким `npm run questions` считает
ждущих, и заодно вычищает отвеченные из файла — тогда список перестаёт быть второй правдой рядом с
самими документами (канон: «пару лучше УБРАТЬ, чем сторожить»).

## Приёмка

1. Мутация: положить в очередь отвеченный документ → `batch` его не показывает и убирает из файла.
2. Мутация: положить неотвеченный → показывает.
3. Живой прогон `node --test tools/review-batch.test.mjs` остаётся зелёным.

## ✅ СТАТУС: DONE (2026-09-12 ≈10:45 +03:00)

Закрыт в серии починок красных багов 2026-09-12 (`qa/reports/2026-09-12_red-bugs-series.md` §6).

**INTENT:** код (`cmdQueue`) дописывал в `queue.json` и печатал длину списка; `cmdBatch` фильтровал
отвеченные только в показе, файл не трогал; документ ожидал «пачка обязана спрашивать признак
„отвечено“ перед показом… и заодно вычищает отвеченные из файла»; расхождение = дефект.

**Лечение:** чистая `pruneQueue(items, isWaiting)` в `tools/lib/review-core.mjs`; в `tools/review.mjs`
общий `readQueuePruned()` — читает очередь, отбрасывает отвеченные и исчезнувшие ТЕМ ЖЕ признаком,
что `npm run questions` (`parseInterview().waiting`), и ПИШЕТ отфильтрованное обратно; `queue`
отвеченный документ в очередь не кладёт и печатает честное число; `batch` работает по очищенному.

**Доказательства 2026-09-12** — новый юнит `tools/review-queue-prune.test.mjs` (в `test:tools` и
воротах): чистая функция · отвеченный в очереди → `batch` печатает «Очередь пуста», файл `items: []`
· `queue` отвеченного не кладёт («всего накоплено: 0»), ждущего кладёт («1»). Приёмка 2 — живой
тест пачки `review-batch.test.mjs` 1/1 (ждущие показываются). Регрессии: `review-core.test` 3/3,
`review.mjs --selftest` чист. **К4 — мутация** (`pruneQueue(...)` → «всё живое», резервная копия):
2 из 3 красные адресно; возврат 3/3.

**Решения, принятые без владельца:** (1) `queue` не кладёт отвеченный документ вовсе — иначе
число «накоплено» соврало бы в ту же секунду. (2) У живого прогона CLI в тесте стоит таймаут 15 с:
на мутанте отвеченный остаётся «живым», `batch` поднимает настоящий сервер и ждёт владельца —
первая редакция теста ВИСЛА вместо красного (замер: прогон ушёл за 120 с, снят вручную вместе с
сиротой сервера пачки). Проверка, не умеющая покраснеть, ничего не доказывает.
