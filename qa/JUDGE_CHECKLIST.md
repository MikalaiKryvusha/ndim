## A. ДО ПРЕДМЕТА — стенд

**A0. Стенд проверяется ПРИБОРОМ, а не рукой, и до первой команды по предмету.**

```bash
node tools/verify-judge-stand.mjs <путь к дереву суда>
```

Четыре вопроса, каждый оплачен живым ложным ответом: зависимости поимённо по `package.json` ·
история не синтетическая · дерево чисто · **оговорка отставания** (сколько коммитов не видно
дереву и какие приборы ворот спрашивают git). Разбор цены каждого — в шапке прибора.
🔴 Цена самого шага: суд №27 начался с **7 красных при честных 3**, потому что во временном
дереве не было `node_modules`. Цена четвёртого вопроса: суд №30, красный стража «неначатых» —
**один шаг от объявления пожара `main`**, которая была чиста.

**7. Базовая линия снимается В ДЕРЕВЕ, СТОЯЩЕМ НА ТОМ, ЧТО ПОДПИСАНО.** Перед строкой «базовая
линия на X» — `git rev-parse HEAD` и сверка с X. Своя ветка ≠ `main`.

**A1. Числа сравниваются ОТ БАЗЫ СЛИЯНИЯ, а не с сегодняшней `main`.**

```bash
git diff --stat $(git merge-base main <голова>) <голова>     # НАСТОЯЩАЯ нагрузка
```

🔴 Оплачено судом №30: плоский `git diff main <ветка>` показал три общих файла с чужой веткой, и
я объявила заявление автора опровергнутым. Замер от базы дал ПУСТОТУ — заявление было верно,
неверен был мой способ. Отставание ветки в плоском диффе выглядит её работой.

**A2. 🆕 ОТВЕТ ПРИБОРА СТЕНДА ПРОТУХАЕТ. Переспроси, прежде чем звать красный находкой.**

`verify-judge-stand.mjs` задаёт вопрос об отставании ОДИН РАЗ — в начале суда. Дерево, не
отстававшее в ту минуту, отстаёт через двадцать: ствол движется под судом, а пять воротных
приборов спрашивают **живой общий ref `main`**, беря файлы из своего дерева.

```bash
node tools/verify-judge-stand.mjs .                  # переспросить ПЕРЕД разбором красного
git merge-base --is-ancestor <виновный коммит> HEAD   # он вообще в моём дереве?
```

🔴 **Оплачено сменой 14, и цена была бы огромной.** Страж «неначатых» дал красный на `bugs/219`
с виновным коммитом **из СТВОЛА** — это выглядело красным `main`, то есть пожаром, и вдобавок
обвинением автора судимой порции. Оба ложны: чистое дерево на стволе дало **13/13**, а виновного
коммита в дереве суда не было вовсе. Прибор печатал причину сам — строкой «спрошено по ссылкам:
HEAD, **main**», — и я прочитал её мимо.
🔑 **Класс: «стенд годен» — это утверждение о ПАРЕ (дерево ↔ `main`), и оно переживает свою
правду молча.** У числа против названной базы срок годности виден; у слова «годен» — нет.
📌 Постановка Менеджеру: прибор обязан ПЕЧАТАТЬ sha `main`, против которого вынес «годен».
До её исполнения переспрашивать — обязанность судьи, а не любезность.

### 🔴 A2а. КРАСНОЕ НА НЕСВЕЖЕМ НЕОТЛИЧИМО ОТ НАХОДКИ — общая форма, шире одного прибора

Смена 14 дала **три ложных красных за один час у трёх разных людей**, и носители несвежести были
РАЗНЫЕ, а класс один:

| у кого | что было несвежим | что печаталось |
|---|---|---|
| судья | **живой ref `main`** ушёл под судом | «документ объявлен неначатым» с коммитом ИЗ СТВОЛА |
| Менеджер | **сборка** `build/` от позавчера | «`book.html`: оценённых 9 из 60, а заголовок зовёт топом» — 4 провала |
| Дизайнер | **отставшая ветка** | тот же `bugs/219` |

🔑 **Злая половина класса, названная Менеджером точнее меня: красное на несвежем печатает
ПРЕДМЕТНЫЕ, УБЕДИТЕЛЬНЫЕ строки.** Оно выглядит не поломкой прибора, а находкой — с именем файла,
числом и цитатой. **Отличить его от настоящего по ТЕКСТУ нельзя в принципе; отличается оно только
по времени файла или по sha.**

**Правило: прежде чем звать красный находкой, спроси у него не „что", а „ОТКУДА".**
```bash
git rev-parse --short main ; git rev-parse --short HEAD   # ref и дерево — одна ли пара
ls -l build/ | head -3                                    # сборка от какого часа
git merge-base --is-ancestor <виновный> HEAD              # он вообще здесь?
```
⚠️ И обратная сторона, которую нельзя терять: **это НЕ повод не доверять красному.** Три из трёх
оказались ложными в тот час — но правило A2 стоит ровно затем, чтобы четвёртый, настоящий, не был
объявлен «опять несвежесть». Проверяется происхождение, а не отменяется тревога.

## B. ПРЕДМЕТ — что судится и чем

1. **Заявление исполнителя — не доказательство.** Каждое число из отчёта перепрогоняется своими
   руками; расхождение объясняется, а не сглаживается.
2. **Проверка, которая никогда не падала, ничего не доказывает** (`TESTING_FRAMEWORK.md`, ворота 5).
   На чужие мутации смотрю, свою — ставлю сам, **назвав адресатов ДО прогона**.
3. **Вакуумность ловится числом наблюдений.** «0 нарушений» и «0 наблюдений» печатаются одинаково —
   требую, чтобы страж печатал, СКОЛЬКО раз он видел то, что стережёт.
4. **Молчаливый пропуск — дефект прибора, а не отсутствие работы.**
5. **Чужую ветку не правлю.** Прогон чужого кода — своим временным деревом, оно удаляется после.

**B1. 🔴 ПРЕЖДЕ ЧЕМ НАЗВАТЬ СРАБАТЫВАНИЕ НАХОДКОЙ — НАПЕЧАТАЙ ЕГО ЦЕЛИКОМ.**
Не число, не счётчик — саму строку, на которой прибор сработал.
🔴 Оплачено смены 11 **четырежды за один заход**, и каждый раз спасал не прибор, а чтение строки:
грубый разделитель затянул в «тексты владельца» комментарий кода · документ, ЦИТИРУЮЩИЙ
запрещённые обороты, дал классу 14 срабатываний · сложение двух строк шапки дало ложное
расхождение · `join` рассыпался на разделителях и выдал декартово произведение за находку.

**B2. Строка АДРЕСА и КОНТУРА — часть улики; вердикт цитирует её, а не только числа.**
Третий род ложного зелёного (находка Дизайнера, смена 11): **проверка исполнилась, признак верен,
а ПРЕДМЕТ ДРУГОЙ** — прибор молча ушёл на чужой слот и вернул правдоподобные числа с чужого
дерева. По отчёту и коду выхода это неотличимо; отличимо только по строке адреса, которая
печаталась и была верна — а глаз шёл мимо неё.

**B3. Строки́ мало — проверь ПОРЯДОК.** Утверждение «правка есть перемещение» счётом строк НЕ
доказывается: для двери выката ломается порядок, а не состав.

```bash
# старая последовательность обязана быть ПОДПОСЛЕДОВАТЕЛЬНОСТЬЮ новой
```
🔴 Оплачено судом №28: авторское доказательство и моё первое считали строки; порядок не проверял
никто. Переставь замок стейджа за сборку — все строки на месте, дверь катастрофична.

**B4. Ошибка не должна читаться как ответ.** У всякого `catch`, глушащего прогон, спроси: какие
коды он смешивает? `git grep` даёт **1** на «не найдено» и **128** на «ветка не разрешилась» —
общий `catch` превращает отказ инструмента в ответ «нигде» (суд №30, `where-cured`).

**B5. Мутируя прибор, который что-то делает С МИРОМ, обезвреживай его В ИСХОДНИКЕ мутанта.**
Правило и его разбор — `TESTING_FRAMEWORK.md`, правило 9 (`EXP-0244`). Здесь только адрес: дублировать
не буду, пара разъедется.

**9. Мутируя АРТЕФАКТ, сперва спроси, какой каталог реально отдаёт сервер.** `vite preview` в
SvelteKit отдаёт `.svelte-kit/output/client/` и `static/`, а НЕ `build/`. Зелёный после правки
`build/` означает «мутации не было», а не «код здоров».

**B6. Отвод объявляется ДО предмета, и компенсируется работой, а не оговоркой.**
Судишь лечение СВОЕЙ находки или форму, которую сам предложил, — скажи это первой строкой и
компенсируй: заглавный замер автора воспроизведи СВОИМ счётом, признаки мутируй ПОРОЗНЬ.
Образец — вердикты №20 и №32.

**B7. 🆕 МУТАЦИЯ И ЗАМЕР — В РАЗНЫХ ПРОЦЕССАХ. Признак негодного опыта — СТАБИЛЬНОСТЬ чисел.**
Правишь файл и тут же меришь тем же процессом — вложенный импорт берётся из кеша модулей, и
мутант не наблюдается. Сбрасывать кеш меткой `?t=` бесполезно: она бьёт только внешний модуль.
```bash
node _замер.mjs        # каждый замер — ОТДЕЛЬНЫЙ дочерний процесс (execFileSync)
```
🔴 Оплачено сменой 14: таблица десяти мутаций различителей Н9 дала **все десять чисел
одинаковыми до сотой**. Прочитать это можно было как «признак устойчив» — а означало оно, что
вопроса не задавали. **Тот же признак, что и в `EXP-0269`: стабильность как примета слепоты.**
🔑 Правило-близнец из `lib/mutate.mjs`, и оно сильнее моего: **два РАЗНЫХ мутанта, давшие
результат, совпавший до строчки, — это не совпадение, это непроведённая подстановка.**

**B8. 🆕 РАСХОЖДЕНИЕ С ЭТАЛОНОМ — СНАЧАЛА ПРОВЕРЬ СВОЁ ОЖИДАНИЕ, ПОТОМ ПРОДУКТ.**
Сверяя реализацию с принятым текстом, судья строит ожидание САМ — и оно бывает неверным чаще, чем
продукт. Прежде чем звать расхождение дефектом: воспроизводит ли моё ожидание ВСЕ правила
эталона, включая те, что срабатывают не всегда?
🔴 Оплачено судом №40: сверка §3 дала два «расхождения» на `movie/1`. Я сравнивал с шаблоном на
два имени страницу, где законно отступила **лестница отката §5**. Реализация была права, неверна
была моя проверка. Лечение — сверять только там, где эталонное правило применимо, и печатать,
СКОЛЬКО случаев отсеяно как неприменимые (91 сверено + 87 отсеяно = 178, сумма сходится).

**B9. 🆕 РАЗОШЛОСЬ С ОЖИДАНИЕМ — ПЕЧАТАЙ ВЫВОД ЦЕЛИКОМ.**
Не «не режь вывод» — это правило все знают и всё равно режут. Рабочая форма узкая и исполнимая:
**обрезанный вывод годится, пока он подтверждает ожидаемое; в ту секунду, когда что-то не сошлось,
первым делом печатается вывод БЕЗ обрезки.**
🔴 Оплачено судом №40: я снял предмет заявки командой с `tail -14`, получил список без
`EXPERIENCE.md` и через минуту едва не объявил «конфликт по файлу, которого автор не трогает».
Спасло не правило «не режь», а недоверие к расхождению.
🔑 Родня по классу и по дню — подъём смены 12: Менеджер обрезал `tail` дельту канона и объявил её
полной; `AGENT_GUIDE.md` стоял в голове списка и не доехал до роли.

## C. ПОКРЫТИЕ И ГОЛОВА

**C1. В шапке вердикта — ДВА числа: коммитов в предмете суда и коммитов, которые понесёт мерж.**

```bash
git rev-list --no-merges --count <голова> ^main      # каноническая команда манифеста
git merge-base --is-ancestor <названная база> <голова>
```

**C2. 🔴 Голова, названная заявкой, ≠ голова ветки. Мержится ИМЕННО судимая.**
Мерж головы тянет ВСЕХ предков, включая неотсуженное.
🔴 Смена 11 дала этот класс дважды за день: у dev-1 поверх судимой лёг один коммит (досудила
сразу), у Интегратора — два. Проверка одной командой:

```bash
git rev-list --count <судимая голова>..<ветка>       # 0 — покрытие полное
```

**C3. Число без коммита — слух** (`EXP-0226`). Всякое число в условии вердикта едет вместе с
головой, на которой снято: «13/13 на `f683f48` + `main` `fca35f4`».

**C4. Опасности мержа проверяются СИМУЛЯЦИЕЙ, а не чтением сообщения коммита.**

```bash
git merge-tree --write-tree main <ветка>             # настоящий мерж, дерево не трогается
```
🔴 Суд №27: мерж-коммит заявлял «три опасности сняты». Две сняты — но симуляция нашла
ЧЕТВЁРТУЮ, дороже трёх: починка и единственный юнит, который покраснел бы при её потере,
лежали ВНУТРИ одного конфликта.

## D. ПОСЛЕ СУДА

**8. Уборка суда ПРОВЕРЯЕТСЯ, а не заявляется.** Перед строкой «окружение после суда» —
`git worktree list` (обязаны остаться только настоящие рабочие места), `git status`, порты слота.
🔴 Оплачено судом №2: он заявил «worktree суда удалён», а тот стоял в списке ещё два суда.

**D1. Мутации откатываются, и откат ПОДТВЕРЖДАЕТСЯ ПРОГОНОМ** — тем же числом, что было до
мутации, названным в вердикте.

**D2. Что НЕ покрыто — называется прямо, отдельным разделом.** Не «судилось всё», а поимённо:
какой файл читался по шапке, а не построчно; какой прогон не ставился и почему; чей контур не мой.

**D3. Норма перечитывается перед ВЫНЕСЕНИЕМ, а не перед началом** (`EXP-0242`): канон движется
под сессией. Голова `main` в шапке вердикта снимается в момент вынесения.

## E. ЧТО СУДЬЯ НЕ ДЕЛАЕТ

- **Не смягчает вердикт** — независимость и есть суть роли (манифест). Изменение объёма — через Менеджера.
- **Не правит чужую ветку и чужие файлы.**
- **Не читает боевую базу** ради оценки вероятности: чужой контур, чужие права.
- **Не молчит о блокере** (манифест, правило 5) и **не объявляет пожар, не перемерив** (шаг A0).
