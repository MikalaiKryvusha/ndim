## Зачем это нужно — одной строкой

Сайт статический: оценки и рейтинги вмораживаются в HTML **на сборке**. Пока никто не пересобирает,
роботы месяцами видят числа дня последнего выката — а `npm run deploy` **вообще не обновляет снимок
каталога** (`fetch-dims-slice` в двери нет, `dims-build.json` вне git). То есть сегодня свежие данные
не доезжают до поиска ВООБЩЕ, даже при ручном выкате.

## Вектор цели

Раз в сутки, внутри дневного цикла полной синхронизации и **после** её расчётов, сайт
пересобирается со свежим снимком каталога и публикуется — **если изменилось хоть что-то**. Хранится
10 версий. Настоящая дверь выката (`npm run deploy`) при этом не ослабляется ни на шаг.

## 🔴 Узел, ради которого этот план вообще нужен

Автомат **не может** пройти три шага боевой двери: ворота Smoke требуют живого стенда, смоук под
сессией требует человека с логином, замок стейджа требует нового коммита. Коммит же при
автопересборке НЕ меняется — меняются только ДАННЫЕ.

🔑 **Различение, на котором стоит весь план:** обычный выкат везёт **новый КОД**, автопересборка
везёт **те же самые исходники с новым снимком данных**. Это разные риски. Мерить их одной дверью —
значит либо остановить автоматизацию совсем, либо ослабить дверь для настоящего кода.

**Отсюда форма ответа: ВТОРАЯ, УЗКАЯ дверь, которая физически не умеет везти код.**

## Критерии приёмки

- [ ] **К1. Дверь данных отказывает при любом изменении кода.** Если хоть один файл `src/`,
      `static/`, конфигов сборки или `package-lock.json` отличается от коммита, на который выписана
      расписка боевой двери, — дверь данных останавливается ненулевым кодом. Доказано мутацией:
      правка одного байта в `src/` роняет дверь.
- [ ] **К2. Публикуется только `hosting`.** Правила Firestore, индексы и функции дверь данных не
      катает НИКОГДА — у неё нет для этого ни повода, ни проверок.
- [ ] **К3. Пустых выкатов нет.** Дрейф 0 → выката нет (`tools/measure-catalog-drift.mjs`,
      `REBUILD_THRESHOLD = 0`). Доказано: прогон на двух одинаковых снимках не публикует ничего.
- [ ] **К4. Не чаще раза в сутки.** Второй запуск в те же сутки отказывает, даже если дрейф есть.
- [ ] **К5. Целостность сборки проверена** — во всей сборке один `__sveltekit_<хеш>` (`bugs/124`).
- [ ] **К6. Читающие стражи прогнаны по СОБРАННОМУ сайту** до публикации: `verify-dimension-pages`,
      `verify-catalog-hubs`, `verify-test-pages`. Им не нужен ни стенд, ни сессия.
- [ ] **К7. После публикации прогнаны читающие боевые пробы:** `verify-prod-dimension-pages`,
      `verify-prod-lang-redirects`, `verify-prod-cache`. Красная проба — громкий отчёт, а не тишина.
- [ ] **К8. Версий в хостинге не больше 10** — уборка выполняется той же дверью.
- [ ] **К9. Расчёт связей не страдает.** Сборка идёт ПОСЛЕ расчётов; её падение не роняет
      синхронизацию и не откладывает следующий цикл.
- [ ] **К10. Документ боевого запуска обновлён** (`plans/04_cutover.md`): как именно публикуется
      сайт теперь, каким ключом и с какой машины.

## Границы — чего этот план НЕ делает

- ⛔ **Не ослабляет `npm run deploy`.** Ни один его шаг не снимается и не смягчается.
- ⛔ **Не катает код.** Никогда, ни при каких флагах. Изменился код — работает человек и обычная дверь.
- ⛔ **Не трогает правила Firestore и индексы.**
- ⛔ **Не заменяет смоук под сессией.** Он остаётся обязательным для выката кода.

## Шаги

### Шаг 1 — Прибор различения: «изменился ли КОД»

- [ ] `tools/verify-code-unchanged.mjs`: сравнивает рабочее дерево с коммитом расписки
      (`.kaif/stage-receipt.json`) по путям, влияющим на сборку. Список путей — ЯВНЫЙ и записан
      в самом приборе с объяснением, почему каждый попал.
- [ ] 🔴 Снимок каталога (`src/lib/content/dims-build.json`) из сравнения ИСКЛЮЧАЕТСЯ поимённо и с
      причиной: он и есть то, ради чего дверь существует. Исключение объявляется одной строкой,
      как `ИМЯ-ОК` у стража бренд-имени.
- [ ] **Проверка:** мутация — правка одного байта в `src/app.html` роняет прибор; правка снимка
      каталога его НЕ роняет.

### Шаг 2 — Дверь данных `tools/deploy-data.mjs`

- [ ] Порядок шагов, и каждый останавливает дверь ненулевым кодом:
      1. код не менялся (шаг 1) · 2. свежий снимок каталога (`fetch-dims-slice --all`, проверить
      строку «источник: полный каталог») · 3. дрейф > 0 · 4. не чаще раза в сутки (отметка на диске)
      · 5. ЧИСТАЯ сборка · 6. целостность `__sveltekit` · 7. читающие стражи по сборке · 8.
      публикация `--only hosting` · 9. читающие боевые пробы · 10. уборка версий до 10.
- [ ] `--dry-run` по умолчанию — как у писаря описаний: публикует только явный `--apply`.
- [ ] `--selftest` без сети: проверяет порядок шагов и то, что каждый умеет остановить дверь.
- [ ] ⚠️ Хук `deploy-guard` обязан пропускать эту дверь ЯВНО по имени — и продолжать блокировать
      голый `firebase deploy`. Правка хука входит в шаг.

### Шаг 3 — Расписание на серверном ПК

- [ ] Задача по расписанию рядом с сервером синхронизации (**не внутри контейнера** — у него своё
      дерево зависимостей, и смешение уже стоило проекту разбора; решение владельца «сервер сам»
      исполняется по МЕСТУ: та же машина, тот же цикл).
      🔴 **Это единственное отступление от буквы заказа, и оно названо вслух** — если владелец
      настаивает на исполнении ВНУТРИ контейнера, шаг переписывается, а риск (падение сборки
      останавливает расчёт связей) принимается им осознанно.
- [ ] Запуск — по сигналу окончания расчётов, а не по часам: сервер синхронизации пишет отметку
      «полный проход завершён», задача её ждёт.
- [ ] **Проверка:** сутки живого наблюдения — в логе видно «расчёт закончен → дверь данных → выкат
      либо отказ по дрейфу».

### Шаг 4 — Наблюдаемость

- [ ] Отчёт одной строкой в лог на каждый прогон: дрейф в процентах и штуках, решение (выкат/отказ),
      номер версии, время.
- [ ] Красный прогон обязан быть ЗАМЕТЕН: молчащая автоматика хуже отсутствующей.
- [ ] **Проверка:** прогон с намеренно красным стражем оставляет в логе явный отказ и не публикует.

### Шаг 5 — Сдача

- [ ] `/fable-judge` по утверждениям плана.
- [ ] Строки в `STATUS.md` и `AGENT_GUIDE.md` → «ВЫКАТ В БОЙ» (две двери, и чем они различаются).
- [ ] `plans/04_cutover.md` — как публикуется сайт теперь.
- [ ] Тег `DONE` в имени этого файла.

## Риски

1. **Ключ выката на серверном ПК.** Дверь данных публикует, значит на машине лежит доступ. Ключ —
   только в `.env` (канон 2026-08-15), и это должен быть отдельный узкий доступ, а не боевой ключ
   на все руки.
2. **Тихая деградация.** Автомат, который публикует каждый день, может месяцами возить сломанное,
   если читающие пробы недостаточны. Отсюда К7 и шаг 4.
3. **Диск.** 334 МБ на артефакт плюс 10 версий в хостинге. Уборка обязательна (К8), иначе 10 ГБ
   кончатся примерно за три месяца (`researches/39`).
4. **Ложное чувство свежести.** Дверь возит ДАННЫЕ; она не заменяет выкат кода и не чинит того,
   что сломано в коде. Это записано в границах.
