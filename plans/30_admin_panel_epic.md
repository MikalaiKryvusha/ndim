## Что этот эпик делает (одной строкой)

Возвращает владельцу возможность **пополнять каталог измерений** — руками через собственную
админ-панель и пачками через ИИ-агентов, чьи находки он вычитывает и одобряет, — и делает это,
не нарушив канон экономии запросов.

## Что этот эпик НЕ делает (границы)

- **Не открывает админу оценки людей.** `points/**` остаётся закрытым для всех (`bugs/100`,
  интервью №002 В4). Никакая «удобная панель» этого не отменяет.
- **Не выносит на витрину, кто наполняет каталог.** Знание «каталог ведёт владелец» — для нас
  (поправка Р11 словаря продукта). Продукт говорит только: человек **предлагает** измерение.
- **Не строит модерацию соцслоя** (`ideas/12`) и не поглощает `ideas/13` целиком: эпик строит
  ДОМ панели и первую комнату, остальные комнаты въезжают позже в тот же каркас.
- **Не трогает ленту и порядок выдачи измерений** — это соседний эпик `ideas/28`. Общая у них
  только одна точка: функция `ensureDimsIndex`, и фаза 1 чинит её для обоих.

## Порядок фаз и почему он такой

🔴 **Порядок работ НЕ совпадает с порядком частей в заказе владельца, и это осознанно.**
Владелец назвал переработку индекса (часть E) пятой, а она — техническое предусловие всего
остального: пока пересборка индекса стоит 5111 чтений и стирает поля, любой код, создающий
измерения, строится на песке (`researches/29` §2.4, §4.1).

Второе смещение: **форма создания измерений — не фича, а возврат утраченного.** В 1.x она была,
в 2.0 её нет вовсе (`researches/29` §2.1, находка 1) — то есть владелец сегодня не может завести
измерение иначе как правкой документа в консоли Firebase. Поэтому ручной CRUD идёт **раньше**
агентской машинерии: он снимает регресс и даёт пользу на следующий день после выката.

```
ФАЗА 1 ─── ФАЗА 3 ─── ФАЗА 4 ─── ФАЗА 5 ─── ФАЗА 6 ─── ФАЗА 7
(индекс)   (дом)     (измерения) (глаза)   (очередь)  (запуск)
   │          ▲          ▲
   │          │          │
ФАЗА 2 ───────┴──────────┘
(решения владельца + макеты — идёт ПАРАЛЛЕЛЬНО фазе 1)
```

## Фаза 1 — Экономный индекс каталога 🔵 РАЗБЛОКИРОВАНА, начинать с неё

**Закрывает часть E заказа** + подбирает по дороге открытый `bugs/106`.
**Решений владельца не требует. Кода в клиенте нет.**

- Обезвредить **мину `title`** (`researches/29` §2.3): документ без `title` сегодня выпадает из
  индекса И одновременно ломает сторож свежести, включая вечную пересборку — 5111 чтений на
  каждом рабочем цикле при бесплатной суточной квоте 50 000.
- **Инкрементальное обновление**: кто создал измерение — тот дописал одну запись в индекс.
  Одно чтение + одна запись вместо 5111 чтений.
- **Полная пересборка становится аварийным путём** и обязана СОХРАНЯТЬ поля, которых не знает
  (требование `ideas/28`: иначе первая же пересборка сотрёт счётчики популярности).
- **`bugs/106`**: `space/stats.dims` = 5112 вместо 5111, диаметр 715 вместо канона 714,9. Фикс
  живёт в той же функции — чинить отдельно значит платить за выкат образа дважды.
- Проверить находку §2.6: ищет ли вычислитель новые измерения по полю, которого в бою нет.

**Ворота входа:** нет (фаза открыта).
**Ворота выхода:**
- страж «индекс обслуживается инкрементально» **красный на сегодняшнем коде**, зелёный на новом,
  доказан ≥2 мутациями;
- `npm test`, `npm run test:calc`, `npm run test:rules` — зелёные;
- пара «истина ↔ зеркало» `dims/{id}` ↔ `dims_list` ↔ `space/stats.dims` вписана в реестр
  `AGENT_GUIDE` с однострочной командой проверки;
- 🔧 **пересборка образа — рука владельца** (`npm run calc:image`), агент не выкатывает.

📄 Операционный план — **`plans/31_admin_epic_phase1_index_economy.md`**.

## Фаза 3 — Дом панели: доступ и каркас 🔲 ждёт фазу 2

**Закрывает часть A заказа.**

- Размещение по ответу В1: отдельный сайт Hosting в том же проекте (`researches/29` §3.1 — в
  документации Firebase этот случай описан дословно) либо группа маршрутов внутри приложения.
- **Дверь из клиентского приложения видит только обладатель claim** — с поправкой на то, что claim
  доезжает не мгновенно (новый вход / обновление токена / `getIdToken(true)`); экран не должен
  мигать дверью.
- Если панель живёт внутри приложения — её маршруты **не попадают ни в `sitemap.xml`, ни в
  индекс** (у нас всё пререндерится, `+layout.ts` → `prerender = true`).
- Правила Firestore: ничего нового не открывается; каждая новая коллекция приезжает **со своими
  тестами-отказами** (умолчание «запрещено» иначе поймает ошибку только в бою).

**Ворота выхода:** страж «не-админ не видит двери и получает отказ правилами» — красный на
мутации · `npm run test:rules` зелёный · QA-прогон живым Chrome (обе темы, две ширины).

## Фаза 5 — Глаза агента: каталог и список кандидатов 🔲 ждёт фазу 4

**Закрывает часть C заказа.**

- Инструмент, которым агент видит весь каталог: это **одно чтение** `dims_list` (566 КБ), а не
  выгрузка 5111 документов. Канон экономии соблюдается по построению.
- **Дедупликация числом, а не на глаз**: прежде чем предложить кандидата, агент обязан доказать,
  что такого измерения нет (нормализация названий — грязь настоящих данных 1.x описана в
  `feed.ts`: задвоенные кавычки, год внутри названия).
- Коллекция приоритетных кандидатов + правила + тесты-отказы.
- Источник популярности — по ответу В2. Рекомендация исследования: **Wikidata** (один реестр на
  все виды объектов культуры, число сайтлинков как принятая мера известности, CC0).
- 🔑 **У кандидата обязателен разрешимый идентификатор реестра.** Основание — цифры, а не вкус:
  ссылки, которые модель приводит по памяти, галлюцинируют в 14–95 % случаев; лучшие
  deep-research-агенты дают 65 % качества ссылок (`researches/29` §3.4).

**Ворота выхода:** N кандидатов, у **каждого** идентификатор разрешается механически ·
дублей с существующим каталогом — **ноль** на контрольной выборке · страж отвергает кандидата
без источника.

## Фаза 6 — Очередь вычитки: агент предлагает, владелец судит 🔲 ждёт фазу 5

**Закрывает часть D заказа — самая ценная и самая опасная часть эпика.**

- Явные статусы, каждый переход намеренный (`researches/29` §3.3 п. 1): черновик → на вычитке →
  одобрено / отклонено / возвращено с комментарием → снова на вычитке.
- Четыре действия владельца одной кнопкой каждое, как он и просил: **одобрить · отредактировать ·
  отклонить · вернуть с комментарием**.
- Комментарий крепится **к конкретному полю**, а не к карточке вообще (практика отрасли: «pins the
  comment to exactly that sentence»).
- 🔴 **Карточка обязана показывать, ЧТО проверить** — источник, спорное поле, похожие измерения из
  каталога. Иначе пачка правдоподобных карточек превращает владельца в штамп «Одобрить»; это
  названный отраслью главный риск таких очередей.
- Одобрение = создание измерения механизмом фазы 4 (второго пути записи в каталог не заводим).
- Рассмотреть переиспользование механики контура вычитки `plans/27` (страница → решение в один
  клик → запись → гейт) — **взаймы, не копией** (`EXP-0118`).

**Ворота выхода:** полный цикл прожит на стенде (кандидат → возврат с комментарием → доработка →
одобрение → измерение в каталоге) · **одно настоящее измерение**, найденное агентом и одобренное
владельцем, стоит в бою.

## Критерии приёмки эпика — наблюдаемые и счётные

1. Владелец заводит измерение **из панели**, ни разу не открыв консоль Firebase.
2. Добавление одного измерения стоит **≤ 3 операций Firestore** вместо 5111 чтений (замер до/после
   одним прибором).
3. Число измерений одинаково на «Пространстве» и «Измерениях»; диаметр Пространства = **714,9**
   при 5111 измерениях (канон 1.x, `bugs/106`).
4. **Не-админ** не видит двери в панель и получает отказ правилами — доказано мутацией.
5. **Ни один кандидат без разрешимого идентификатора источника** не доезжает до владельца —
   доказано стражем.
6. Прожит полный цикл «агент нашёл → владелец вернул с комментарием → агент доработал → владелец
   одобрил → измерение в бою» — хотя бы один раз на настоящих данных.
7. Занятость индекса `dims_list` печатается в приёмке числом (сегодня 54,0 % от 1 МиБ, потолок
   каталога ≈ 9 400 измерений).

## Трассировка и исполнение

- Каждый шаг операционного плана цитирует **строку-якорь этого метаплана**; шаг без якоря — дрейф
  охвата, пойманный до диффа (`AGENT_GUIDE` → шаг 7 чеклиста).
- Каждая фаза исполняется фейбл-циклом; закрывает фазу прогон `/fable-judge`, и **только после
  этого** пишется операционный план следующей.
- Отметки о закрытии фаз ставятся здесь же; на закрытии эпика заполняется секция «Решения,
  принятые без владельца».
