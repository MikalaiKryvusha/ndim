## Вектор цели (по `REQUIREMENTS_FRAMEWORK.md`)

- **Achieve:** у NDim появляется поверхность ТЕСТ — страница-инструмент со своим адресом, куда
  человек приходит по «тестовому» запросу, получает честный результат БЕЗ аккаунта и уносит его
  ссылкой. Это крупнейший измеренный спрос из всех достижимых: RU «тест личности» 219 453,
  «тест на характер» 95 445, «тест на совместимость» 62 467 (`researches/30` + §16
  `researches/34`); выдачу держит 16personalities — структурный аналог, а не конкурент по нише.
- **Maintain:** честность инструмента — результат из настоящей математики, а не Барнум
  (`researches/30` §7.4 — наше отличие); инварианты: числа похожести не публикуются нигде
  (№018 В4 + №023), шеринг результата — БЕЗ чисел; никаких обещаний трафика раньше зимы
  2026/27; язык человека, не продукта (урок C.1).
- **Avoid:** дублировать интерактив лендинга (граница с `plans/21` зафиксирована метапланом:
  тот остаётся на месте, тест — самостоятельная поверхность) · решать механику и форму за
  владельца (это видение: интервью + 4 макета) · эссе-кластеры вокруг теста (§7.1: AI
  Overviews съедают их первыми — выживает ИНСТРУМЕНТ).

#### Такт В — модель данных пары и решения (2026-08-14, сильная модель; решения ДО кода)

**Модель: ОДИН документ `testPairs/{pairId}`** — `{ slug, created, aUid, aAnswers, bUid|null,
bAnswers|null }`, где `aAnswers`/`bAnswers` — map `dimId → 0…10`.

1. **Почему map, а не «документ на ось» (как в `points`).** Точке человека документ-на-ось
   нужен, потому что правила не умеют перебирать значения map и валидируют каждую оценку
   отдельно. Для пары перебор НЕ нужен: правила умеют `map.values().hasOnly([0…10])` и
   `map.size() <= 40` — валидация целиком без итерации (приём уже живёт в правиле воронки:
   `values()[0] == 1`). Один документ = 1 чтение результата вместо 2×N — канон экономии.
2. **Приватность (№002 В4) — согласие явным действием.** В документ пары попадают ТОЛЬКО
   оценки из НАБОРА обёртки (пересечение своих оценок с очередью, фильтрует клиент при
   нажатии), и кладутся они кнопкой («Создать ссылку» / «Сравнить») рядом с панелью, которая
   показывает ровно эти строки. Оценки вне набора не покидают `points` никогда.
3. **Непубличность ссылки (№028).** `pairId` — случайный длинный id; читать пару может
   только вошедший (гость — вошедший) по прямому `get`; **`list` запрещён** — перечислить
   пары нельзя никому. Ссылка — `/{lang}/test/{slug}?pair={id}`: пререндер и canonical
   остаются на чистом адресе (вариант с query поиск не индексирует), при `?pair` гидратация
   добавляет `noindex`. Отдельного маршрута нет — статический хостинг не пререндерит
   неизвестные id, а страница обёртки и так несёт движок.
4. **Правила:** create — только собой (`aUid == auth.uid`, `bUid == bAnswers == null`,
   валидный slug, ответы валидны); update — ТОЛЬКО присоединение второго (`bUid == null` →
   `auth.uid`, не сам с собой, a-поля и slug/created неизменны); delete — любой из
   участников (право забрать свои ответы); read — `get` вошедшим, `list` никому.
   Известная цена: до присоединения второго ответы создателя технически читаемы любым
   вошедшим, у кого есть ссылка, — это и есть адресат ссылки; подглядеть «до прохождения»
   можно только через devtools, вредя лишь собственному развлечению. Сервера-посредника,
   который скрыл бы их до обмена, у нас нет по архитектуре (бэкенд без входящих портов).
5. **Результат — чистая функция `pairFacts` (`src/lib/model/test-pair.ts`)**: пересечение
   двух карт → точные совпадения · «рядом» (|разница| ≤ 1) · «по-разному» (≥ 4) · общие
   «десятки». Счёт совпадений — форма результата «Калькулятора любви» (№028 В3 = А).
   🔴 Ни процентов, ни похожести, ни порядка близости — страж: тест фиксирует ЗАКРЫТЫЙ
   набор полей результата и запрещённые лексемы, доказан мутацией (критерий 5 фазы).
6. **Второй проходит тест, НЕ видя ответов первого** (интерфейс не показывает их до
   присоединения), затем «Сравнить» пишет его ответы тем же согласием.
