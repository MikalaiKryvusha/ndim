# План 08 — Память состояния экранов при навигации

**Статус:** 🔴 ОТКРЫТ · **Когда/контекст:** 2026-07-29, волна владельца `ideas/21` (п. 9) ·
**Тип:** план (механика нужна всему приложению, а не одному экрану) ·
**Блокирует старт:** развилка владельца — см. «⛔ Ждёт владельца»

Это не баг одного экрана. Пункт 9 волны — про **общее свойство приложения**: экран обязан
открываться таким, каким его оставили. Тем же механизмом закрываются часть Б пункта 1 и
пункт 2 той же волны (`bugs/74`, `bugs/75`), поэтому чинить их поодиночке нельзя — получится
три разных приёма для одной механики.

## Симптом — слово владельца дословно

> при навигации, страницы открываются вверху, не сохраняются позиции скрола по каждой из
> страниц. Должны сохраняться. Страницы должны открываться в том состоянии, в каком их
> оставили при навигации С ЭТИХ страниц.

Ударение владельца — на второй фразе: не только прокрутка, а **состояние**.

## Причина — по коду

Разведка (`test-results/ideas21/recon.txt`, «=== ПУНКТ 9 ===», вердикт
ПОДТВЕРЖДЁН_КОДОМ) доказывает причину **пустым грепом**: механизма нет вовсе.

По всему `src/` не встречается ни одного вхождения `export const snapshot`, `afterNavigate`,
`beforeNavigate`, `noScroll`, `scrollRestoration`. Из семейства `data-sveltekit-*` в проекте
ровно один атрибут — `data-sveltekit-preload-data="hover"` (`src/app.html:168`), к прокрутке
он отношения не имеет. Единственный вызов истории во всём приложении —
`history.replaceState(null, '', '/profile')` в почтовом флоу (`src/routes/profile/+page.svelte:232`),
записей он не добавляет. Все `window.scrollTo` — локальные жесты внутри `/dims`
(строки 691, 716, 749, 830).

**Половина первая — прокрутка.** Навигация продукта — обычные ссылки:
`src/lib/ui/BottomNav.svelte:37` и `src/lib/ui/SideRail.svelte:44` — `<a href={item.href} …>`.
Каждый тап по нав-панели — это history PUSH, а не BACK. Клиентский роутер SvelteKit
восстанавливает прокрутку на возврате «назад», а на push ставит её в 0. Механика зафиксирована
не «по здравому смыслу», а **в самом репозитории** — комментарий
`src/routes/+layout.svelte:123-125`:

> SvelteKit при переходе ставит прокрутку в 0, а при возврате «назад» восстанавливает
> прежнюю — оба раза программно.

Значит «Профиль → Измерения → Профиль» — это три записи истории, и третья открывается сверху
**по построению платформы**, а не по ошибке в нашем коде.

> **Честная граница (из разведки).** Что SvelteKit на push-переходе ставит `scrollTo(0,0)` —
> поведение фреймворка, а не строка продуктового кода. В репозитории оно записано как принятый
> диагноз (`+layout.svelte:113-130`), и замер выше с ним согласуется, но отдельным
> экспериментом «push против popstate» это в 2.0 **не перепроверялось**.

**Половина вторая — состояние.** Вид экрана живёт в `$state` компонента и умирает вместе с
ним при уходе с маршрута:

| Файл:строка | Что теряется |
|---|---|
| `src/routes/dims/+page.svelte:92` | `let tab = $state<Tab>('all')` — возврат всегда открывает «Все» |
| `src/routes/dims/+page.svelte:664` | `const tabScroll: Record<Tab, number> = { all: 0, mine: 0 }` — обычная переменная внутри компонента |
| `src/routes/dims/+page.svelte:148` | `shown` — сколько карточек ленты уже показано |
| `src/routes/dims/+page.svelte:157` / `:136` / `:768` | `expanded` (раскрытая карточка), `submitted` (отправленный поиск), `searchOpen` |
| `src/routes/relations/+page.svelte:68` | `revealed = $state(REVEAL_PORTION)` — докуда раскрыт топ (порция 24, `:67`) |
| `src/routes/relations/+page.svelte:49` | `expanded` — раскрытая карточка связи |
| `src/routes/profile/+page.svelte:62` | `seeMeOpen` — открытое «Как меня видят» |

Переживают навигацию только **данные** (кэш сессии, `ideas/18`), но не **вид**.

**Третья, скрытая часть причины: одной прокрутки мало.** Вернуть `scrollY` на длинный экран
нельзя, пока документ не набрал прежнюю высоту, — браузер прижмёт прокрутку к текущему концу.
Это не теория: `bugs/64` поймал промах QA-прогоном — «просили 7658px, получали 7191px»
(`src/routes/dims/+page.svelte:680-684`). Значит «докуда долистана лента» — не украшение, а
**условие** работы памяти прокрутки.

## Что даёт платформа (и почему НЕ надо изобретать своё)

В проекте `@sveltejs/kit ^2.63.0` (`package.json:39`). Штатных механизма два, и оба сейчас
не используются ни разу.

**1. `export const snapshot = { capture, restore }` в `+page.svelte`.** Заведомо существующий
штатный API SvelteKit (по разведке — с версии 1.5). Страница объявляет, что́ считать своим
снимком; платформа снимает его перед уходом и возвращает **при возврате на ту же запись
истории** (back/forward). Это ровно наш случай «вернулся системной „Назад“».

**2. Собственное управление прокруткой SvelteKit.** Роутер сам ведёт позиции по записям
истории: на popstate возвращает прежнюю, на push ставит 0. Плюс есть штатные крючки
`beforeNavigate` / `afterNavigate` (`$app/navigation`) и атрибуты ссылок `data-sveltekit-*`,
которыми поведением прокрутки на переходе управляют декларативно.

**Чего платформа НЕ закрывает сама.** Нав-панель продукта — это push-навигация: тап по
«Измерениям» создаёт **новую** запись истории, а не возвращается на прежнюю. Снимок, снятый
у старой записи `/dims`, к новой записи не относится. Поэтому требование владельца — «в том
состоянии, в каком оставили при навигации **С ЭТИХ** страниц» — снимком в чистом виде не
выполняется: нужен **тонкий свой слой** поверх штатного (`beforeNavigate` → запомнить снимок
по маршруту, `afterNavigate` → вернуть).

> ⚠️ **Не проверено (проверяется первым же шагом плана):** точные границы штатного `snapshot` —
> переживает ли снимок перезагрузку страницы и закрытие вкладки, что именно платформа считает
> «той же записью истории». Строить слой памяти на догадках об этом нельзя: шаг 2 плана
> отводится ровно на то, чтобы увидеть это на стенде.

**Почему не своё.** Самодельная память истории — это самодельный роутер: перехват `popstate`,
свои индексы записей, свои гонки с восстановлением прокрутки роутера. Разведка по пункту 3 той
же волны отдельно предупреждает: три похожих оверлея уже просили себе такой перехват, и это
«быстро превратится в самодельный роутер поверх штатного». Наш слой обязан быть **тонким**:
хранение снимков по маршруту + порядок восстановления. Всё, что умеет платформа (back/forward,
позиции по записям истории), забираем у платформы.

## Где это хранить

Три честных варианта, выбор — за владельцем (вопрос А):

1. **Память сеанса приложения** — модуль рядом с кэшем данных. Прецедент в проекте есть:
   кэш живёт в `const store = new Map<string, Entry>()` (`src/lib/data/cache.ts:110`), никакого
   хранилища браузера. Плюс: единая с данными судьба (F5 обнуляет и то и другое — вид не
   разъедется с содержимым). Минус: перезагрузка страницы теряет позицию.
2. **`sessionStorage`** — переживает перезагрузку страницы, умирает с вкладкой. Прецедент
   тоже есть (`src/lib/data/funnel.ts:50-51`). Минус: данные к моменту возврата перечитаны
   заново и лента может быть **другой** (см. риск ниже) — позиция окажется «в никуда».
3. **`localStorage`** — переживает всё, вплоть до перезапуска браузера. Агент против:
   «вернуть человека туда, где он был вчера» — это уже не память состояния, а сюрприз.

**Ключ хранения — путь маршрута** (`/dims`, `/relations`, …), а не запись истории: именно
этого требует формулировка владельца про push-навигацию по нав-панели.

## Чего НЕ делать

Собрано из заметок разведки (пп. 1, 2, 3, 9) и истории `bugs/64` — это уже пройденные тупики:

- **Не возвращать `scroll-behavior: smooth` на корень.** На программном восстановлении это и
  даёт «съезд», от которого ушли: `src/routes/+layout.svelte:113-130`, `:130 scroll-behavior: auto`.
- **Не городить самодельный роутер** — свой перехват `popstate`, свои индексы истории. Тонкий
  слой поверх штатных `beforeNavigate`/`afterNavigate`/`snapshot`, и не больше.
- **Не восстанавливать прокрутку до того, как документ набрал высоту.** Проверено на живом
  прогоне `bugs/64`: просили 7658px — получали 7191px.
- **Не бороться с рукой человека.** Отступление возврата при `wheel`/`touchstart`/`keydown`/
  `pointerdown` (`dims:700-708`) сохранить при переносе в общий модуль.
- **Не копировать гонку таймеров 1.x** (`setTimeout` 10 мс + 200 мс, `ndim_old/public/scripts/app.js:1157-1161`,
  `:2931-2949`). 1.x добивался порядка задержками; у нас для этого есть явный флаг из шага 6.
- **Не «лечить» панель `/dims` строкой `toolbarHidden = false` в начале `switchTab`**:

## Проверка

**Наблюдение, которым судим починку** (оно же — сценарий владельца): пролистать экран вниз,
уйти по нав-панели на соседний, вернуться — человек видит то же место и тот же вид, без кадра
«сверху» и без рывка.

**Страж `tools/verify-plan08.mjs`** (живой браузер, 390 и 1440, обе темы):

- для каждого из пяти экранов: прокрутить до X → уйти → вернуться → `|scrollY − X| ≤ 2`;
- «Измерения»: вкладка «Мой NDim ID» переживает уход и возврат; у каждой вкладки своя позиция;
- «Измерения» и «Связи»: после возврата в ленте **не меньше** карточек, чем было до ухода
  (иначе позиция вернулась в короткий документ);
- панель «Все / Мой NDim ID» видна после возврата и после смены вкладки туда-обратно
  (общий страж с `bugs/75`);
- консоль чиста.

**Чем доказывается сам страж (мутация).** Отдельная мутация не нужна — красный прогон уже
снят до кода: `test-results/ideas21/report.txt` (900→0, 72→0, 900→0) и есть тот самый
«сломанный код», на котором страж обязан падать. Порядок такой: сначала написать страж и
прогнать его **на текущем `main`** — он обязан дать те же три провала с теми же числами.
Дополнительно, уже после фикса: отключить восстановление «докуда долистано» (шаг 5) — страж
обязан покраснеть на проверке длины ленты, а не только на прокрутке.
