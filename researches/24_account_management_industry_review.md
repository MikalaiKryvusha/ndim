## §1. Firebase Auth — точная механика (зона, где память модели врёт)

🔴 **Первое, что нужно знать: главный гайд Firebase устарел.** Страница
[docs/auth/web/manage-users](https://firebase.google.com/docs/auth/web/manage-users) до сих пор учит
`updateEmail()` и **не содержит ни слова** `verifyBeforeUpdateEmail`, ни слова `enumeration`
(проверено грепом по скачанной странице, и HTML, и markdown). Источник истины — **reference**
(`auth.md`, генерируется из JSDoc в `firebase-js-sdk`) и страница **Email Enumeration Protection**.

### 1.1 Защита от перечисления почт (EEP) — развилка всего эпика

> «If you created your project on or after September 15, 2023, email enumeration protection is
> enabled by default. […] If you created your project before September 15, 2023, email enumeration
> protection is not automatically enabled.»
> — [docs.cloud.google.com/identity-platform/docs/admin/email-enumeration-protection](https://docs.cloud.google.com/identity-platform/docs/admin/email-enumeration-protection)

⚠️ Дата задаёт **умолчание**, а не текущее состояние: флаг переключается в обе стороны (Console →
Authentication → Settings → User actions, либо PATCH Identity Toolkit с
`emailPrivacyConfig.enableImprovedEmailPrivacy`). **Проверять надо фактическое состояние проекта.**
Наш боевой проект — тот же, где живут 331 человек и их пароли из 1.x, то есть он СТАРШЕ водораздела.

Что меняет включённая EEP:

| Операция | Поведение при EEP |
|---|---|
| `updateEmail()` | **Запрещён**: «you can no longer change a user's email address with the update REST API, the setAccountInfo REST API, or the `updateEmail` client SDK method on all platforms» → `auth/operation-not-allowed` |
| `linkWithCredential` с `EmailAuthCredential` (завести пароль) | **Запрещён**; официальный обход — REST `accounts:signUp` с `idToken` |
| `sendPasswordResetEmail()` | Не бросает ошибку для несуществующего адреса — просто резолвится |
| `verifyBeforeUpdateEmail()` | Письмо уходит, **только если новый адрес НЕ занят**, и ошибки при этом нет |
| `fetchSignInMethodsForEmail()` | Возвращает **пустой список** всегда; помечен Deprecated |

🔴 **Смертельная UX-ловушка:** «письмо отправлено» может быть неправдой — при занятом адресе promise
резолвится молча. Единственный честный текст на экране — нейтральный: *«Если адрес свободен, письмо
придёт»*. Ровно так же на сбросе: *«Если такой адрес зарегистрирован, письмо придёт»*.

> «In both cases, there are no specific error messages indicating when emails aren't sent.» — там же.

### 1.2 Смена почты — только `verifyBeforeUpdateEmail`

> «Sends a verification email to a new email address. The user's email will be updated to the new one
> after being verified. If you have a custom email action handler, you can complete the verification
> process by calling `applyActionCode`.»
> — [firebase-js-sdk, packages/auth/src/core/strategies/email.ts](https://raw.githubusercontent.com/firebase/firebase-js-sdk/master/packages/auth/src/core/strategies/email.ts)

Уточнения скептика, важные для кода:

- `actionCodeSettings` **необязателен** (`actionCodeSettings?: ActionCodeSettings | null`); без него
  письмо ведёт на дефолтный обработчик Firebase.
- `applyActionCode(auth, code)` принимает **auth и код из ссылки**, а не объект пользователя.
- `handleCodeInApp: true` нужен **только для входа по ссылке** (`sendSignInLinkToEmail`), где он
  обязателен и в вебе. Для сброса пароля и `verifyBeforeUpdateEmail` — не нужен.
- Формулировка `dynamicLinkDomain` устарела, в текущем API — `linkDomain`.
- Пометки «security sensitive / requires recent login» у `verifyBeforeUpdateEmail` в reference
  **нет** (она есть у `updateEmail`, `updatePassword`, `deleteUser`). Утверждать, что смена почты
  требует свежего входа, по докам нельзя — но экран обязан уметь показать шаг реавторизации.

### 1.3 Отзыв смены почты — есть, но не там, где кажется

Firebase шлёт на **старый** адрес письмо со ссылкой отмены (режим `mode=recoverEmail`):

> «Revoking email address changes — when users change their accounts' primary email addresses,
> Firebase sends an email to their old addresses that allow them to undo the change»
> — [firebase.google.com/docs/auth/custom-email-handler](https://firebase.google.com/docs/auth/custom-email-handler)

🔴 **Но в reference этот механизм привязан к `updateEmail`, а не к `verifyBeforeUpdateEmail`.**
В исходниках Auth-эмулятора OOB-код `RECOVER_EMAIL` порождается только на пути `setAccountInfo`
([operations.ts](https://raw.githubusercontent.com/firebase/firebase-tools/master/src/emulator/auth/operations.ts):
`if (signInProvider !== PROVIDER_ANONYMOUS && user.initialEmail && isEmailUpdate) { sendOobForEmailReset(...) }`).
**Значит защита от угона почты может не приехать сама — проверяется только в бою** (§7, вопрос 3).

Официальный образец обработчика `recoverEmail`: `checkActionCode` → `info.data.email` →
`applyActionCode` → и Google **рекомендует тут же предложить сброс пароля** «in case the account was
compromised».

### 1.4 Пароль

| Вопрос | Ответ |
|---|---|
| Смена пароля | `updatePassword(user, newPassword)`; **требует недавнего входа** — «this is a security sensitive operation that requires the user to have recently signed in» |
| Завести пароль тому, у кого его нет | При EEP `linkWithCredential` **запрещён**; официальный путь — REST `POST accounts:signUp` с `{idToken, email, password}`. Допустимо в статике (обычный `fetch`), но это ручной HTTP, а не SDK |
| Минимальная длина | Серверное правило Firebase — **6 символов** (`WEAK_PASSWORD: The password must be 6 characters long or more`), [REST auth](https://firebase.google.com/docs/reference/rest/auth) |
| Сброс | `sendPasswordResetEmail` → `verifyPasswordResetCode(auth, code)` (вернёт почту владельца кода) → `confirmPasswordReset(auth, oobCode, newPassword)`. Полный цикл клиентский |
| Сброс для аккаунта **без** провайдера password | 🔴 **Ни одна официальная страница этого не описывает.** Для 2.0 это ключевой случай — нужен эксперимент, а не утверждение |

⚠️ **Узнать, есть ли у почты пароль, на клиенте НЕЛЬЗЯ:** `fetchSignInMethodsForEmail` помечен
Deprecated и при EEP всегда пуст. Опираться надо на **`auth.currentUser.providerData`** — список
провайдеров ТЕКУЩЕГО вошедшего человека, он приходит в самом объекте User, без запроса.

### 1.5 Реавторизация

> «Certain sensitive operations — such as deleting an account, updating a user's email, changing a
> password, or enabling multi-factor authentication — require the user to have signed in recently.»
> — [docs.cloud.google.com/identity-platform/docs/web/reauth](https://docs.cloud.google.com/identity-platform/docs/web/reauth)

**Точной цифры «свежести» в доках НЕТ** — только «recently» / «too long ago». Значит UI обязан
всегда быть готов к `auth/requires-recent-login`, а не рассчитывать на «пять минут».

Три пути, и они не взаимозаменяемы:

| Как человек вошёл | Чем реавторизоваться |
|---|---|
| Google (popup) | `reauthenticateWithPopup(user, new GoogleAuthProvider())` |
| Ссылка на почту | `EmailAuthProvider.credentialWithLink(email, location.href)` + `reauthenticateWithCredential` — **документировано отдельно** |
| Пароль (331 человек из 1.x) | `EmailAuthProvider.credential(email, password)` + `reauthenticateWithCredential` |

🔴 `reauthenticateWithPopup`/`WithRedirect` принимают **только OAuth-провайдеров**: «Non-OAuth
providers like EmailAuthProvider will throw an error». Для человека со ссылкой popup невозможен.

⚠️ Официальная оговорка к реавторизации по ссылке: *«as the flow could end up on a different device
where the original user was not logged in, this flow might not be completed. In that case, an error
can be shown to the user to force them to open the link on the same device»*
([email-link-auth](https://firebase.google.com/docs/auth/web/email-link-auth)).

### 1.6 Сессии на других устройствах

> «Refresh tokens expire only when one of the following occurs: The user is deleted; The user is
> disabled; A major account change is detected for the user. This includes events like password or
> email address updates.» — [Firebase, Manage session cookies](https://firebase.google.com/docs/auth/admin/manage-sessions)

То есть **смена пароля и смена почты сами отзывают чужие сессии** — это можно честно написать
человеку. Сброс пароля тоже: «the Firebase Authentication backend handles the revocation
automatically in that case».

🔴 **А вот кнопку «выйти на всех устройствах» сделать нельзя:** явный отзыв живёт только в Admin SDK,
сервера в проде у нас нет. Это ограничение, которое надо записать, а не обойти молча (§5, ASVS 7.4.3).

### 1.7 Удаление

> «`deleteUser(user)` Deletes and signs out the user.» — reference

🔴 **Следствие, определяющее порядок операций:** после `delete()` человек уже не аутентифицирован —
значит **все данные в Firestore и Storage надо удалять ДО вызова**, пока правила его пускают.

Официальное расширение **Delete User Data** удаляет данные по UID из Firestore, RTDB и Storage — но:
требует тариф Blaze, работает на **Cloud Functions** (сервер, которого у нас нет), и
[Firebase Extensions закрываются 31 марта 2027 года](https://extensions.dev/extensions/firebase/delete-user-data)
(«You will not be able to install or edit extensions after this date»). Ставить архитектуру удаления
на расширение — тупик по двум причинам сразу.

### 1.8 Эмулятор — что им можно проверить, а что нельзя

| Можно | Нельзя |
|---|---|
| Забрать oob-коды по REST: `GET /emulator/v1/projects/{p}/oobCodes` (поля `email`, `oobCode`, `oobLink`, `requestType`) — **наш способ тестировать почтовые флоу без почты** (`EXP-0045`) | Проверить **тексты писем**: «The Authentication emulator doesn't send any emails or SMS messages» |
| Прогнать логику сброса и подтверждения | Проверить **лимиты и антифрод**: «does not replicate production rate limiting or anti-abuse features» |
| Переключить EEP флагом `emailPrivacyConfig.enableImprovedEmailPrivacy` (найдено в исходниках, тропа недокументированная) | 🔴 **Довериться зелёному стенду в смене почты:** эмулятор **не применяет запрет EEP** в `setAccountInfo` — `updateEmail()` на стенде пройдёт, а в бою упадёт |

### 1.9 Словарь кодов ошибок (для русских текстов)

`auth/requires-recent-login` · `auth/user-token-expired` · `auth/email-already-in-use` ·
`auth/invalid-email` · `auth/weak-password` · `auth/wrong-password` · `auth/invalid-credential` ·
`auth/user-not-found` · `auth/user-disabled` · `auth/operation-not-allowed` ·
`auth/expired-action-code` · `auth/invalid-action-code` · `auth/too-many-requests` ·
`auth/network-request-failed` · `auth/user-mismatch` · `auth/provider-already-linked` ·
`auth/credential-already-in-use` · `auth/email-change-needs-verification` ·
`auth/unauthorized-continue-uri` · `auth/missing-password`
(константа `AuthErrorCodes`, reference).

**Русские формулировки у нас УЖЕ ЕСТЬ** — в 1.x их писал владелец (§2.4). Переписывать заново нельзя.

## §2. Как это было в 1.x (разведка архива `ndim-old`, снята дословно)

Клон архива, чтение `public/index.html` и `public/scripts/app.js`, сверка с кадрами
`design/reference-1x/`. **Кадр совпал с кодом до буквы** — значит снятое достоверно.

### 2.1 Экран «Управлять аккаунтом» (`app-14`)

Заголовок — **«Управлять аккаунтом»** (инфинитив, `index.html:2181`), не «Управление аккаунтом».
Состав: карточка **«Мой аккаунт»** (жирное `Email` + адрес, жирное `Создан` + дата и время), ниже
через заметный зазор — три строки-двери с иконками и шевронами, строго в порядке:

1. **«Поменять пароль»** (`lock.svg`)
2. **«Поменять Email»** (`support.svg`)
3. **«Удалить аккаунт»** (`person-x.svg`)

Глаголы — совершенного вида «Поменять …». Удаление — рядовая третья строка, **не красная**; краснеет
только кнопка внутри. Карточка «Мой аккаунт» помечена `hidden` и раскрывается, когда данные пришли.

Формат даты (`app.js:5119-5132`): `{year:'numeric', month:'long', day:'numeric'}` + `« в »` +
`{hour, minute}` → **«28 февраля 2025 г. в 20:48»**. Повторяем один в один.

### 2.2 «Поменять пароль» — ДВА поля, а не три

`index.html:2310-2342`: «Текущий пароль:» · «Новый пароль:» (оба с глазом 👁) · кнопка «Сохранить» ·
ниже ссылка **«Сбросить пароль»**. **Поля «повторите пароль» не было** — `researches/12` записал это
неверно, строка исправлена.

Механика (`app.js:7955-7964`): реавторизация текущим паролем → `updatePassword` → **`goBack()`** →
зелёный тост **«Пароль успешно обновлен.»**. Паттерн «успех → уходим назад + тост».

### 2.3 «Поменять Email» — пароль ВЫШЕ нового адреса

`index.html:2383-2408`, порядок: пояснение → «Текущий пароль:» → «Введите новый Email:» →
«Выслать письмо». Пояснение дословно:

> «Для изменения Вашего текущего Email на новый запросите письмо верификации на Ваш новый Email и
> пройдите по ссылке в полученном письме.»

Механика (`app.js:8508-8513`): **уже `verifyBeforeUpdateEmail`** с возвратом на
`https://ndim-space.web.app/?email_change_success=true`. То есть 1.x был технически прав.
После отправки экран **не переключается**, показывается синий тост:

> «Письмо верификации отправлено на указанный новый Email. Пожалуйста, проверьте почту.»

Свои проверки: «Новый Email не может быть пустым.» · «Новый Email не может быть равен текущему.»

⚠️ **Половина сложности 1.x у нас исчезает:** там при следующем входе почта догонялась в трёх
коллекциях Firestore (`users`, `ndimids`, `relations`, `app.js:8138-8166`). В 2.0 почта — ПДн и в
Firestore **не хранится вовсе**, синхронизировать нечего.

### 2.4 «Удалить аккаунт» — и его дефект

`index.html:2451-2475`: предупреждение → «Текущий пароль:» → две кнопки в ряд, «Отмена» и красная
«Удалить». Текст предупреждения дословно:

> «Ваша учётная запись и все её данные будут безвозвратно удалены. Удалить?»

🔴 **Каскад (`app.js:8690-8701`) сносил ровно четыре документа** — `users/{uid}/privat/{uid}`,
`ndimids/{uid}`, `users/{uid}`, `relations/{uid}` — и **`users/{uid}/avatar/avatar.webp` в Storage
оставался сиротой**. Прямое нарушение собственного обещания «все её данные».

🔴 **Второй дефект:** `deleteDocumentById` глушил ошибки внутри себя (`app.js:9697-9711`) —
`deleteUser` выполнялся, даже если данные не удалились. Человек терял вход, данные оставались.
**В 2.0 порядок гарантий обратный: не удалилось — учётную запись не трогаем и честно говорим.**

### 2.5 Сброс пароля (`public-force-reset_password_page`)

Публичный экран, **доступный не вошедшему**. Пояснение дословно:

> «Введите Email на который зарегистрирован Ваш аккаунт. Если аккаунт с указанным Email существует,
> то на этот адресс электронной почты Вы получите письмо для сброса пароля от аккаунта.»

Формулировка «если аккаунт существует» — **правильная приватная формулировка**, совпадает с тем, что
сегодня требует OWASP (§5). Берём как есть. (В тексте живёт опечатка «адресс», в заголовке —
латинская `C` в «Cбросить пароль». Править текст владельца без его слова нельзя — вопрос в §7.)

Приём кода — отдельный экран «Новый пароль»: «Вы запросили сброс пароля от аккаунта {почта}.
Пожалуйста, придумайте новый пароль.», ОДНО поле, минимум 6 символов, `confirmPasswordReset(oobCode)`,
затем переброс на вход.

⚠️ Деталь, о которой легко забыть: перед отправкой 1.x ставил **`auth.languageCode`** — без неё
письмо от Firebase приходит по-английски.

### 2.6 Русские тексты ошибок — язык владельца, не переписывать

`app.js:11208+` (`errorMessengerDocument`): «Пароль должен быть не менее 6 символов.» · «Этот адрес
электронной почты уже используется другой учетной записью.» · «Предоставленные учетные данные
неверны.» · «Эта операция конфиденциальна и требует недавней аутентификации. Авторизуйтесь еще раз,
прежде чем повторить эту операцию.» · «Слишком много запросов. Пожалуйста, повторите попытку позже.» ·
«Что-то пошло не так.» · «Новый пароль не может быть пустым.»

### 2.7 Главная развилка, которую 1.x нам не решает

> ```js
> const credential = EmailAuthProvider.credential(user.email, provided_password);
> await reauthenticateWithCredential(user, credential);
> ```
> — `app.js:8083-8090`

**Весь экран управления аккаунтом 1.x молча предполагал, что у человека ЕСТЬ пароль.** В 2.0 вход —
Google / ссылка на почту / гость. Дословный перенос невозможен: экран обязан ветвиться по
`user.providerData`, а поле «Текущий пароль:» показывать только тем, у кого провайдер `password` есть.

## §3. Форма экрана — что делают зрелые продукты

| Продукт | Форма | Донор чего |
|---|---|---|
| **GitHub** | Отдельный экран настроек, боковой рельс разделов; удаление — **внизу**, отдельным блоком, в документации названо просто «Delete account» (не «danger zone») | Позиция деструктива; формула необратимости «GitHub cannot restore your content» — **без слова «навсегда»** |
| **Vercel** | Беспарольный (код на почту + провайдер). Раздел называется **«Authentication»** и показывает **СПИСОК способов входа** | Ближайший к нам прецедент: имя раздела и анатомия строки почты (адрес + бейдж состояния + меню) |
| **Notion** | Беспарольный, но пароль — **опция с тремя операциями: завести · сменить · убрать**. Новая почта подтверждается **кодом**, который вводят обратно в интерфейс | Форма, вмещающая оба наших состояния (есть пароль у 331 / нет у остальных) |
| **Slack** | Смена почты — **раскрывашка** («Expand») внутри страницы, замок — пароль | Третий вариант формы для макетов |
| **Google** | Раздел назван действием — «How you sign in to Google»; при удалении **перечисляет потери конкретными вещами** («emails, files, calendars, and photos») | Имя раздела; конкретика вместо «все данные» |
| **Substack** | Беспарольный; смена почты подтверждается письмами **и на старый, и на новый** адрес | Защита от угона — самый ценный приём |

**Подтверждение удаления, три найденных способа:** ввод почты/фразы в поле (GitHub — **два** поля,
пароль не спрашивается; Notion — почта аккаунта вручную) · повторный вход (GitHub sudo mode, 2 часа) ·
письмо со ссылкой (Vercel — **требует сервера, нам недоступно**).

**Аватар — единогласно:** точка входа в управление фото это **само фото** (Notion: «Select your
current photo»), удаление живёт **в том же меню**, что и загрузка (GitHub: «Edit → Remove photo to
revert to your identicon»), а шаг кадрирования есть у всех трёх (GitHub, Slack, Google).

🔴 **Два антипримера, которые владелец-QA засчитает как дефект:** у Slack удаление фото **только на
десктопе**, у Substack смена почты **только в вебе**. Набор действий обязан совпадать на телефоне и
на десктопе.

### 3.1 Правила деструктивных действий

- **NN/g:** диалог подтверждения — только для серьёзных последствий; **«Do not ask *Are you sure you
  want to do this?*»**; кнопки описывают исход, а не «Да/Нет»; **умолчания лучше не задавать вовсе**
  (чтобы Enter не удалял аккаунт) ([Confirmation dialogs](https://www.nngroup.com/articles/confirmation-dialog/)).
- **NN/g:** соседство деструктивной и безобидной кнопок — в **десятке главных ошибок**
  проектирования; закон Фиттса разрешает намеренно **усложнить** попадание в опасную
  ([Proximity of consequential options](https://www.nngroup.com/articles/proximity-consequential-options/)).
- **NN/g:** частые подтверждения обесцениваются («cry wolf»); undo — **дополнение** к подтверждению,
  а не альтернатива.
- **GOV.UK:** красная кнопка — только на **финальном** подтверждении, на входе кнопка обычная; и
  **нельзя полагаться на один цвет** — смысл несёт текст ([Button](https://design-system.service.gov.uk/components/button/)).
  Для нас это вдвойне: канон бренда требует Ч/Б-инварианта.
- **Apple:** деструктивная кнопка красная и **слева**, «Отмена» справа; и осторожно с русским
  словом «отмена» в заголовке — «Отменить смену почты?» с кнопками «Отменить»/«Отмена» это каша.
- **GOV.UK** разрешает группировать связанные вопросы на одной странице — то есть дробить
  «Управление аккаунтом» на четыре маршрута не обязательно, но каждое **действие** внутри должно
  быть отдельным сфокусированным шагом.

### 4.2 OWASP Cheat Sheets

- **Forgot Password:** одинаковый ответ и **одинаковое время** для существующего и несуществующего
  адреса · токен одноразовый, привязан к человеку, истекает · после сброса — письмо (**без пароля
  внутри**) · **не логинить автоматически** · спросить про инвалидацию сессий ·
  **не блокировать аккаунт** в ответ на шквал запросов (это отказ в обслуживании) —
  [cheatsheetseries.owasp.org](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html).
- **Authentication:** зачем поле текущего пароля — дословно про наш случай:
  > «a user logs in on a public computer and forgets to log out. Another person could then use that
  > active session. If we don't verify the current password, this other person may be able to change
  > the password.»
- **Authentication, «Changing A User's Registered Email Address»:** золотой стандарт — **два письма**:
  уведомление на старый адрес (со ссылкой «сообщить о неожиданной активности») и подтверждение на
  новый. **Если MFA нет — планка выше: подтверждение и со старого адреса тоже.**
  Там же честная оговорка: Google для парольных аккаунтов шлёт на старый адрес **только
  уведомление**, и OWASP называет это рискованным подходом.
- **Session Management:** идентификатор сессии перевыпускается после любой смены уровня привилегий,
  смена пароля названа прямо.
- **Choosing and Using Security Questions** открывается предупреждением: секретные вопросы больше не
  признаются приемлемым фактором, а **«Account recovery is just an alternate way to authenticate so
  it should be no weaker than regular authentication»** — лучший критерий для нашего сброса.

### 4.3 NIST SP 800-63B-4

- **§3.1.1.2:** минимум **15 символов**, если пароль — единственный фактор (8 допустимо только внутри
  MFA); максимум не менее 64 · **SHALL NOT** правила состава · **SHALL NOT** периодическая смена ·
  **SHALL** сверять новый пароль со списком утёкших · **SHALL** разрешать менеджеры паролей,
  **SHOULD** разрешать вставку и предлагать показ · пароль проверяется **целиком**, обрезка запрещена.
- **§3.1.1:** *«Passwords are not phishing-resistant.»* — одной строкой обосновывает, почему не надо
  добавлять пароль в беспарольный продукт «для удобства».
- **§4.6:** события аккаунта **SHALL** вызывать уведомление, и оно **SHALL** содержать чёткую
  инструкцию, что делать, **если это не Вы**.
- **§4.3:** 🔴 **ключевое для нас** — *«Replacement of a forgotten password where the subscriber can
  authenticate with one or more other authenticators is considered to be the binding of a new
  authenticator rather than account recovery.»* То есть **в беспарольном продукте «сброс пароля» не
  существует как отдельная сущность** — это «войдите привычным способом и задайте новый способ входа».
- **§4.5:** аутентификаторы **SHALL** аннулироваться, когда аккаунт перестал существовать или человек
  попросил — норма и под удаление, и под гашение legacy-паролей.
- **Приложение B:** **passkeys** (WebAuthn) легитимны до AAL2 включительно; для публичных приложений
  отсутствие аттестации **SHOULD NOT** блокировать их использование.
- **FAQ B11 (§5.1.3.1):** почта **не допускается** как канал одно- или многофакторной аутентификации
  («methods that do not prove possession of a specific device, such as VOIP or email, SHALL NOT be
  used for out-of-band authentication»). Для потребительского продукта уровня L1 это не блокер (ASVS
  относит запрет к L3), но это **осознанный компромисс, который надо записать**, и довод против того,
  чтобы почта была ЕДИНСТВЕННЫМ способом восстановления.

### 4.4 Право на удаление — это обязанность, а не жест

- **GDPR ст. 17(1):** человек вправе требовать стирания, и контролёр **обязан** стереть «without
  undue delay» ([gdpr-info.eu/art-17-gdpr](https://gdpr-info.eu/art-17-gdpr/)).
  **Ст. 12(3):** сообщить о действиях — в течение **одного месяца**.
- **Google Play (Account Deletion Requirement):** нужны **ОБА** пути — внутри приложения **и**
  веб-ссылка, по которой удаление можно запросить, **не возвращаясь в приложение и не переустанавливая
  его**. Для не-мобильных поверхностей (веб) внутренний путь не обязателен, но «readily discoverable
  option to initiate account deletion» обязателен
  ([support.google.com/googleplay/…/13327111](https://support.google.com/googleplay/android-developer/answer/13327111?hl=en)).
- **App Store Guidelines 5.1.1(v)**, с **30 июня 2022**: «If your app supports account creation, you
  must also offer account deletion within the app»; и **только деактивации недостаточно** —
  «only offering to temporarily deactivate or disable an account is insufficient»
  ([developer.apple.com](https://developer.apple.com/support/offering-account-deletion-in-your-app/)).

## §5. Что из этого следует для NDim Space 2.0

1. **Смена почты — только `verifyBeforeUpdateEmail`.** Текст нейтральный («если адрес свободен»),
   потому что при EEP успех может быть молчаливой неудачей.
2. **Нужна своя страница-обработчик почтовых действий.** Доки требуют лишь «веб-страницу,
   использующую Firebase JS SDK» — то есть `adapter-static` не мешает, `/auth/action` пререндерится,
   работу делает клиентский JS. Режимы: `resetPassword`, `recoverEmail`, `verifyEmail`,
   `verifyAndChangeEmail`. 🔴 **Если своя страница появится, она ОБЯЗАНА уметь `recoverEmail`** —
   иначе ссылка отмены смены почты приведёт в никуда.
3. **Реавторизация ветвится по `providerData`** — трёх путей, не одного. Поле «Текущий пароль:»
   показываем только тем, у кого провайдер `password` есть.
4. **«Сброс пароля» в беспарольном мире переименовывается.** По NIST §4.3 это привязка нового
   способа входа. Раздел логичнее назвать по способу входа (модель Vercel/Google), а не «Пароль».
5. **Удаление: порядок фиксирован и обратен 1.x.** Сначала Storage и Firestore (клиентом, батчами),
   **потом** `deleteUser`. Не удалилось — учётную запись **не трогаем**.
6. **Каскад упирается в правило `relations`.** Клиенту запись в `relations/{uid}` запрещена
   (`firestore.rules:255 — allow write: if false`), а Cloud Functions в проде нет. Варианты: новое
   правило «владелец удаляет свой `relations`» либо чистка суточным проходом сервера синхронизации.
   Плюс подколлекции Firestore не удаляются вместе с документом — их придётся вычищать поштучно.
7. **Обещание «выйти на всех устройствах» дать нельзя** (Admin SDK). Но смена пароля/почты делает
   это сама — так и написать, честно.
8. **Уведомление на СТАРЫЙ адрес нам отправить нечем.** Приём Substack недоступен без сервера; можно
   рассчитывать только на письмо-откат Firebase, а оно, возможно, приходит лишь на пути `updateEmail`
   (§1.3). Проверка — в бою.
9. **Проверку пароля по спискам утечек** (NIST SHALL) без внешнего вызова не сделать: единственный
   практичный путь — k-anonymity API Have I Been Pwned. Это не CDN-скрипт, но это внешний сетевой
   вызов — вопрос к владельцу.
10. **Публичная страница удаления** (требование Google Play к веб-ссылке) дешевле сделать сразу, чем
    возвращаться, если продукт когда-нибудь пойдёт в сторы обёрткой.
11. **Письма Firebase — лицо продукта.** Сейчас они английские и от лица Firebase. Перевод и вычитка
    трёх шаблонов (сброс пароля · смена адреса · подтверждение адреса) — работа эпика, о которой
    легко забыть. Правится в консоли, агент туда не ходит.

## §6. Анти-паттерны (сводно)

**Пароли:** секретные вопросы (отвергнуты трижды: NIST, ASVS 6.4.2 на L1, отдельный лист OWASP) ·
подсказка к паролю · принудительная периодическая смена · правила состава («минимум одна заглавная») ·
потолок длины ниже 64 и тихая обрезка · запрет вставки и борьба с менеджерами · пароль в письме.

**Почта и сброс:** разные ответы (и разное **время** ответа) для существующего и несуществующего
адреса · «этот адрес уже занят» на экране смены · блокировка аккаунта в ответ на шквал «забыл
пароль» · автовход сразу после сброса · многоразовый или долгоживущий токен · смена почты без
подтверждения нового адреса (наивный `updateEmail`) · смена почты без реавторизации и без
уведомления старого адреса.

**Сессии:** оставить все сессии живыми после смены пароля/почты.

**Удаление:** «заморозка» вместо удаления (Apple прямо: insufficient) · удаление только по письму в
поддержку · удаление документа с оставлением файлов в Storage (сирота-ПДн — **дефект 1.x**) ·
мгновенное необратимое стирание без окна отмены · «Вы уверены?» вместо названного последствия ·
кнопки «Да/Нет» · деструктивная кнопка в фокусе по умолчанию · «Сохранить» рядом с «Удалить» ·
постоянно висящая красная кнопка · красный как единственный носитель смысла · слово «навсегда».

**Платформа:** верить гайду `manage-users` · `fetchSignInMethodsForEmail` как способ узнать про
пароль · расчёт на «5 минут свежести» · popup-реавторизация для человека со ссылкой · Cloud
Functions / расширение Delete User Data как основа каскада · удаление данных **после** `delete()` ·
зелёный Auth-эмулятор как доказательство готовности смены почты.

**Форма:** разрыв возможностей между телефоном и десктопом · отдельный полноэкранный маршрут ради
одного аватара · загрузка аватара без шага кадрирования · «danger zone» как подпись в интерфейсе.

### 7.2 🔴 Замер, опровергающий механизм, заложенный в план `[TESTED: 2026-08-01 · tools/probe-account-phase2.mjs + типы SDK]`

**`providerData` НЕ отличает «есть пароль» от «входит по ссылке».** Прибор показал `providerId:
password` у человека, заведённого **только** ссылкой на почту, — и это не артефакт эмулятора.
Типы SDK говорят прямо:

> `static readonly PROVIDER_ID: 'password';`
> `/** Always set to {@link ProviderId}.PASSWORD, **even for email link**. */`
> — `node_modules/@firebase/auth/dist/auth-public.d.ts:1031, 1041`

Различие живёт в **`signInMethod`** (`password` против `emailLink`), а его на клиенте отдавал только
`fetchSignInMethodsForEmail` — **устаревший и при EEP всегда пустой** (§1.4).

🔴 **Что это ломает.** Решение владельца В1 = А («раздел пароля видят только те, у кого пароль
реально есть») **нечем исполнить тем способом, который записан в плане**. Нужен другой механизм —
это работа фазы 7, и она начинается не с вёрстки, а с ответа на вопрос «как отличить».
Известные направления (ни одно не проверено): пробный `updatePassword` с ловлей ошибки · отметка,
поставленная миграцией 1.x (кто пришёл с паролем — известно из архива) · показывать «Сбросить
пароль» всем с почтой (для беспарольного это по NIST §4.3 и есть «задать способ входа», то есть
безвредно, но это уже другое решение владельца).

### 7.3 🔴 Отмена смены почты не рождается `[TESTED: 2026-08-01 · эмулятор Auth, 2 прогона из 2]`

После `verifyBeforeUpdateEmail` и перехода по ссылке почта **реально менялась** (HTTP 303, новый
адрес в аккаунте), но кода `RECOVER_EMAIL` **не появилось ни разу**. Совпадает с чтением исходников
эмулятора (§1.3): откат порождается только на пути `setAccountInfo`, то есть на мёртвом `updateEmail`.

⚠️ **Это индикация, а не приговор:** эмулятор ≠ бой, а в бою шаблон отката настроен и по-русски
(§7.1). Проверяется **только живым тестовым аккаунтом**. Но планировать фазу 5 надо от худшего:
**защита от угона почты может не приехать сама**, и тогда её роль играет наш собственный UX.

### 7.4 CORS боевого бакета — блок оказался ложным `[TESTED: 2026-08-01 · OPTIONS-предзапрос, 4 метода]`

`storage.cors.json` разрешает только `GET`, и локальная разведка занесла это в блокеры. Замер
заголовками (а не чтением конфига — `EXP-0063`) показал обратное: v0-эндпоинт Firebase Storage
отвечает на предзапрос с `Origin: https://ndimspace.app`:

```
Access-Control-Allow-Origin:  *
Access-Control-Allow-Methods: POST, GET, HEAD, DELETE, PATCH
```

— одинаково для всех четырёх запрошенных методов. `storage.cors.json` управляет **другой**
поверхностью (API самого GCS), а SDK ходит на `firebasestorage.googleapis.com/v0`. **Загрузка
(`POST`) и удаление (`DELETE`) блоком не являются.**

⚠️ **Но `PUT` в списке НЕТ.** Если `uploadBytesResumable` где-то использует `PUT`, он упрётся в
предзапрос. Ещё один довод за простой `uploadBytes` (§`researches/23` §6) — и повод замерить, если
всё же понадобится отмена загрузки.

### 7.5 Что осталось «только боем»

- Ведёт ли себя `sendPasswordResetEmail` при EEP так, как описано, — **и рождается ли код для
  аккаунта без пароля.** 🔴 **Прибор этого не измерил:** переключить EEP на эмуляторе по найденной
  в исходниках тропе **не удалось (HTTP 404)**, а контрольный опыт не различал два случая, потому
  что оба показывали провайдер `password` (§7.2). Замер честно провален, а не «зелёный».
- Приходит ли письмо-откат в бою (§7.3).
- Требует ли `verifyBeforeUpdateEmail` свежего входа: **застаревшую сессию эмулятор не
  воспроизводит**, состарить токен нечем. Экран обязан ловить `auth/requires-recent-login` в любом
  случае.
- Меняется ли download-token при перезаписи объекта Storage.
