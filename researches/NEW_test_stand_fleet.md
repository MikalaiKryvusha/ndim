Почему именно так: механизм уже наполовину существует и ничего не надо изобретать.

настоящим адресом (доказано по коду CLI, `emulator/env.js:14–27`). То есть слот **не надо
настраивать, объявлять и помнить** — он выводится из того, где роль стоит, а половина приборов
получает верный адрес сама, как только перестанет игнорировать переменную.

## 2. Точки изоляции — что каждая технология даёт даром

### Firebase Emulators — изоляция есть, но только через СВОЙ конфиг

- **Порты берутся ИЗ `firebase.json`**, флагов `--port` у `emulators:start`/`exec` нет вовсе
  (проверено `firebase emulators:start --help`: только `--only`, `--inspect-functions`,
  `--import`, `--export-on-exit`, `--log-verbosity`).
- **Но есть глобальный флаг `-c, --config <path>`** (проверено `firebase --help`) — он и есть
  дверь к парку: каждой роли свой `firebase.<слот>.json` с её портами.
- **Занятый порт не «переезжает» молча**, а роняет запуск: `Could not start …, port taken.`
  (`emulator/portUtils.js:321`). Отсюда сегодняшняя реальность: две роли физически не могут
  поднять стенд одновременно — вторая получает отказ. Замок доски описывает эту механику, а не
  создаёт её.
- 🔑 **`emulators:exec` САМ раздаёт адреса дочернему процессу** — `setEnvVarsForEmulators`
  (`emulator/env.js:10–27`) кладёт в окружение команды `FIRESTORE_EMULATOR_HOST`,
  `FIREBASE_AUTH_EMULATOR_HOST`, `FIREBASE_STORAGE_EMULATOR_HOST` и
  `CLOUD_STORAGE_EMULATOR_HOST` с ФАКТИЧЕСКИМ `host:port`. Значит любой прибор, запущенный
  внутри `npm run stand`, получает верный адрес слота бесплатно — если читает переменную.
- `singleProjectMode: true` и `--project demo-ndim-dev` изоляции портов НЕ дают (это про
  идентификатор проекта), но и мешать парку не будут: экземпляры разные, данные у каждого свои.

### Vite — изоляция даром

`vite dev --port N` и `vite preview --port N --strictPort` уже используются проектом; в
`vite.config.ts` порт не задан вовсе, то есть перебивается флагом без правки конфига.
`--strictPort` обязателен: без него vite тихо переезжает на соседний порт, и роль начинает
смотреть чужой сайт.

### Playwright — адрес берётся из конфига, и здесь же лежит мина

`playwright.config.ts` задаёт `baseURL` и `webServer.url` литералом, а `webServer` имеет
**`reuseExistingServer: true`**.

🔴 **Это опасно уже СЕГОДНЯ, до всякого парка.** Если сосед держит `vite preview` на 4173,
`npm run e2e` у другой роли не поднимет свой сервер, а молча прогонит проверки **по чужой
сборке**. Прогон будет выглядеть нормальным. Это тот же класс, что `EXP-0091` (осиротевший
preview отдаёт старую сборку), но теперь с чужим worktree в роли источника.

### Приложение — знает эмуляторы «по факту localhost»

`src/lib/firebase.ts:93–95`: стенд определяется ХОСТОМ (`localhost`/`127.0.0.1`), а порты
эмуляторов вшиты константами. Отсюда второе следствие для парка, важное само по себе:

🔴 **Правило `EXP-0027` («e2e требуют погашенного стенда») сегодня действует МЕЖДУ РОЛЯМИ.**
Проверки ждут поведения «эмуляторов нет», а приложение стучится на 8181 независимо от того, чей
это стенд. Значит **стенд соседа красит чужой e2e в красный**, и сессия идёт чинить исправный
код. При парке формулировка правила становится «гаси СВОЙ стенд» — но только если порты
эмуляторов станут слотовыми и в приложении тоже; иначе парк сделает этот класс ложных падений
не реже, а чаще.

прогретый.**

### Состояние машины прямо сейчас

| Величина | Значение |
|---|---|
| Физическая память | **31,89 ГБ**, свободно **4,59 ГБ** |
| Лимит фиксации (ОЗУ + файл подкачки) | **53,89 ГБ**, свободно **0,56 ГБ** |

| Посторонний — игра `Palworld` (2 процесса) | ~5,7 ГБ |

### Что из этого следует — и чего НЕ следует

1. **Дорог не стенд, дорога команда.** Пять стендов по 1,6 ГБ — это **≈8 ГБ**; одни только окна
   VS Code пяти ролей стоят 10,4 ГБ, то есть дороже всего парка.
2. 🔴 **Ограничитель — не ОЗУ, а ЛИМИТ ФИКСАЦИИ, и сегодня его осталось 0,56 ГБ.** Это
   единственное число, из-за которого нельзя написать «32 ГБ хватит на всё»: система уже
   выписала почти все обязательства, и следующий крупный процесс упрётся не в физическую память,
   а в этот потолок. Именно так выглядит родня `bugs/134`: падение по нехватке памяти при живом
   стенде и одновременной сборке.
3. **Замер сделан на «грязной» машине, и это названо честно:** рядом идёт игра (~5,7 ГБ) — она
   транзиентна и к команде отношения не имеет. Без неё картина заметно легче, но проверять это
   надо замером, а не арифметикой.
4. **Практический вывод:** парк на 2–3 одновременных стенда сегодняшняя машина держит; парк на
   5 одновременных — это разговор с владельцем про файл подкачки и про то, сколько окон он
   держит открытыми. Разговор ведёт Менеджер, не я.

⚠️ **Чего замер НЕ говорит.** Он не мерил ДВА стенда разом — их сегодня нельзя поднять
(порт занят, CLI отказывает). Число «два стенда = 2 × 1,6 ГБ» — арифметика, а не факт: у
эмуляторов может быть общий дисковый кэш и разная реакция на параллельную сборку. Первым делом
плана должен быть замер двух слотов, а не вера в умножение.

## 4. Схема параметризации — предложение с ценой

### Рекомендуемая: СЛОТ РОЛИ из имени каталога

```
слот = позиция роли:  manager 0 · designer 1 · qa 2 · dev-1 3 · dev-2 4 · dev-3 5
порт  = база + слот × 10
        preview 4173 → 4173, 4183, 4193, 4203, 4213, 4223
        dev     5173 → 5173, 5183, …
        firestore 8181 · auth 9099 · storage 9199 — так же
```

**Почему выведение, а не настройка.** Файл настройки можно забыть, скопировать чужой, потерять
при `reset` ветки. Имя каталога подделать нельзя: роль стоит там, где стоит. Функция
`roleFromDirName` уже написана и покрыта самотестом (`tools/team-status.mjs:96–105, 166–168`) —
её надо переиспользовать, а не писать вторую.

**Порты проверены на свободность пробой, а не предположением** (`Get-NetTCPConnection -State
Listen`): диапазоны `4173…4230`, `5173…5230`, `8181…8240` свободны целиком; в окрестности
`9099` занят **9100** (`lghub_updater`), в окрестности `9199` — **9247** (`nordvpn-service`);
`8080` занят `llama-swap`, как и записано в досье. Шаг 10 обходит все три занятых порта.

### Цена — пять мест правды

| № | Файл | Что делать | Строк |
|---|---|---|---:|
| 1 | `tools/lib/stand-slot.mjs` (новый) | слот и все порты одной функцией; переиспользует `roleFromDirName` | ~60 |
| 2 | `firebase.json` → `firebase.<слот>.json` | генерировать из шаблона; `emulators:exec -c` | ~30 (генератор) |
| 3 | `package.json` | `stand`, `test:rules`, `test:sync`, `preview`, `dev` — через обёртку, знающую слот | 5 строк |
| 4 | `src/lib/firebase.ts` | три константы → `import.meta.env.VITE_*` с нынешними значениями по умолчанию | ~8 строк |
| 5 | `playwright.config.ts` | `baseURL`/`webServer.url` из переменной; **`reuseExistingServer` пересмотреть** | ~5 строк |

**Плюс хвост приборов — 110 правок по одной-две строки:** 36 обязательных (эмуляторы: читать
`FIRESTORE_EMULATOR_HOST` и родню, литерал оставить умолчанием) и 74 желательных (адрес
приложения из общего модуля). Правки механические и однотипные; после них **страж** —
по образцу уже стоящего `src/lib/ops/stand-cleanup.test.ts`: «ни один прибор не вшивает адрес
стенда литералом мимо общего модуля». Без стража хвост отрастёт заново в первую же неделю.

**Порядок, при котором польза приходит раньше расходов:**
1. слот + эмуляторы + `npm run stand` → **снимает главный дефицит** (за замок дерутся ради
   эмуляторов);
2. preview и e2e → снимает вторую очередь (кадры, живая приёмка) и **лечит мину
   `reuseExistingServer`**;
3. хвост приборов + страж → делает парк необратимым.

### Альтернативы, честно взвешенные

| Путь | Плюс | Минус | Вердикт |
|---|---|---|---|
| **A. Слот роли** (рекомендую) | ничего не настраивать, механизм наполовину есть | 110 механических правок в хвосте | ✅ |
| **B. Оставить один стенд, усилить дисциплину очереди** | ноль кода | не исполняет заказ владельца; очередь уже наблюдалась | ❌ |
| **C. Docker-контейнер со стендом на роль** | изоляция полная, включая ОС-ресурсы | контейнеры — синглтоны Менеджера по манифесту; +память на слой; эмуляторы в Docker — новый неизведанный контур | ⏸ обсуждать, если A упрётся в память |
| **D. Слот из файла настройки в worktree** | явнее, чем выведение | файл забывают, копируют чужой, теряют при `reset` — класс «истина ↔ зеркало» | ❌ |

## 5. Риски и «чего не делать»

- ⛔ **Не трогать синглтоны машины.** Docker-контейнеры `ndim-server-*`, боевая и стейдж базы,
  дверь выката `npm run deploy` — остаются под замком и за Менеджером. Парк — про СТЕНД, и
  только про стенд.
- ⛔ **Не занимать `8080`** (`llama-swap`) — доказано пробой сегодня. И не занимать `9100`
  (`lghub_updater`) и `9247` (`nordvpn-service`): на машине живут чужие службы, и они старше
  нашей команды.
- 🔴 **`reuseExistingServer: true` в Playwright — мина, которая уже заряжена.** До парка её
  надо либо выключить, либо привязать к своему порту: иначе роль прогоняет e2e по сборке соседа
  и получает зелёное там, где своего кода нет вовсе.
- 🔴 **`EXP-0027` перестаёт быть верным как написан.** «Гаси стенд перед e2e» превращается в
  «гаси СВОЙ стенд»; до слотовых портов в ПРИЛОЖЕНИИ соседский стенд продолжит красить чужие
  прогоны красным. Урок придётся переписать вместе с кодом, а не после.
- ⚠️ **Память — предусловие, а не следствие.** Пока лимит фиксации на нуле, парк из пяти
