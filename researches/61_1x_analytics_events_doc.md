## Где это лежит у владельца

**`working_docs/Events for analytics.ods`** — таблица OpenDocument, 26 265 байт, рядом с его
логотипами и текстом приглашения в бету. Не в коде, не в README — отдельным рабочим документом.

**Он вёл её в git, и вёл долго:** 7 коммитов, и имена коммитов показывают ритм работы —
`events doc` · `doc` · `utm analytics for user atribution` · `report_dim_form and base
functionality` · `event Email verified` · `verifyAndChangeEmail`. То есть документ правился
ТЕМ ЖЕ коммитом, что и код, который заводил событие.

**Объём на момент снятия:** 162 строки, **35 событий**, версии приложения от `0.2` до `1.3`.

## Формат — дословно

Документ несёт ДВЕ таблицы, и это его главное устройство.

### Таблица 1 — события. Шапка дословно:

```
Version | Event Name | Description | Property Name | Property Description | Data Type | Sample Values
```

Одно событие занимает столько строк, сколько у него свойств: первая строка несёт версию, имя и
описание события плюс первое свойство, каждое следующее свойство идёт своей строкой с пустыми
первыми колонками.

**Образцы его записей, дословно:**

| Version | Event Name | Description | Property Name | Property Description | Data Type | Sample Values |
|---|---|---|---|---|---|---|
| 0.2 | event Dom loaded | Приложение загрузило DOM модель сайта | | | | |
| 0.2 | event Page opened | Открыта страница приложения | page | ID страницы | String | home_page |
| 0.2 | event User did search | Пользователь выполнил поиск Dims | search_string_raw | Поисковой запрос пользователя исходный, без нормализации | String | Пятый элемент 1324№;№!№%: |

### Таблица 2 — свойства пользователя. Шапка дословно:

```
Version | Property Name | Property Description | Data Type | Sample Values
```

Здесь живёт то, что цепляется ко ВСЕМ событиям сразу: `build` (номер сборки, Int, `300`) ·
`build_time` · `version` (`«0.6 beta 4»`) · `commit_hash` · `email_verified` (Boolean) ·
`app_type` (`web` — в веб-браузере; `pwa` — установленным PWA) · `utm_source` / `utm_medium` /
`utm_campaign` (появились в версии 1.2, «Источник атрибуции»).

## Четыре свойства его формата, ради которых он и снят

1. **Колонка `Version` — это версия ПРИЛОЖЕНИЯ, в которой событие появилось.** Она и делает
   документ отслеживаемым во времени: по нему видно, что `event User suggested new dim` пришёл
   в 0.6, атрибуция — в 1.2, а `event Email verified` — в 1.3. Историю событий он держал внутри
   документа, а не только в git.
2. **Имя события — человеческой фразой с приставкой `event`,** в прошедшем времени, о
   СЛУЧИВШЕМСЯ факте: `event Sign in`, `event Account deleted`, `event Abuse attempt`.
3. **Каждое свойство описано словами и снабжено ОБРАЗЦОМ значения.** Колонка `Sample Values`
   заполнена почти везде — это то, что делает документ пригодным для чтения через полгода.
4. **Описание события отвечает на вопрос «что произошло в системе»,** а не «куда нажал человек»:
   «Приложение успешно закрыло экран загрузки и открыло какой-то из главных экранов».

## 🔴 Две находки, которые обязаны попасть в решение

### Находка 1. `.ods` — двоичный файл, и git его изменения НЕ показывает

Владелец просит документацию, «*чтобы её можно было отслеживать*». Его собственный носитель эту
задачу решает наполовину: файл в git лежит, 7 коммитов видно, а ЧТО именно поменялось внутри —
не видно, потому что OpenDocument это zip. Отследить можно факт правки, не саму правку.

**Отсюда наше решение:** берём его формат — семь колонок, две таблицы, колонку версии, образцы
значений — и кладём его в **Markdown-таблицу в git**. Тогда «отслеживать» начинает работать
целиком: `git diff` показывает добавленное событие строкой, а страж может сверить документ с
кодом. Формат владельца сохраняется дословно; меняется только носитель, и меняется он ровно
ради того свойства, которое владелец назвал вслух.

### Находка 2. Содержимое таблицы 1.x повторять НЕЛЬЗЯ — оно нарушает инварианты 2.0

Это разведка формата, и содержание её образцов в 2.0 законом не является. В таблице 1.x прямо
записано, что в аналитику уезжало:

- **`email` — «Email пользователя Firebase»** (образцом там стоит личная почта владельца; сюда
  она не переписана — ПДн в git не заводим) — стоит свойством
  у `event Sign in`, `event Sign out`, `event User signed up`, `event Account deleted` и ещё
  у шести событий, плюс в таблице свойств пользователя;
- **`uid` — UID пользователя Firebase** — там же;
- **предмет оценки**: `event User added a new dim` несёт свойства `name` («Имя Dim на русском»,
  образец `Пятый элемент`), `value` («Оценка Dim, выставленная пользователем», образец `10`),
  `author`, `year`;
- **поисковый запрос человека дословно**: `search_string_raw` — «исходный, без нормализации».

В 2.0 это запрещено собственными решениями владельца: предмет оценки третьей стороне не уходит
(интервью №002, В4 — стоп-критерий, подтверждён при выборе инструмента в №054), а почта и UID —
персональные данные, которым в стороннем сервисе места нет.

🔑 **Формулировка правила, чтобы будущая сессия не спутала:** **из 1.x мы берём ФОРМУ документа
и не берём СОСТАВ событий.** Форма — его работа, которую он просит повторить. Состав — то, что
в 2.0 решают его же более поздние решения о приватности.

## Как ведём документацию у нас — предложение к исполнению

- **Место:** `qa/analytics-events.md` — рядом с картой путей человека (`qa/JOURNEYS.md`), теми же
  правилами дома. ⚠️ Точку кладёт Менеджер: `qa/` — дом QA, и заводить там документ без его
  слова я не стану.
- **Форма:** две таблицы дословно по колонкам владельца. `Version` у нас — версия приложения из
  `package.json` на момент, когда событие завелось.
- **Правило правки:** документ правится ТЕМ ЖЕ коммитом, что и код события, — так его вёл он
  сам, и это же снимает вечный дрейф «код ушёл вперёд документа».
- **Страж пары «истина ↔ зеркало»** (по канону реестра пар): истина — белый список имён событий
  в коде, зеркало — строки документа; одна команда сверяет, что множества совпадают. Событие без
  строки в документе краснеет, строка без события краснеет тоже. Без стража документ проживёт до
  первой спешки.
- **Наполнение:** белый список событий `plans/78` Ш4 переезжает сюда и перестаёт жить в плане.

## Границы этой разведки

Прибор `logEvent(` в `public/scripts/app.js` архива не встречается ни разу — 1.x звал аналитику
другим способом, и я его не разбирал: заказ владельца был про ДОКУМЕНТАЦИЮ, а не про способ
отправки. Наш способ отправки задан выбором инструмента (интервью №054) и планом внедрения.
Файл архива в дерево проекта не копировался; клон лежит в скретчпаде сессии и умрёт вместе с ней.
