# Исследование 44 — Команда разработки из ИИ-агентов на git worktree: обзор индустрии и разведка машины

> **Создан:** 2026-08-21 · **Родитель:** `ideas/40` (заказ владельца, его рукой) ·
> **Статус:** ✅ разведка закрыта 2026-08-21 — обзор индустрии + официальная документация
> Claude Code + локальные замеры этой машины · **Исходящее:** метаплан эпика `plans/66`

**Вопрос исследования:** как организовать параллельную работу нескольких ИИ-агентов над одним
репозиторием — ролями, в отдельных git worktree, в отдельных окнах VS Code, со связью через
сообщения, — чтобы это работало на ЭТОЙ машине и не ломало ни канон KAIF, ни продукт.

---

## §1. Индустрия: worktree — стандартный ответ на параллельных агентов

Практика «один агент — один worktree» в 2025–2026 стала отраслевым стандартом параллельной
ИИ-разработки; это не наша выдумка, а зрелый приём.

- **Что решает.** Несколько сессий в одном каталоге затаптывают друг друга: одна переписывает
  файл, пока другая его правит; тесты падают от чужого состояния; контекст засоряется чужой
  работой. Worktree даёт каждому агенту свой каталог со своей веткой при ОБЩЕЙ истории git —
  изоляция файлов без копирования репозитория.
  Источники: [MindStudio — Run Multiple Claude Code Sessions in Parallel With Git
  Worktrees](https://www.mindstudio.ai/blog/claude-code-git-worktree-parallel-branches),
  [Nimbalyst — Git Worktrees for AI Coding Agents: Full
  Guide](https://nimbalyst.com/blog/git-worktrees-for-ai-coding-agents-complete-guide/),
  [Dan Does Code — Parallel Vibe Coding](https://www.dandoescode.com/blog/parallel-vibe-coding-with-git-worktrees).
- **Масштаб, проверенный полем:** к середине 2026 команды стабильно держат **4–8 параллельных
  worktree на одного человека**; дальше узким местом становится не агент, а РЕВЬЮ их работы
  ([Claude Directory — Worktrees Guide
  2026](https://www.claudedirectory.org/blog/claude-code-worktrees-guide)). Наши 6 ролей — внутри
  проверенного диапазона, и наш ответ на узкое место ревью встроен в саму идею: роли QA и
  Менеджера.
- **Известные грабли индустрии** (совпадают с нашими замерами §4): каждому worktree нужны свои
  зависимости и свои порты; ресурсы-синглтоны машины (эмуляторы, БД, докер) агенты обязаны
  делить явно, а не «как получится».

**Вывод для нас:** архитектура идеи владельца — ролевые worktree + отдельные окна VS Code —
ложится точно на отраслевой стандарт. Изобретать нечего, надо аккуратно развернуть.

## §2. Индустрия: оркестратор-и-исполнители — проверенная топология команды

Anthropic публично разобрала собственную многоагентную систему (исследовательскую): паттерн
**orchestrator–workers** — ведущий агент планирует, декомпозирует и раздаёт задачи, исполнители
работают параллельно, каждый со своим контекстом
([Anthropic — How we built our multi-agent research
system](https://www.anthropic.com/engineering/multi-agent-research-system)).

Правила постановки задач из той же публикации (они лягут прямо в манифест команды):

- у каждой задачи исполнителю — **цель, формат результата, границы** («clear task boundaries»);
  размытая постановка = дубли и дыры между исполнителями;
- **масштабируй усилие под задачу**: простой факт — один агент; сложная работа — несколько с
  явно разделёнными зонами;
- **план живёт в памяти вне контекста** (у нас это и есть документы KAIF: планы, STATUS);
- **checkpoint'ы и устойчивость к сбоям**: агент может умереть посреди работы — прогресс
  фиксируется инкрементально (у нас: частые коммиты в ветке роли).

Вторая публикация Anthropic — «когда многоагентность НЕ нужна»
([When to use multi-agent systems](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them)) —
даёт три честных критерия пользы: **изоляция контекста** (чужой шум не деградирует работу),
**параллелизм** (задачи независимы), **специализация** (узкий набор инструментов и правил на
роль). И честную цену: многоагентная работа тратит **в 3–10 раз больше токенов** и добавляет
координационные издержки; «telephone game» — потеря информации при передаче — главный риск
разрезания по этапам (план → код → тест). Их полевое лекарство — **выделенный проверяющий агент**
(verification subagent) с минимальной передачей контекста: критерии приёмки + артефакт. Это
дословно роль нашего QA, а правило «You MUST run the complete test suite» — наш канон стражей.

**Вывод для нас:** топология идеи (Менеджер = оркестратор, QA = выделенный проверяющий,
разработчики = исполнители с границами задач) совпадает с проверенной. Цену (токены,
координация) владелец принял самой идеей; манифест обязан снижать её правилами постановки задач.

## §3. Транспорт связи: cross-session messaging Claude Code — НАТИВНЫЙ и уже работает здесь

Официальная документация — [Message your other Claude Code
sessions](https://code.claude.com/docs/en/cross-session-messaging). Факты, на которых строим:

| Факт | Значение для команды |
|---|---|
| Требование: Windows ≥ v2.1.234 | ✅ у нас 2.1.238 (`env: claude-code-2.1.238-win32-x64`) |
| Инструменты `ListAgents` + `SendMessage`, транспорт — именованный pipe на этой машине, БЕЗ серверов Anthropic | связь мгновенная и локальная; секреты через неё не ходят |
| **Имя сессии задаётся**: команда `/rename` или флаг `claude --name <имя>`; по умолчанию — из имени каталога (`ndim-82`) | 🔑 роли получают ФИКСИРОВАННЫЕ имена-адреса: владелец открывает окно роли, сессия называет себя по манифесту |
| Занятое имя → вариант имени у второго | имена ролей уникальны по построению (одна роль — одно окно) |
| `@`-упоминание сессии в промпте (≥2.1.232) | владелец может адресовать Менеджера из любого окна |
| Сообщение — только текст (≈1 МБ), НИКОГДА файлы/история | артефакты едут через git-ветки и файлы; сообщения — координация |
| Доставка: между tool-вызовами; очередь у занятой сессии; анти-шторм (лимит всплеска, дедуп повторов, потолок очереди 50) | какофония глушится и механикой, не только манифестом |
| `notify_when_idle` (≥2.1.236, обе стороны) — одноразовое «скажи, когда освободишься» | Менеджер подписывается на занятого исполнителя вместо опроса |
| Входящие: `crossSessionInbound` accept/hold/refuse; при умолчании сессии, СПРАШИВАЮЩИЕ разрешения, доставляют друг другу сразу | если все окна команды в обычном интерактивном режиме — сообщения ходят без диалогов одобрения |
| Сообщение не может ничего одобрить, не исполняет команды, разрешения получателя действуют | чужая сессия не обходит права — безопасно по построению |
| **Замер этой машины 2026-08-21:** `ListAgents` из этой сессии видит 4 живые сессии (`ndim-82`, `ndim-bb`, `ndim-6c`, `kumm-d2`) | транспорт РАБОТАЕТ на этой машине уже сейчас, не «должен заработать» |

⚠️ Пресса писала «macOS и Linux» ([MacRumors](https://www.macrumors.com/2026/08/08/claude-code-adds-cross-session-messaging/)) —
это устарело для нативного Windows; официальный док и наш живой замер выше решают вопрос
(наблюдение вместо цитаты прессы).

**Альтернатива, рассмотренная и отклонённая:** нативные «agent teams» Claude Code (одна сессия
порождает и супервизирует команду). Отклонена самой постановкой владельца: он хочет **сам
открыть окно VS Code каждой роли** и видеть каждую сессию отдельно; cross-session messaging —
ровно этот случай по документации («Coordinate parallel worktrees»).

## §4. Разведка машины: что здесь уже есть и что уже оплачено

- **Worktree уже применялись** в этом проекте (судейские прогоны, партии кандидатов —
  `.claude/worktrees/candidates-batch2` в STATUS). Уроки оплачены:
  - 🔴 **`EXP-0175`**: `node_modules` подцеплялись в worktree junction-ссылками; `git worktree
    remove --force` и `Remove-Item -Recurse` идут СКВОЗЬ junction и съедают настоящий
    `node_modules` главной копии. Уборка: сначала `cmd /c rmdir "<wt>\node_modules"`, потом
    удаление. Скрипт рабочих мест обязан нести это в себе.
  - **`EXP-0176`**: исполнителю ставится ВЕСЬ конвейер до продукта; посылка «у тебя нет
    доступа» проверяется пробой, а не объявляется.
  - **`EXP-0131`**: на этой машине живут ЧУЖИЕ агентские процессы (соседние проекты). Гасить —
    только по своему документу/пути, порты страниц вычитки — фиксированные.
- **Ресурсы-синглтоны машины** (двум worktree одновременно НЕ достанутся):
  - эмуляторы стенда: Firestore **8181**, Auth **9099**, Storage **9199** (порты фиксированы
    конфигом; 8080 занят `llama-swap`);
  - `vite preview` для e2e и стражей по собранному сайту: **4173 --strictPort**;
  - Docker-контейнеры `ndim-server-prod` / `ndim-server-stage` — боевые, трогает только
    Менеджер по канону выката;
  - боевая и стейдж базы — пишущие прогоны по ним и так под AUTH-правилами канона;
  - `vite dev` 5173 — уступчив (второй уедет на 5174), но стендовые приборы ждут его на 5173.
  **Вывод:** нужен явный ЗАМОК на «тяжёлые прогоны» (стенд + e2e + verify-* с портами) — один
  на машину; остальное параллелится свободно (юниты `npm test`, `check`, `typecheck`, сборка
  `npm run build` — в каждом worktree свои).
- **`node_modules` в worktree:** junction (быстро, но опасная уборка и общее состояние пакетов)
  против `npm ci` на worktree (изоляция; диск ~ несколько сотен МБ × 4; `prepare` сам гонит
  `svelte-kit sync`). Для ПОСТОЯННЫХ рабочих мест ролей верен `npm ci` — изоляция дороже диска;
  junction остаётся приёмом коротких судейских worktree (как в EXP-0175, с его уборкой).
- **Хуки проекта едут в каждый worktree** — `.claude/settings.json` отслеживается git: страж
  выката (`deploy-guard`), таймер свежести, страж STATUS работают у всех ролей автоматически.
- **Вера-строка** ставится прибором `tools/stamp-creed.mjs` из ОДНОГО источника — новые
  канон-документы команды добавляются в его список `DOCS`, не набираются руками.
- **Общая доска = главная копия.** Все worktree живут на одной машине, путь главной копии
  известен и постоянен: `D:\work\ai_sandbox\ndim`. Файл статуса команды лежит ТАМ и правится
  всеми ролями по абсолютному пути (иначе каждая роль писала бы статус в своей ветке, и таблицу
  никто бы не собрал). Гонки записи гасятся инструментом строки (см. метаплан).

## §5. Столкновения с действующим каноном — названы, не спрятаны

1. **«Работаем только в `main`, без feature-веток»** (`AGENT_GUIDE.md` → Git-процесс). Команда
   вводит ветки ролей/задач — это ПРАВКА КАНОНА, легитимная словом владельца в `ideas/40`
   («Отдельная роль работает в своей ветке worktree», «Менеджер мержит работы своих подопечных
   в main»). Канон получит врезку: соло-сессии — по-старому в `main`; командный режим — ветки
   через Менеджера.
2. **«Место вопросов — interviews/»** остаётся: подопечный НЕ пишет интервью владельцу сам, а
   просит Менеджера (слово идеи); Менеджер оформляет интервью по канону. Форма вопроса —
   класс-правило №043 — действует для Менеджера как и раньше.
3. **Выкат, боевая база, ключи** — не меняются: единственная дверь `npm run deploy` из главной
   копии; исполнители в бою ничего не трогают.
4. **STATUS.md проекта** остаётся главной эстафетой МЕЖДУ сессиями во времени;
   `NDIM_WORKTREE_DEV_TEAM_STATUS.md` — синхронизация ролей В МОМЕНТЕ. Разные вопросы, разные
   документы; манифест проведёт границу, чтобы они не дублировались.
