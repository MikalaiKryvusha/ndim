## 3. Главное: доступ выдаёт КОНСОЛЬ, а не облако

Это единственный узел, в котором легко ошибиться, и ошибка стоит дня блуждания по IAM.

Роли Google Cloud к данным Search Console **отношения не имеют**. Требование сформулировано на
странице предусловий API дословно: «*Your account must have the appropriate Search Console
permission on a given property in order to call that method on that property*». То есть API пускает
того, кто числится **пользователем ресурса в самой Search Console**, — а добавить туда адрес может
только человек с правами владельца ресурса.

Сервисный аккаунт добавляется как обычный пользователь по своей почте. Google документирует ровно
эту процедуру в требованиях Indexing API: «*In the Verified owner list, click Add an owner. Provide
your service account email as the delegated owner*», и адрес брать из поля `client_email` ключа.

**Три условия доступа, и только одно из них может выполнить агент:**

| # | Условие | Кто может |
|---|---|---|
| 1 | `searchconsole.googleapis.com` включён в проекте | ✅ агент — сделано |
| 2 | ключ аккаунта лежит в `.env` | ✅ агент — сделано |
| 3 | **адрес аккаунта добавлен пользователем ресурса в Search Console** | 🔴 **только владелец** |

**Области доступа** (`OAuth scopes`), их всего две:

- `https://www.googleapis.com/auth/webmasters.readonly` — чтение. **Берём эту.**
- `https://www.googleapis.com/auth/webmasters` — чтение и запись (нужна только для подачи карты
  сайта через API; миссии не нужна, и лишнее право здесь — лишний риск).

⛔ **Доменное делегирование Workspace НЕ нужно** и не имеет к нашему случаю касательства: оно про
подмену личности сотрудника внутри организации. У нас личный аккаунт `kotkrinik@gmail.com`.

## 5. Что API отдаёт — четыре ресурса

| Ресурс | Метод | Что даёт |
|---|---|---|
| **Search Analytics** | `searchanalytics.query` | клики, показы, CTR, средняя позиция |
| **Sitemaps** | `list`, `get`, `submit`, `delete` | список карт, когда прочитана, сколько адресов принято |
| **Sites** | `list`, `get`, `add`, `delete` | какие ресурсы видны аккаунту и с каким уровнем доступа |
| **URL Inspection** | `urlInspection.index.inspect` | состояние ОДНОГО адреса в индексе |

Подробности `searchanalytics.query`, снятые с документации:

- **Измерения:** `query`, `page`, `country`, `device`, `searchAppearance`, `date`, `hour`.
- **Величины:** клики, показы, CTR (0…1), средняя позиция.
- **Строк за запрос:** «*Valid range is 1–25,000; Default is 1,000*».
- **Свежесть:** `dataState: all` включает предварительные данные, `final` (или пропуск) — только
  окончательные.

## 6. 🔴 Находка, меняющая постановку миссии: покрытия в API НЕТ

`ideas/37` называет среди снимаемого «*покрытие (проиндексировано / исключено и почему)*». Такого
метода в API **не существует**: отчёт «Индексирование страниц» наружу не отдаётся ни целиком, ни
постранично. Единственный машинный путь к состоянию индекса — `urlInspection.index.inspect`, и он
работает **по одному адресу за вызов** под квотой **2000 в сутки на ресурс**.

**Арифметика, которую обязан знать проектировщик миссии:** публичных страниц у нас **10 222**.
Полный обход инспекцией = `10 222 / 2000` ≈ **6 суток непрерывной работы**, и это при том, что
квота одна на весь ресурс и её же захотят другие приборы.

**Отсюда следствие для эпика:** «здоровье индексации» снимается **выборкой**, а не целиком, и
выборку надо проектировать честно — по видам страниц (карточка каталога, хаб, страница «Тест»,
документ, лендинг) и по языкам, с фиксированным составом, чтобы ряд снимков сравнивался сам с
собой. Случайная выборка каждый раз давала бы дребезг вместо динамики.

⚠️ **Indexing API это НЕ лечит.** Он существует только для вакансий и прямых трансляций и на
обычные страницы не распространяется — включать его незачем.

## 8. Глубина истории — 16 месяцев, и это довод срочности

Search Console хранит данные эффективности **за последние 16 месяцев** и прошлое не восстанавливает;
данные становятся доступны примерно **через 48 часов** после сбора. Значит:

- всё, что старше 16 месяцев, **исчезает навсегда** — и каждый день ожидания это ещё один день,
  который через 16 месяцев пропадёт;
- «сегодняшних» чисел в консоли не бывает: окно наблюдения всегда отстаёт на двое суток, и прибор
  обязан это учитывать (иначе последние дни всегда будут выглядеть провалом);
- фаза 8 эпика каталога требует **≥3 датированных замеров** — без прибора принять каталог нечем.

## 12. Второй путь, который важнее первого: выгрузка в BigQuery

У Search Console есть массовая выгрузка данных: она **каждый день сама пишет выдачу в BigQuery**, и
там она лежит без срока. Это прямой ответ на §8 — часы, которые сейчас тикают против нас.

**Что нужно:**

1. Выдать аккаунту Google `search-console-data-export@system.gserviceaccount.com` две роли в проекте:
   `roles/bigquery.jobUser` и `roles/bigquery.dataEditor`.
2. В консоли: Настройки → Массовый экспорт данных → проект `ndim-space`, набор `searchconsole`,
   расположение набора.

**Что появляется** — три таблицы: `searchdata_site_impression` (эффективность по ресурсу),
`searchdata_url_impression` (по адресам, с полями анонимизации и типа появления в выдаче),
`ExportLog` (журнал успешных выгрузок).

**Чего выгрузка НЕ даёт:** покрытия в ней тоже нет — только эффективность. Дыра §6 остаётся дырой,
и закрывается она только инспекцией по выборке.

🔴 **Порядок важен, и он не косметика: выгрузку включать ПЕРВОЙ.** Прошлые 16 месяцев API отдаст в
любой момент, пока они не состарились, — а вот суточная детализация с сегодняшнего дня копится
только у того, кто выгрузку уже включил.

⚠️ **Что я НЕ подтвердил первоисточником:** выгружает ли экспорт задним числом. Прочитанная
документация про это молчит. **Проверить наблюдением** через сутки после включения:
`SELECT MIN(data_date) FROM searchconsole.searchdata_site_impression` — если минимальная дата равна
дню включения, значит задним числом не выгружает, и §8 остаётся в силе целиком.

Цена: место в BigQuery платное. При наших числах (94 человека, показов единицы) это единицы
мегабайт в сутки — но строка расхода появляется, и владелец о ней предупреждён.

### 🔴 Находка 1: «в индексе одна страница» — больше не правда

`STATUS.md` носил число замера от 2026-08-03: «в индексе Google была ровно ОДНА страница».
Машина говорит: показы получают **250 страниц**, из них 249 — карточки каталога, на **221
различном запросе**. Каталог проиндексирован и уже приносит показы на обоих языках.

⚠️ **Как этим числом НЕ пользоваться.** «250 страниц с показами» — это не «250 страниц в индексе»:
страница может быть в индексе и не получить ни одного показа. Замер меряет **показы**, а не
покрытие, и покрытия API не отдаёт вовсе (§6). Число — нижняя граница проиндексированного, и в
этом качестве оно и ценно.

### 🔴 Находка 2: спрос информационный — и это про СПРОС, а не про наш текст

Запросы, по которым нас показывают: `10 things i hate about you plot` · `a fistful of dollars wiki` ·
`another round movie language` · `bad genius 2024 age rating` · `леди баг лондон на краю времени`.
То есть люди приходят не за знакомствами, а с вопросом об объекте культуры. Это ценное знание о
спросе, и оно смыкается с поводом прийти, названным владельцем: «*Хочешь найти хороший фильм на
вечер? — приходи в NDim Space посмотреть рейтинги*».

⛔ **И ЗДЕСЬ ЖЕ ЗАПИСАНА ОШИБКА ВЫВОДА, ЧТОБЫ ЕЁ НЕ ПОВТОРИЛИ.** Первая редакция этого параграфа
читала список запросов как улику против наших текстов: «запросы википедийные → значит наши описания
прилипли к Википедии». **Вывод неверен, и поправил его владелец** (2026-08-17): «*у нас и после
вычистки будет — это названия*».

Он прав арифметически. Запрос `10 things i hate about you plot` — это **имя объекта плюс слово
«plot»**. Люди будут набирать его и после вычистки, потому что запрос описывает ПРЕДМЕТ каталога, а
не нашу прозу. Список запросов меряет **спрос**, и о нашем тексте не свидетельствует вовсе.

🔑 **Класс ошибки назван в каноне заранее** (`AGENT_GUIDE.md` → «Сборка», обобщение `EXP-0136`): «*у
каждого класса дефектов есть свой прибор… подменять одно другим — значит держать целый класс без
охраны*». Прибор для вопроса «прилип ли наш текст к Википедии» у проекта **уже есть** —
`tools/measure-wikipedia-overlap.mjs`, он меряет самый длинный дословный ряд. Я подменил его списком
запросов и получил вывод, которого этот список не несёт.

⚠️ **И вторая поправка владельца, тоже принятая:** данные могут отставать. «*гугл ведь медленно
раскачивается*». Окно замера — 16 месяцев целиком, правки в бой ещё не выкачены, а перекраул 10 222
страниц занимает недели. Плюс сами числа малы: 469 показов на 250 страницах и 221 запросе — средняя
позиция здесь дребезжит от единичных показов. `ideas/37` предупреждала об этом дословно: «*на таких
величинах любая „динамика“ — это чаще всего дребезг, и критерии гипотез обязаны это учитывать, иначе
агент начнёт „объяснять“ случайность*». Предупреждение было написано ДО замера, и я его нарушил.

### ⛔ Стоячее правило: откат к тексту Википедии запрещён, и числа его не отменяют

Слово владельца 2026-08-17: «*Я НЕ ДУМАЮ, что нужно твои правки откатывать обратно к википедии*».

Правило названо **до** замера «после», чтобы опровержение не превратилось в торг. Три причины, и ни
одна не зависит от позиции в выдаче:

1. **Лицензия.** Текст Википедии — CC BY-SA; дословная копия без указания источника и без сохранения
   лицензии её нарушает. Это верно при любом числе.
2. **`GOAL.md`.** Описание, являющееся чужим текстом, — не голос нашего продукта.
3. **Это заказ владельца**, и принимался он не по числам.

Если позиция после публикации ухудшится — это разрешает **другую** работу (текст лучше и больше,
перелинковка, поиск настоящей причины), но возврат копии не разрешает никогда. Правило продублировано
в шапке `tools/rewrite-catalog-descriptions.mjs` — там, где лежат файлы откатов и куда пойдёт тот,
кто решит откатывать.

### 🔴🔴 ПОРОГ ВЫВОДОВ НАЗНАЧЕН ВЛАДЕЛЬЦЕМ 2026-08-17 — читать до любого анализа консолей

`ideas/37` ставила вопросом «как отличать сигнал от шума». Владелец ответил порогом, дословно:

> «*когда наше приложение месяц уже будет в поиске, и когда у нас будет аудитория в месяц хотя бы
> человек 100 — вот тогда можно будет выводы делать из гугловской аналитики по психологии и
> поведению, и как нас находят или не находят*»
>
> «*пока наша задача — зацепиться за популярные кейворды и активно органический трафик привлекать
> из поисковиков*»

🔴 **И СРАЗУ ГЛАВНОЕ УТОЧНЕНИЕ ВЛАДЕЛЬЦА, без которого правило будет прочитано неверно.** Первая
редакция этого параграфа записала его слова как точный шлюз («месяц И 100 человек»). Он поправил
дословно: «*мой порог — условный, не точная цифра, а образ мышления — не доверять наслово гуглу на
раннем этапе жизни приложения*».

**Значит правило — НЕ арифметическое.** «Месяц» и «сотня человек» называют ПОРЯДОК величины, при
котором данные начинают что-то значить, а не рубеж, который считают и объявляют пройденным.
⛔ Не писать страж «аудитория ≥ 100 → можно делать выводы»: это ровно та подмена, от которой
владелец предостерегает — доверие к числу вместо суждения о его зрелости.

**Что действует вместо шлюза:** на раннем этапе данные консолей читаются как **инженерные** факты и
НЕ читаются как факты о людях.

🔑 **Что порог означает практически, а не как лозунг.** До него консоли снимаются, но читаются
только как **инженерные** факты: индексируется ли страница, прочитана ли карта сайта, есть ли ошибки
обхода. Всё, что требует объяснения ПОВЕДЕНИЯ людей — почему кликают, что ищут, чего им не хватает, —
ждёт порога. Ровно это правило я и нарушил час назад, объяснив позицию 56,5 через качество наших
текстов при 469 показах.

⏭ **И задача, названная взамен:** зацепиться за популярные ключевые слова и активно тянуть
органический трафик. То есть работа сейчас — **на стороне предложения** (поверхности, тексты,
ключи), а не на стороне анализа поведения. Территория — `researches/34` (семантическое ядро) и
`plans/34` (ядро притока), а не отчёты миссии.

### Что базовая линия всё-таки даёт

Замер снят **до выката** (правки в базе с утра, сайт отдаёт старый текст), и это по-прежнему полезно —
но как база сравнения, а не как доказательство гипотезы. Честная мера будущего сравнения: сдвиг
позиции **по тем же страницам**, при **достаточном числе показов** и **после подтверждённого
перекраула** (дата чтения карты сайта плюс инспекция выборки). Без всех трёх условий сравнение
измерит шум.

### 🔴 Находка 3: поле «проиндексировано» у карты сайта врёт нулём

API карты сайта отдаёт `submitted: 10252` и `indexed: 0`. **Ноль здесь не факт о мире.** Он
противоречит собственным данным того же API: 250 страниц получают показы, а непроиндексированная
страница показов не получает. Поле давно не заполняется — читать его как покрытие нельзя, и прибор
миссии обязан либо не показывать его вовсе, либо подписывать «поле не заполняется».

### ⚠️ Поправка к моему же доводу о срочности

Я подавал 16 месяцев как тающий архив. Замер это уточняет: история сайта в поиске начинается
**2026-07-14** — ей около месяца, и состариться пока нечему. **Выгрузка защищает будущее, а не
спасает прошлое.** Действие остаётся тем же (включать раньше — правильно), но довод честнее
звучит так: она страхует от потери с этого дня, а не вытаскивает утраченное.

### Что осталось проверить наблюдением

- ⏳ **Выгружает ли экспорт задним числом** — таблицы приедут в течение суток. Прогнать
  `SELECT MIN(data_date) FROM searchconsole.searchdata_site_impression`: равно дню включения —
  значит задним числом не выгружает.
- ⏳ **Уровень `siteFullUser` и инспекция адресов** — хватает ли его для `urlInspection`,
  не проверялось (§13).
