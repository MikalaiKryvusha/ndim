## 2. Где ключ рождается — регистрация, и только она

`public/scripts/app.js:8608–8613` — единственное место записи, внутри обработчика регистрации:

```js
// создаем privat документ пользователя в Firestore при регистрации
const userPublicFirestoreDocRef = await setDoc(doc(db, "users", user.uid, "privat", user.uid), {
  uid: user.uid,
  user_secret_key: generateUserSecretKey(),
  privat_data: {}
});
```

То есть документ заводится каждому зарегистрировавшемуся, один к одному, с именем документа,
равным `uid`. Это объясняет и форму пути `users/{uid}/privat/{uid}`, которая иначе выглядит
странно.

### Генератор — `app.js:308–331`

```js
// генератор секретного ключа пользователя для доступа к API
function generateUserSecretKey() {
  let key_letters = "ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789";
  let key_length = 30;
  ...
  var time_hash = Date.now().toString(36);
  key_length -= time_hash.length;
  for (var i = 0; i < key_length; i++) {
    base_key += key_letters.charAt(Math.floor(Math.random() * key_letters.length));
  }
  full_key = base_key + time_hash;
```

🔑 **Комментарий автора называет назначение прямым текстом: «для доступа к API».** Это не догадка
разведки — это строка в коде.

Устройство ключа, названное честно: 30 знаков, из них ~22 случайных из алфавита в 62 знака плюс
8-значный хеш времени в base36. Случайность берётся из `Math.random()` — генератора, который не
предназначен для секретов (состояние PRNG движка восстановимо), а хвост времени предсказуем в
принципе. **Оговорка, без которой это утверждение было бы пугалкой:** качество ключа не имеет
последствий, потому что предъявлять его некому — см. раздел 3.

## 3. 🔑 Кто ключ ПРОВЕРЯЕТ — никто, и API не существует

Это главный ответ разведки, и он получен исчерпывающим поиском, а не выборочным.

**Замер:** упоминания `secret_key` во всём дереве 1.x, кроме артефактов сборки и `node_modules`,
живут ровно в **трёх** файлах:

| Файл | Что там |
|---|---|
| `firestore.rules` | правила доступа к самому документу (раздел 5) |
| `public/scripts/app.js` | запись при регистрации · дозаполнение · чтение админской кнопкой |
| `public/index.html` | одна строка — кнопка `check_users_for_secret_key_button` в админке |

**Серверной части, которая могла бы ключ принять, в 1.x нет вовсе.** Каталоги верхнего уровня
архива: `.github` · `NDim_Space` (файлы лазерной гравировки) · `merch` · `my-pwa` (обёртка
Android) · `public` (само приложение) · `scripts` (три сборочных скрипта: хеширование статики,
восстановление дев-ссылок, версия) · `storage` · `working_docs`. Ни `functions/`, ни `api/`, ни
любого другого бэкенда.

**Единственный читатель — админская диагностика** (`app.js:10918–10941`): она собирает по всем
`ndimids` строку о каждом человеке и рисует её в `div`:

```js
let user_secret_key = "no_key";
...
  user_secret_key = privatSnap.data()?.user_secret_key || "no_key";
...
const userData = { status, email, lang, name, dims, uid, secret_key: user_secret_key };
```

Ключ здесь не проверяется и никуда не отправляется — он **показывается администратору списком**.
Это инвентаризация, а не аутентификация.

> ### Вывод раздела
> `user_secret_key` — **выданный, но никогда не предъявленный пропуск**. Механизм, ради которого
> его выдавали, в 1.x не был написан: API, который принимал бы этот ключ, не существует ни в
> одной строке архива. Ключ не «мёртв» в смысле «когда-то работал и перестал» — он **не начинал
> работать ни разу**.

## 4. И это подтверждает сам автор — дважды, в правилах

`firestore.rules` версии 1.x, блок `privat`, комментарии владельца:

```
// пока что этот документ не используется
allow read: if ...

// пока что этот документ не используется
allow update: if ...
```

и там же, в правиле записи, честная заглушка:

```
&& (request.resource.data.privat_data.keys().hasOnly([])) // временная заглушка, чтобы ничего не писать в приватные данные
```

🔑 **Это снимает главную неопределённость `bugs/127`** («никто в 2.0 не знает, что этот ключ
означает, кто его выдал и что он открывает»). Ответ: выдал автор, при регистрации, под будущий
API — и сам пометил документ как ещё не используемый. Пласт не забыт, он **заготовлен впрок**.

## 5. Права доступа: 1.x против 2.0 — сравнение, а не тревога

| | 1.x | 2.0 (сегодня) |
|---|---|---|
| Документ описан правилами | **да**, отдельным блоком с проверкой полей | **нет** |
| Кто мог прочитать | сам человек (`uid` + подтверждённая почта) **и** две захардкоженные почты владельца | **никто из клиентов** |
| Чем закрыт | явным правилом | финальным `match /{document=**} { allow read, write: if false; }` |
| Описан в схеме проекта | — (схемы как документа в 1.x не было) | **нет** в `src/lib/model/schema.ts` |

**Вывод, который важно не переврать:** 2.0 закрывает эти данные СТРОЖЕ, чем 1.x, — регресса
приватности нет, и утечки нет. Расхождение в другом: **строгость получена умолчанием, а не
решением.** Правила не называют пласт, схема о нём не знает, и потому ни один страж не заметит,
если завтра кто-то напишет для `users/{uid}/**` правило пошире и заодно откроет то, о чём не
помнил. Это дефект вида «одна нога инварианта» — тот самый класс, на который владелец указал в
№059 В3.

## 6. Что происходит с пластом при удалении аккаунта в 2.0 — и здесь есть настоящая находка

**Клиентское удаление `src/lib/data/erase.ts` подколлекцию `privat` НЕ трогает.** Шаг 2 функции
`eraseAccount` перечисляет подколлекции поимённо (`erase.ts:106–118`): `groups/*/members` ·
`groups` · `profile` · `audience` · `points/{uid}/dims`. `privat` в списке нет — и не могло быть,
её не знает ни схема, ни разработчик. Комментарий там же честно предупреждает о механике:

> «Шаг 2 — подколлекции. **Firestore не удаляет их вместе с документом.**»

То есть после клиентского удаления `users/{uid}` исчезает, а `users/{uid}/privat/{uid}` остаётся
висеть под несуществующим документом.

⚠️ **НО СЕТЬ БЕЗОПАСНОСТИ СУЩЕСТВУЕТ, и не назвать её значило бы поднять ложную тревогу.**
Сервер синхронизации, проход `cleanupDeletedPeople` (`sync-server/index.mjs:1046–1062`), опознаёт
ушедшего человека по признаку «`relations/{uid}` есть, а `points/{uid}` нет» и делает:

```js
await db.recursiveDelete(db.doc(`users/${uid}`));
```

`recursiveDelete` Admin SDK **сносит подколлекции вместе с документом** — то есть `privat` он
заберёт.

🔑 **Где остаётся щель, названная точно.** Уборщик находит человека ТОЛЬКО по живому
`relations/{uid}`. Человек, у которого документа связей нет (ни одной синхронизации не
случилось), в выборку `gone` не попадает вовсе — и его `privat/{uid}` с ключом и полем `uid`
остаётся в базе навсегда, уже недостижимый ни для одного из уборщиков, потому что оба ищут по
следам, которых больше нет.

📏 **Насколько это вероятно — честно: НЕ ЗАМЕРЕНО.** 331 документ принадлежит когорте 1.x, а
1.x связи считал, поэтому `relations` у них скорее всего есть у всех. Но «скорее всего» — это
утверждение о моих ожиданиях, а не о базе. Замер назван в разделе 8: он дешёвый и его надо
сделать до любого решения.

## 9. Предложение — три варианта, с ценой и рекомендацией

Решение о боевых данных принимает владелец; ниже — материал для его решения.

### Вариант А (рекомендую) — снять пласт целиком

Удалить `users/{uid}/privat/{uid}` у всех, кого покажет замер 1.

**Довод:** ключ никогда не был предъявлен ни одному потребителю — API не существует ни в одной
строке 1.x (раздел 3), и автор сам пометил документ как неиспользуемый (раздел 4). Пока пласт
жив, каждая копия базы, каждая выгрузка и каждый бэкап копируют 331 неизвестный секрет и 331
лишний носитель `uid`. Ничего не ломается: читателя нет.

**Цена:** ~331 удаление (разово, копейки). **Необратимость** — настоящая, поэтому нужен слепок до
удаления. **Риск «а вдруг пригодится»** — нулевой в том смысле, который важен: ключи случайные,
ни у кого на руках их нет (предъявлять было некуда), и будущий API 2.0 выдаст свои по своему
канону, а не унаследует эти.

### Вариант Б — оставить, но описать вслух

Явное правило `deny` для `users/{uid}/privat/{document=**}` в `firestore.rules` + строка в
`schema.ts` + случай в `tests/rules/`.

**Довод:** строгость перестаёт быть умолчанием и становится решением (лечит раздел 5).
**Цена:** пласт секретов остаётся в базе навсегда, а вместе с ним долг «никто не знает, что это».
Лечит симптом «правила молчат», не лечит «секрет без хозяина».

### Вариант В — оставить документ, снять поле

Удалить только `user_secret_key`, документ с пустым `privat_data` оставить.

**Довод:** секретов в базе не остаётся, форма пласта сохраняется.
**Цена:** худшее из двух — данные всё ещё вне схемы и правил, но уже и не те, что были.
Не рекомендую: это половина А по цене А.

### 🔴 Что делать в ЛЮБОМ из трёх вариантов

1. **Закрыть щель раздела 6** — включить `privat` в `eraseAccount`, если пласт остаётся жить хоть
   один день (при варианте А — не нужно: удалять будет нечего).
2. **Датированная поправка в `researches/02`.** Там стоит «`privat` — приватные данные. **Не
   используется** (заглушка)» и «мёртвая подколлекция-заглушка». По факту замера это **половина
   правды**: заглушка `privat_data` пуста действительно, а ключи живые. Правится датированной
   поправкой в тексте, история не переписывается — тот же порядок, что применён к доводу
   `__data.json` в `researches/55` (решение Менеджера по `bugs/214`, путь 2).
3. **Строка в `bugs/127`** со ссылкой сюда: три вопроса раздела «Что осталось выяснить» закрыты.

## 10. Границы этой разведки — чего я НЕ проверял

- **Боевую базу не читал ни разу** — ключа контура в копии роли нет, и это правильно.
- **Данные не трогал**, правил не выкатывал, кода не писал — порция была разведочной.
- **Не проверял прогоном**, что `recursiveDelete` уносит `privat`: это документированное
  поведение Admin SDK, а не наш код. Проверяется на стенде за минуту и обязано войти в приёмку
  любого варианта.
- **Не искал ключ вне репозитория 1.x** — в бэкапах владельца, в выгрузках, в переписке. Если
  ключи куда-то выгружались, это знание владельца, а не кода.
- **Двоичный `working_docs/app-release.apk`** на поиск отозвался, но это сборка того же
  приложения, а не отдельный потребитель; разбирать её не стал.
