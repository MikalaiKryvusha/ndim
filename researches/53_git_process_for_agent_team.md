## §1. Что говорит индустрия (первоисточники)

1. **Trunk-based development** — [trunkbaseddevelopment.com](https://trunkbaseddevelopment.com/):
   «developers collaborate on code in a single branch called 'trunk' and resist any pressure
   to create other long-lived development branches». Вариант для команд: «short-lived feature
   branches are used for code-review and build checking (CI) … before commits land in the
   trunk» — ветка живёт коротко и умирает при интеграции.
2. **GitHub flow** — [docs.github.com](https://docs.github.com/en/get-started/using-github/github-flow):
   branch → commit → PR → review → resolve → merge → delete branch. Конфликты решает **автор
   PR**, до мержа: «GitHub will tell you if your pull request has conflicts that must be
   resolved before merging». Ворота мержа (branch protection) — одобрения ревьюеров.
3. **DORA** — [dora.dev/capabilities/trunk-based-development](https://dora.dev/capabilities/trunk-based-development/):
   выше делятся команды с **≤3 активными ветками** и **мержем в trunk не реже раза в день**;
   чем дольше ветка живёт без мержа, тем дороже конфликты. Малые порции ревью двигаются
   быстрее и откатываются дешевле.
4. Отдельно про наш случай: конфликты в PR ИИ-агентов — уже предмет исследований
   ([AgenticFlict, arXiv 2604.03551](https://arxiv.org/pdf/2604.03551)) — класс не
   экзотический, а массовый; лечение то же: короткие ветки, частая интеграция.

## §2. Чем наша реальность отличается от учебника

| Особенность | Следствие для процесса |
|---|---|
| Авторы — ИИ-агенты в изолированных worktree, один git | Ветки ролей ПОСТОЯННЫ ПО ИМЕНИ (`ndim_<роль>`), «удалить ветку после мержа» заменяется «сбросить от свежего main» |
| QA — независимый судья, его вердикт обязателен | Ворота PR у нас СТРОЖЕ GitHub flow: вердикт QA — не «approve» коллеги, а прогон с мутациями |
| Push части ролей заперт предохранителем | «PR» бывает двух форм: настоящий GitHub PR (у кого push жив) и заявка сообщением (ветка+голова) |
| Слабые модели в ролях | Конфликт решает автор, но РЕШАЮЩИЕ конфликты (поведение двери, прибора) идут с предписанием QA — как развязка C сегодня |
| Владелец — единственный человек | Никаких релизных веток и gitflow: бой кормится только из main через `npm run deploy` |

## §4. Синтез — правила для манифеста

1. **main = trunk.** Всегда зелёный (юниты, check, typecheck), всегда выкатываемый. В main
   пушит только Менеджер.
2. **Ветка роли — короткоживущая по содержимому.** Сдача порциями размером в один вердикт QA;
   несмерженная работа старше **2 рабочих дней** — сигнал Менеджеру на доску. «Копить смену»
   запрещено — цена замерена (§3).
3. **Обновление — обязанность автора (слово владельца).** Перед заявкой на мерж роль сама
   делает `git merge main` в своей ветке, решает конфликты у себя, приводит юниты/линтер/типы
   к зелёному. Конфликт, меняющий ПОВЕДЕНИЕ чужого решения (прибор, дверь, правило), роль не
   решает молча — эскалация Менеджеру, при споре предписание даёт суд QA.
4. **Заявка на мерж (наш PR).** Форма: ветка · голова · что внутри · чем проверено · вердикт
   QA (номер из журнала). У кого push жив — обычный GitHub PR тем же содержимым; у кого
   заперт — заявка сообщением, пушит Менеджер после Tech Lead-ревью.
5. **Мерж — только Менеджер, только после вердикта QA.** `--no-ff` (след смены виден в
   истории). После мержа Менеджер сбрасывает ветку роли от свежего main и сообщает роли.
6. **Перезапуск ветки на origin** — force-push Менеджера, ШТАТНЫЙ, но только после того, как
   прежняя голова origin спасена веткой `<роль>-shiftN-<дата>` (усвоено 2026-08-28).
7. **Номера документов** — по правилу `NEW_` (уже канон), номер присваивает Менеджер при мерже.

## §5. Что НЕ берём и почему

- **Gitflow** (develop/release/hotfix-ветки) — для непрерывно выкатываемого веб-продукта с
  одним интегратором это чистый оверхед; сам Atlassian зовёт его legacy.
- **Rebase веток ролей на main** — переписывание истории в общем репозитории с force-push
  от слабых моделей; merge даёт тот же результат без рисков.
- **Прямые коммиты ролей в main** (чистый small-team trunk) — ломает ворота QA и Tech
  Lead-ревью; наша цена ошибки в бою выше цены изоляции.
