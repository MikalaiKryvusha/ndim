## 2. Bing Webmaster Tools API

### 2.1 Доступ

Два способа, оба документированы: **OAuth 2.0** и **ключ API**. Для нашей задачи (агент читает
метрики без человека) годится ключ.

> «API key can be generated from Bing Webmaster Tools by following the steps below: … Click on
> **Settings** button on top right corner and then go to **API Access** section. … Click on
> **Generate API Key** to create an API Key. Only one API key can be generated per user.»

🔑 **Ключ выдаётся ПОЛЬЗОВАТЕЛЮ, а не сайту** — дословно: «*the API key is generated for a user
and not a site and hence a user can use the same API key for all their verified sites*». То есть
одного шага владельца хватит на все его сайты сразу, и повторять его при добавлении ресурса не
придётся.

⛔ **Ключ живёт только в `.env`** (канон-правило владельца 2026-08-15). Имя переменной предлагаю
`NDIM_BING_WEBMASTER_KEY` — рядом с `NDIM_CONSOLE_SA_B64`, тем же способом.

Источник: [Getting Access to the Bing Webmaster Tools API](https://learn.microsoft.com/en-us/bingwebmaster/getting-access)

### 2.2 Транспорт

Три протокола: SOAP · POX/HTTP · JSON/HTTP. Нам нужен JSON, и его формат адреса документирован
дословно:

| Протокол | Формат |
|---|---|
| JSON GET | `https://ssl.bing.com/webmaster/api.svc/json/METHOD_NAME?apikey=API_KEY&param1=VALUE&…` |
| JSON POST | `https://ssl.bing.com/webmaster/api.svc/json/METHOD_NAME?apikey=API_KEY` |

Ошибка приходит кодом 400 с телом `{"ErrorCode":3,"Message":"InvalidApiKey"}` — то есть разбирается
машиной без догадок.

Источники: [API Services / протоколы](https://learn.microsoft.com/en-us/bingwebmaster/api-protocols) ·
[Getting Started](https://learn.microsoft.com/en-us/bingwebmaster/getting-started)

### 2.3 Что отдаёт — по нашим нуждам

Разобрано по списку методов интерфейса `IWebmasterApi`. Полезное нам:

| Метод | Что даёт | Зачем нам |
|---|---|---|
| `GetRankAndTrafficStats(siteUrl)` | ряд по датам: `Impressions`, `Clicks` | прямой аналог среза «по дням» Google — вторая независимая линия ряда |
| `GetQueryStats(siteUrl)` | подробная статистика по ТОП-запросам | спрос глазами Bing |
| `GetPageStats(siteUrl)` | подробная статистика по ТОП-страницам | какие карточки каталога живут в Bing |
| `GetQueryPageStats` · `GetPageQueryStats` | пересечение «запрос × страница» | 🔑 у Google этого разреза в одном запросе нет |
| `GetUrlTrafficInfo(siteUrl, url)` | трафик одной страницы | точечная проверка карточки |
| `GetUrlInfo(siteUrl, url)` | **сведения об ИНДЕКСЕ одной страницы** | 🔑 дыра покрытия у Google (`researches/40` §6) здесь частично закрыта |
| `GetChildrenUrlInfo(siteUrl, url, …)` | сведения об индексе по КАТАЛОГУ адресов | покрытие раздела `/en/dimension/…` целиком |
| `GetCrawlStats` · `GetCrawlIssues` | статистика и проблемы обхода | здоровье индексации из заказа |
| `GetKeywordStats` · `GetRelatedKeywords` | историческая статистика ключей и родня | вход в семантику, ср. `tools/bing-keywords.mjs` |
| `GetUrlSubmissionQuota(siteUrl)` | остаток квоты отправки адресов | сколько адресов можно подать в сутки |
| `SubmitUrlBatch(siteUrl, urls)` | подача пачки адресов | ⛔ ПИШУЩИЙ — см. §5 |

🔑 **`GetUrlInfo` и `GetChildrenUrlInfo` — самое ценное здесь, и вот почему.** У Google API
покрытия нет вовсе: он отдаёт только эффективность, а «проиндексировано / исключено и почему»
доступно лишь глазами в панели (`researches/40` §6, дыра названа там честно и осталась дырой).
Bing отдаёт индексные сведения по адресу и по каталогу адресов машинно. То есть **вопрос «сколько
наших 10 222 карточек вообще в индексе» впервые получает машинный ответ — пусть и по индексу Bing,
а не Google.**

Источник: [IWebmasterApi Interface — полный список методов](https://learn.microsoft.com/en-us/dotnet/api/microsoft.bing.webmaster.api.interfaces.iwebmasterapi)

### 2.4 Лимиты

Числовой суточной квоты на ЧТЕНИЕ в документации не названо. Квота есть у ПОДАЧИ адресов, и она
спрашивается у самого API — `GetUrlSubmissionQuota` (и `GetContentSubmissionQuota`). То есть
правильный способ узнать лимит — спросить его прибором, а не искать константу в доке.

### 2.5 🔴 РУБЕЖ 31 АВГУСТА 2026 — ТРИ ДНЯ ОТ СЕГОДНЯ

На странице протоколов (обновлена 2026-08-10) стоит врезка, дословно:

> «Legacy SOAP and POX APIs will be retired on August 31, 2026. Migrate to our REST APIs to avoid
> service disruption.»

**Что это значит для нас практически:** строить надо на JSON/HTTP, а не на SOAP или POX. Все
примеры «как работать с Bing API», которые агент может встретить в вебе и в собственной памяти,
написаны под SOAP (официальный «Getting Started» — целиком про SOAP-клиент в Visual Studio, и его
дата правки 2019 год). **Пойти по первому попавшемуся примеру — значит построить на том, что
умрёт через три дня.**

⚠️ **Чего я НЕ подтвердил первоисточником и что проверяется наблюдением:** является ли
`api.svc/json/` тем самым «REST API», который переживает рубеж. Врезка называет отставку только
SOAP и POX; JSON на той же странице стоит отдельным третьим протоколом со своим форматом адреса —
но прямой строки «JSON остаётся» я не нашёл, а страница-разъяснение отставки
(`bing.com/webmasters/help/soap-pox-api-retirement-s0appox01`) отдаётся без содержания.
**Проверка дешёвая и однозначная: первый же прогон прибора после 31.08 либо отдаст данные, либо
нет.** До тех пор считать это допущением, а не фактом.

## 3. Яндекс.Вебмастер API 4.0

### 3.1 Доступ и токен

Базовый адрес — `https://api.webmaster.yandex.net/v4/`. Авторизация — OAuth-токен Яндекс ID.

Порядок (первоисточник): зарегистрировать приложение на `oauth.yandex.ru/client/new` → платформа
«веб-сервисы», redirect URI `https://oauth.yandex.ru/verification_code` → запросить права
**`webmaster:hostinfo`** и **`webmaster:verify`** → скопировать ClientID → открыть
`https://oauth.yandex.ru/authorize?response_type=token&client_id=<ClientID>` и забрать токен со
страницы.

**Токен действует 6 месяцев** — то есть шаг владельца повторяется дважды в год. Это стоит записать
в домашку: молча протухший токен выглядит как поломка прибора.

⛔ Токен — только в `.env`; имя предлагаю `NDIM_YANDEX_WEBMASTER_TOKEN`.

Все адреса ниже требуют `{user-id}` — он берётся отдельным запросом к `/v4/user/`, и `{host-id}` —
из `/v4/user/{user-id}/hosts/`.

Источник: [Авторизация — API Яндекс Вебмастера](https://yandex.ru/dev/webmaster/doc/ru/tasks/how-to-get-oauth)

### 3.2 Разделы API

Обзор ресурсов называет двенадцать разделов; нам по делу шесть: `hosts` · `search-queries` ·
`indexing` · `search-urls` · `recrawl` · `diagnostics` (плюс `sitemaps` и `links` про запас).

Источник: [Overview of API resources](https://yandex.com/dev/webmaster/doc/en/concepts/getting-started)

### 3.3 Статистика поиска

`GET /v4/user/{user-id}/hosts/{host-id}/search-queries/all/history`

| Параметр | Значения |
|---|---|
| `query_indicator` | `TOTAL_SHOWS` · `TOTAL_CLICKS` · `AVG_SHOW_POSITION` · `AVG_CLICK_POSITION` |
| `device_type_indicator` | `ALL` (умолчание) · `DESKTOP` · `MOBILE_AND_TABLET` · `MOBILE` · `TABLET` |
| `date_from` / `date_to` | без них — последние 7 дней |

Ответ: `{"indicators": {"TOTAL_SHOWS": [{"date": "…", "value": 100.0}, …]}}`.

🔑 **Разрез по устройствам есть и у Яндекса, и он совпадает по смыслу с нашим срезом Google.** Это
важно именно сегодня: снимок 2026-08-28 показал у Google расхождение CTR десктоп/мобильный в 19
раз (0,19 % против 3,62 %). Появится токен — можно спросить, повторяется ли перекос у Яндекса,
то есть свойство это нашей выдачи или наших страниц.

Глубины истории документация не ограничивает явно.

Источники: [Общая статистика по всем запросам](https://yandex.com/dev/webmaster/doc/en/reference/host-search-queries-history-all) ·
[Популярные запросы](https://yandex.com/dev/webmaster/doc/en/reference/host-search-queries-popular)

### 3.4 🔴 УДАЛЁННЫЕ ИЗ ПОИСКА СТРАНИЦЫ — МАШИННЫЙ ОТВЕТ НА СЕГОДНЯШНЕЕ ПИСЬМО

`GET /v4/user/{user-id}/hosts/{host-id}/search-urls/events/samples`

Параметры: `offset` (≥ 0) · `limit` (1…100, умолчание 50). Доступно **до 50 000** адресов.

Поля строки: `url` · `title` · `event_date` · `last_access` · `event` · `excluded_url_status` ·
`bad_http_status` · `target_url`.

**Тип события** (`ApiSearchEventEnum`): `APPEARED_IN_SEARCH` · `REMOVED_FROM_SEARCH`.

**Причина исключения** (`ApiExcludedUrlStatus`) — полный перечень:
`NOTHING_FOUND` · `HOST_ERROR` · `REDIRECT_NOTSEARCHABLE` · `HTTP_ERROR` · `NOT_CANONICAL` ·
`NOT_MAIN_MIRROR` · `PARSER_ERROR` · `ROBOTS_HOST_ERROR` · `ROBOTS_URL_ERROR` · `DUPLICATE` ·
**`LOW_QUALITY`** · `CLEAN_PARAMS` · `NO_INDEX` · `OTHER`.

🔑 **Вот что это даёт нам ровно сегодня.** Владелец получил письмо: «Главная страница сайта
недоступна для робота», «Страницы в поиске: 3 (−100 %)», карточки удаляются как «малоценные».
Каждое из трёх утверждений письма имеет машинный адрес в этом API:

| Утверждение письма | Машинная проверка | Ожидаемый код |
|---|---|---|
| карточки удаляются как «малоценные» | `search-urls/events/samples`, событие `REMOVED_FROM_SEARCH` | `excluded_url_status = LOW_QUALITY` |
| главная недоступна роботу | та же выборка по адресу корня | `HOST_ERROR` · `HTTP_ERROR` · `ROBOTS_URL_ERROR` |
| корень под `noindex` (гипотеза Менеджера) | там же | 🔑 **`NO_INDEX`** — отдельный код, НЕ смешанный с недоступностью |
| «Страницы в поиске: 3» | `indexing/samples` (до 50 000 адресов) | список того, что в индексе |

⚠️ **И это ровно тот случай, ради которого код важнее толкования.** «Недоступна для робота» и
«закрыта от индексации» — в письме одна фраза, а в API **два разных кода**: `HTTP_ERROR`/
`HOST_ERROR` против `NO_INDEX`. Диагноз Менеджера («причина — `noindex` на корне») и диагноз
письма («недоступна») различаются именно здесь, и различить их можно ОДНИМ запросом вместо спора.

🔴🔴 **ИМЕНА КОДОВ В ЖИВОЙ КОНСОЛИ И В ДОКУМЕНТАЦИИ API НЕ СОВПАДАЮТ, И ЭТО НАДО ЗНАТЬ ДО
НАПИСАНИЯ ПРИБОРА.**

| Что видно в живой консоли | Что перечисляет документация `ApiExcludedUrlStatus` |
|---|---|
| **`LOW_DEMAND`** | `LOW_QUALITY` — похожий по смыслу, но ДРУГОЕ слово |
| **`META_NO_INDEX`** | `NO_INDEX` — то же самое |

Двух наблюдаемых кодов в документированном перечне **нет вовсе**. Три объяснения, и выбрать между
ними по бумаге нельзя: перечень в доке устарел · интерфейс и API называют состояния разными
словарями · выгрузка CSV консоли и поле API — вообще разные поля.

⛔ **Практический запрет, вытекающий отсюда:** прибор Яндекса **НЕ ДОЛЖЕН зашивать список кодов
константой и НЕ ДОЛЖЕН отбирать строки сравнением с `LOW_QUALITY`**. Он обязан складывать коды
как есть, группировать по факту и печатать то, что пришло. Иначе получится страж, который молча
не находит ничего, — ровно класс ложного зелёного из лестницы трёх вопросов (вопрос 2: «признак
проверки верен?»).

📌 **Ответ на прямой вопрос Менеджера — «может ли официальный API отдать список исключённых с
причинами, аналог CSV `status=LOW_DEMAND`»: ДА.** Метод — `search-urls/events/samples`, событие
`REMOVED_FROM_SEARCH`, причина в поле `excluded_url_status`, до 50 000 адресов, страницами по 100.
То есть снимок Яндекса встаёт рядом со снимком Google, и слепота закрывается с двух сторон.
⚠️ С одной оговоркой, которая и есть содержание врезки выше: **какое ИМЯ придёт в
`excluded_url_status` для наших 1352 страниц — по документации предсказать нельзя.** Узнаётся
первым же запросом с токеном.

### 3.4.2 Внутренний gate-API консоли — для разведки формата, не для канала

Менеджер нашёл в живой консоли внутренний адрес списков:
`https://webmaster.yandex.ru/gate/searchable-samples/event-samples-list/` (пагинация `page=N`,
`perpage` 20, поле `totalCount`).

⛔ **В машинный канал он не годится и брать его туда я не предлагаю.** Это внутренний адрес
интерфейса: он не документирован, не имеет обязательств совместимости, живёт на сессии-куках
владельца и может измениться в любой день без предупреждения. Прибор на нём — это прибор, который
однажды молча начнёт врать. Ценность у него ровно одна и разведочная: **по нему видно, какие поля
и какие имена состояний консоль отдаёт на самом деле**, и этим можно заранее свериться с тем, что
придёт из официального API.

⛔ **Границу своей зоны держу:** работа с Вебмастером под сессией владельца — контур Менеджера,
я в него не иду. Здесь описан машинный путь, который эту работу заменит, а не подменяет её сейчас.

Источники: [Примеры страниц, появившихся в поиске или удалённых из него](https://yandex.com/dev/webmaster/doc/en/reference/hosts-search-events-samples) ·
[Примеры проиндексированных страниц](https://yandex.com/dev/webmaster/doc/en/reference/hosts-indexing-samples)

### 3.5 Переобход страниц и его квота

**Поставить в очередь:** `POST /v4/user/{user-id}/hosts/{host-id}/recrawl/queue`
Тело: `{"url": "https://example.com/…"}` — **один адрес за запрос**.
Ответ 202: `{"task_id": "UUID", "quota_remainder": <int>}`.

Ошибки, все именованные: `400 INVALID_URL` · `403 INVALID_USER_ID` · `404 HOST_NOT_VERIFIED` ·
`409 URL_ALREADY_ADDED` · **`429 QUOTA_EXCEEDED`** («Суточная квота запросов исчерпана»).

**Спросить квоту:** `GET /v4/user/{user-id}/hosts/{host-id}/recrawl/quota` →
`{"daily_quota": <int>, "quota_remainder": <int>}`.

🔑 **Числовой суточной квоты в документации НЕТ, и это не пробел разведки — это устройство API:**
квота зависит от сайта и сообщается самим сервисом. Значит прибор обязан её СПРАШИВАТЬ перед
подачей, а не зашивать число. Зашитая константа здесь — будущий `429` в самый нужный момент.

🔴 **И живое число рядом, для сравнения, которое придётся сделать.** В ИНТЕРФЕЙСЕ Вебмастера
лимит переобхода — **150 адресов в сутки** (замер Менеджера 2026-08-28, счётчик остатка виден на
странице). Совпадает ли он с `daily_quota` официального API — **неизвестно**, и это не мелочь:

| Если пулы ОБЩИЕ | Если пулы РАЗДЕЛЬНЫЕ |
|---|---|
| руками отправленные 150 уже съели суточную квоту API на сегодня | API даёт ещё столько же сверх интерфейсных 150 |
| очередь в 1201 адрес растянется на 9 суток | вдвое быстрее |

**Проверка одним запросом и стоит секунду:** `GET …/recrawl/quota` сразу после интерфейсной
отправки. `quota_remainder` близкий к нулю — пулы общие; равный `daily_quota` — раздельные.
⚠️ До этой проверки планировать сроки разбора очереди нельзя: разница вдвое.

⚠️ **И ограничение формы, о котором легко забыть:** API принимает **ОДИН адрес за запрос**
(`{"url": "…"}`), тогда как интерфейсная `textarea` берёт пачку. То есть 150 адресов — это 150
вызовов, а не один. Для нашей очереди в 1201 это важно при расчёте времени прогона.

**Список поставленных задач:** `GET /v4/user/{user-id}/hosts/{host-id}/recrawl` — то есть очередь
наблюдаема, и «подали и забыли» не бывает.

Источники: [Отправка страницы на переобход](https://yandex.ru/dev/webmaster/doc/ru/reference/host-recrawl-post) ·
[Проверка квоты на переобход](https://yandex.com/dev/webmaster/doc/en/reference/host-recrawl-quota-get) ·
[Список задач на переобход](https://yandex.com/dev/webmaster/doc/en/reference/host-recrawl-get)

### 3.6 IndexNow — отдельный путь, ключом, без OAuth

`GET https://yandex.com/indexnow?url=<URL>&key=<KEY>[&keyLocation=<URL>]`
`POST https://yandex.com/indexnow` с телом
`{"host": "…", "key": "…", "keyLocation": "…", "urlList": ["…", …]}`

**До 10 000 адресов за один запрос.** Ключ — 8…128 знаков из `a-zA-Z0-9-`, выкладывается файлом в
корень сайта (либо адрес файла указывается в `keyLocation`).

Коды: `200` успех · `202` ключ ещё проверяется · `400` неверные параметры · `403` ключ не подошёл ·
`422` ошибка проверки (кривой URL, неверный формат ключа) · `429` превышен темп.

🔑 **IndexNow не требует ни OAuth-токена, ни ключа консоли — только файла в нашем корне.** Это
единственный из всех разведанных путей, который агент может подготовить ЦЕЛИКОМ САМ: ключ мы
генерируем сами, файл кладём в `static/`, он уезжает ближайшим выкатом. Шага владельца здесь нет
вовсе.

⚠️ **И это прямо смыкается с давним хвостом проекта.** `STATUS.md` держит строку: «IndexNow был
отвергнут посылкой „страницы меняются раз в неделю деплоем“ (`researches/26` §11.5). Ночная сборка
эту посылку сняла: каталог растёт каждый день. Разведку надо перемерить». **Перемеряю прямо здесь:
посылка действительно снята** — каталог пополняется карточками ежедневно, а лимит 10 000 адресов
за запрос покрывает весь наш каталог (10 222 страницы) практически целиком. Bing — участник того
же протокола, то есть один ключ работает на две консоли. Google в IndexNow не участвует
(`researches/26` §11.5) — для него остаётся карта сайта.

⛔ **Решение о включении IndexNow я не принимаю:** это правка `static/` и поведение продукта
наружу. Выношу как готовое предложение с ценой — решать владельцу через Менеджера.

Источники: [IndexNow — справочник запросов (Яндекс)](https://yandex.com/support/webmaster/en/indexnow/reference) ·
[Ключ для подтверждения (Яндекс)](https://yandex.com/support/webmaster/en/indexnow/key.html) ·
[indexnow.org](https://www.indexnow.org/)

## 5. Границы, которые я держу

- ⛔ **Пишущие вызовы в этот прибор не входят.** `SubmitUrlBatch`, `recrawl/queue` и IndexNow —
  действия, меняющие поведение наших страниц в чужом индексе; они требуют слова владельца и
  отдельного разговора о том, что и когда подавать. Разведка описывает их, прибор снимка их не
  зовёт. Область доступа Google у нас намеренно `webmasters.readonly` (`researches/40` §9), и
  соседние консоли держим тем же правилом.
- ⛔ **Вебмастер под сессией владельца — контур Менеджера** (постановка смены 7). Не хожу.
- ⛔ **`robots.txt`, `sitemap` и мета корня не трогаю** — лечение причины идёт вопросом владельцу.
- 🟡 **Числа консолей наружу не показываем** (`ideas/37`): это внутреннее знание проекта.

## 6. Что НЕ подтверждено первоисточником — названо честно

1. **Переживает ли `api.svc/json/` рубеж 31.08.2026** (§2.5). Допущение, проверяется прогоном.
2. **Числовая суточная квота переобхода Яндекса** — документация её не называет; спрашивается у
   API. Не пробел, а устройство.
3. 🔴 **Один ли пул у интерфейсных 150 адресов и у квоты API** (§3.5). Разница в сроке разбора
   очереди вдвое. Проверка — один `GET …/recrawl/quota` после интерфейсной отправки.
4. 🔴 **Какое ИМЯ кода придёт в `excluded_url_status`** для наших удалённых страниц (§3.4.1).
   Живая консоль показывает `LOW_DEMAND` и `META_NO_INDEX`, документированный перечень — их не
   содержит. Прибор обязан складывать коды как есть, а не искать заранее известное слово.
5. **Разрезы Bing по устройствам и странам** — в списке методов не нашёл; возможно, живут внутри
   полей `GetQueryStats`. Выяснится первым же прогоном с ключом.
6. **Глубина истории Яндекса** — явного ограничения в доке нет; сколько на самом деле, покажет
   первый запрос с `date_from` подальше.
7. **Ни один запрос обеих консолей не прогнан** — ключей нет. Весь документ — разведка, не замер.
   Живые числа §3.4.1 сняты Менеджером ГЛАЗАМИ в интерфейсе, а не по API: они правда о консоли,
   но не доказательство того, что API отдаст то же самое теми же словами.

## 7. Что предлагаю дальше (решает Менеджер, часть — владелец)

1. **Два шага владельца одной домашкой** — ключ Bing (2 минуты) и токен Яндекса (5 минут, живёт
   6 месяцев). Оба кладутся в `.env` рядом с ключом Google. Без них разведка так и останется
   разведкой.
2. **Прибор Яндекса — ПЕРВЫМ, вперёд Bing**, и довод календарный, а не вкусовой: письмо про
   удаление страниц пришло сегодня, а `search-urls/events/samples` отвечает на него поимённо.
   Bing даёт вторую линию ряда — это ценно, но не горит.
3. **IndexNow — отдельным предложением владельцу**: посылка, по которой его отвергли, снята
   замером (§3.6); шага владельца он не требует вовсе; цена — файл ключа в `static/` и ближайший
   выкат.

## Решения, принятые без владельца

| Решение | Как выбрал |
|---|---|
| Разведка только по документации вендоров, без единого прогона | Ключей нет, а выдумывать ответы сервера запрещено (правило трёх дверей). Помечено границей §6 п.5 |
| Для Bing выбран JSON/HTTP, а не SOAP | SOAP отставляется через три дня (§2.5). Официальный «Getting Started» ведёт именно на SOAP — по нему пойти нельзя |
| Для Яндекса запрошены права `webmaster:hostinfo` + `webmaster:verify` | Это ровно то, что называет первоисточник для чтения; расширять «на будущее» не стал — чтением ограничена и область Google |
| Имена переменных `.env` предложены, но не заведены | Заводить переменную под ключ, которого ещё нет, значит завести пустую строку, которая читается как «доступ настроен» |
| IndexNow вынесен предложением, а не сделан | Правка `static/` и поведение продукта наружу — вне «где работать» моей постановки |
| Пишущие вызовы описаны, но в прибор не заложены | Область доступа проекта — только чтение; расширение — разговор с владельцем, а не деталь реализации |
