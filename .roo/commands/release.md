# /release — опубликовать релиз на GitHub

Человек просит выпустить новую версию. Это **необратимое внешнее действие** (публичный тег +
GitHub Release). Выполняй процедуру **по порядку**; проговаривай каждый шаг в чате. Если шаг
провалился — остановись, покажи ошибку, НЕ продолжай вслепую.

> ⚠️ **ТРЕБУЕТСЯ ПОДТВЕРЖДЕНИЕ.** Перед самой публикацией покажи человеку: какая будет версия
> (текущая → новая), что дерево чистое, что сборка прошла. Публикуй только по его явному «да». Релиз —
> это публичный тег и Release, откатывать неприятно. **В автономном режиме (`/autoloop` и другие
> циклы) релизы НЕ публикуй.**

## Шаг 0. Определи тип бампа и кодовое имя (остановка ИДЕНТИЧНОСТИ, а не формальность)

Согласуй с человеком (или подтверди умолчание): patch / minor / major. Назови текущую → новую версию.

**У релиза обычно есть короткое кодовое имя** (запоминающееся слово или два, описывающие тему
релиза). Кодовое имя определяет **заголовок** релиза и подзаголовок — см. шаг 6.

**Кодовое имя — это ИДЕНТИЧНОСТЬ, а идентичность авторизует владелец — никогда не агент, при ЛЮБОЙ
широте одобрения.** Огульное «выпускай, меня не спрашивай» снимает ТРЕНИЕ подтверждений с действий;
оно не передаёт АВТОРСТВО того, как продукт себя называет (полевой инцидент: под буквальным
«Я ОДОБРЯЮ ВСЁ, не спрашивай» агент выдумал кодовое имя релиза, и владелец встретил имя своего
продукта как свершившийся факт). У этой жёсткой остановки ровно три законных исхода:

1. **владелец называет имя** (или выбирает из предложенных тобой кандидатов);
2. **ты делаешь ВСЁ остальное и задаёшь ОДИН точечный вопрос об имени** — один вопрос внутри уже
   одобренной работы ничего не стоит и не есть то, о чём было «не спрашивай»;
3. **релиз БЕЗ ИМЕНИ** под нейтральным фактическим заголовком (`NDim Space X.Y`) — ВСЕГДА доступный
   запасной выход: когда владелец недоступен, релиз не блокируется навечно, а именовать (хоть задним
   числом) может только владелец. Никогда не имя-заглушка: заглушка — это всё равно имя, которое
   кому-то потом придётся раз-решать.

**У выпущенного имени есть артефакт-ИСТОЧНИК** — строка в заметках релиза или плане:
`кодовое имя: <владелец · канал · дата>` — как у научного утверждения есть цитата; имя без автора
обязано бросаться в глаза. И если выпущенное имя оказалось неудачным — агент не переименовывает по
своей инициативе: исправление брендовой ошибки — тоже брендовое решение.

## Шаг 1. Предпроверка окружения (не релизь на грязном или сломанном дереве)

```bash
git status --short          # дерево должно быть ЧИСТЫМ (кроме gitignored-артефактов)
git branch --show-current   # ветка релиза (main)
git pull --rebase           # чтобы push был fast-forward
gh auth status              # gh залогинен (нужен для GitHub Release)
```
Если дерево грязное — сначала закоммить или разберись (`/pause` или твой инструмент коммитов).

Если проект ведёт **реестр пар «истина ↔ зеркало»** (`AGENT_GUIDE.md` → «Гигиена документов и
текста»), прогони команду проверки каждой строки сейчас — релиз поверх разъехавшейся пары
запечатывает расхождение в поставку. Красная строка = стоп и сведение до продолжения.

## Шаг 2. Освежи README (все языки)

**README и заметки релиза — артефакты ВЛАДЕЛЬЦА, витрина, которую он подписывает.** Поэтому если в
проекте есть портрет голоса (`AUTHOR_STYLOMETRY.md`, `/owner-voice`) — ОТКРОЙ его сейчас и прогони
его самопроверку перед сдачей текста; портрета нет — обязательства нет, и его отсутствие релиз не
краснит. ЧЕРНОВОЙ портрет (пороги не взяты, слепой тест не пройден) — по нему ПИШУТ, но режим
rewrite с черновика не стартует. В любом случае вердикт «звучит как я» принадлежит владельцу —
класс вкуса агент не судит. **Статус артефактов владельца НЕ вносит в них пометок провенанса**
(`AGENT_GUIDE.md` → пометки провенанса, исключение витрины): README и заметки релиза уезжают как
есть и `[AI]…[/AI]` не несут никогда. Их очередь приёмки — ВЫЧИТКА владельцем, и она так же
обязательна: заведи запрос домашкой и скажи прямо в отчёте релиза, что текст витрины ещё не
вычитан, если это так. **Витрину судит МАШИНА, а не память:** правила — `AGENT_GUIDE.md` →
«Витрина — текст, который читает посторонний»; линтера витрины у проекта пока нет — пройди десять
правил руками перед сдачей текста.

Приведи `README.md` в соответствие с реальностью: статус фаз, работающие фичи, инструкции. Если он
двуязычный (ru/en — на этом проекте так и есть), держи оба языка синхронными. Не выдумывай — отражай
только то, что действительно сделано и проверено (сверься со `STATUS.md` и закрытыми `bugs/`/`ideas/`
с тегом `DONE`).

**Номер версии живёт и ВНУТРИ картинок — перегенерируй их командой, а не на глаз.** Витрина несёт
версию в местах, куда текстовый поиск не дотягивается: подпись, вжатая в лого или баннер, плюс
бейдж, строка версии, alt-текст картинки и свежая строка таблицы истории версий. Один раз перечисли
эти места, дай каждому команду и прогони их здесь (у этого проекта версионных картинок пока нет —
появятся, впиши команды сюда). Затем ОТКРОЙ картинку и прочитай подпись — рендер судят глазами.
Оплачено в поле на самом истоке фреймворка: релиз 2.3 уехал на GitHub с лого, на котором стояла
версия 2.2, и с README прошлой версии — потому что подпись было нечем перерисовать и никто её
не открыл.

**А СМЫСЛ кодового имени версии спрашивается у владельца — никогда не выводится из самого имени.**
Если витрина объясняет, что значит имя версии, процитируй слово владельца об этом смысле
(интервью, журнал решений, сообщение в чате). Слова нет — либо задай один точечный вопрос, либо
не объясняй имя вовсе: нейтральная подача легитимна. Оплачено в той же сессии: имя прочли как
правдоподобную метафору, и догадка расползлась по обеим языковым половинам заметок релиза
абзацами и заголовками, пока все стражи витрины оставались зелёными.

## Шаг 3. Перегенерируй рендеренные документы

```bash
node tools/snapshot-landing-metric.mjs   # снимок витрины лендинга «С нами уже N человек»
```

Обязателен перед КАЖДЫМ выкатом (`bugs/81`): число живёт в пререндере, чтобы не доезжать «на
горячую», и обновляет его только этот инструмент — иначе витрина стареет. Дифф в
`src/lib/content/landing-metric.ts` попадает в коммит шага 5, а страж
`node tools/verify-bug81.mjs` проверяет результат по собранному сайту.

Если появятся другие генерируемые артефакты (например, `README.pdf`), перегенерируй их здесь же.

## Шаг 4. Контрольная сборка (перед релизом)

Запусти сборку проекта (см. `AGENT_GUIDE.md` → «Сборка»). Она обязана пройти. Это ловит ошибки ДО
бампа версии, чтобы не оставить полурелизнутую версию.

## Шаг 4а. Судейский проход — ОБЯЗАТЕЛЕН перед публикацией

Прогони `/fable-judge` по релиз-кандидату: перепрогони заявленные проверки (тесты, сборка,
`kaif:check`), сверь фактический дифф с тем, что релиз ЗАЯВЛЯЕТ. Вердикт REFUTED = релиз не выходит,
пока расхождение не устранено. Релиз — необратимое внешнее действие; неподтверждённое «всё проверено»
здесь дороже всего.

## Шаг 5. Закоммить изменения документов и сборки (перед релизом)

Закоммить обновления README и документов, чтобы коммит `release: X.Y` был чистым бампом версии:
```bash
git add -A && git commit -m "docs: README для релиза X.Y"
```

## Шаг 6. Опубликуй (после подтверждения человека)

```bash
# бампни версию (в version.json или манифесте), затем:
git commit -am "release: X.Y" && git tag vX.Y && git push && git push --tags
gh release create vX.Y --title "NDim Space X.Y — <Кодовое имя>" --notes-file <NOTES.md> <АРТЕФАКТЫ, если есть>
```

> 📛 **Заголовок релиза — ФИКСИРОВАННЫЙ ФОРМАТ (КАНОН):** `NDim Space X.Y — <Кодовое имя>` — имя
> проекта, версия `major.minor`, длинное тире `—`, затем кодовое имя из шага 0. При законном исходе
> «БЕЗ ИМЕНИ» из шага 0 заголовок — нейтральный `NDim Space X.Y`: фактический, без выдуманного
> имени. **Не** `vX.Y`, без кавычек и ёлочек. Держи формат согласованным со всеми прошлыми релизами
> (проверь `gh release list`).
>
> 📝 **Заметки релиза — ДЕЛЬТА, никогда не копия README (НЕ используй `--generate-notes`).** Заметки
> отвечают на ОДИН вопрос: *«что изменилось в ЭТОЙ версии и стоит ли обновляться?»* — строго дельта
> этой версии; всё, что описывает продукт вообще, даётся ССЫЛКОЙ на README, а не копией (полевой
> инцидент: 34 КБ заметок оказались почти копией README; переписаны по дельте — 12 КБ, ни один факт
> не потерян). Механическая проверка объёма перед публикацией: **абзац, который можно вставить в
> README без правки, принадлежит README, а не заметкам.**
> **Разные документы черпают из разных колодцев:** заметки берут форму у ПРЕДЫДУЩИХ заметок релизов
> ЭТОГО проекта (`gh release view <prev> --json body -q .body` — следуй домашнему стилю); README
> берёт форму у текущего README и других витрин владельца. Продублируй **на каждом языке, который
> есть в README**, с якорями или переключателями языка на странице. Структура на язык: строка
> заголовка (дата релиза · место), абзац «что это за релиз», приложенные артефакты, раздел
> **✨ Что нового** (дельта), заметка **⬆️ Обновление**, когда уместна, и ССЫЛКА на README о том,
> что такое продукт и как начать. Запиши заметки в файл и передай через `--notes-file`.

## Шаг 6.4. ВОРОТА ПУБЛИКАЦИИ — открой отрендеренную страницу и прочитай первый экран ГЛАЗАМИ

Проверить ИСТОЧНИК — не значит проверить ПУБЛИКАЦИЮ. Правила рендеринга принадлежат чужой среде, и
они разные: **тело релиза GitHub сохраняет одиночные переносы строк** (врап по 100 колонок
превращается в рваный текст), **README их склеивает**, **PDF переливает под свою ширину**. Полевой
случай: страница релиза вышла с союзом, повисшим на отдельной строке, и разрезанным пополам
предложением — при четырёх зелёных инструментах по исходному файлу; дефект приехал скриншотом от
владельца.

```bash
gh release view vX.Y --web   # открой ОПУБЛИКОВАННУЮ страницу, а не файл заметок
```

Прочитай первый экран: абзацы целы, переносы там, где задуманы, картинка на месте, ссылки
кликабельны. Механическая половина ворот идёт ДО публикации: в файле тела заметок **не должно быть
двух непустых строк подряд** вне блоков кода и таблиц. Правило шире релизов и действует для любой
чужой среды — тикета, письма, чат-бота, слайда: узнай её правило переноса ДО письма, открой
результат ПОСЛЕ отправки.

## Шаг 6.5. Чеклист выката (когда релиз заменяет РАБОТАЮЩУЮ систему)

Если релиз включает выкат поверх живого сервера, контейнера или службы — пройди пять ворот. Каждые
существуют потому, что пропуск ровно этих ворот однажды уронил настоящий прод:

1. **Сначала зеркало прода.** Сними ФАКТИЧЕСКУЮ конфигурацию работающего прода ДО того, как его
   заменять (`docker inspect`, переменные окружения, версия) — прод часто живёт с настройками,
   которых не помнит ни один документ, и слепой перевыкат «по докам» молча меняет поведение (или
   направляет прод в эмулятор стенда). Каждое отличие старого запуска от нового обязано быть
   осознанным и названным решением.
2. **Живой смоук.** Запусти новый экземпляр и прочитай глазами его первый рабочий цикл в логе
   (`TESTING_FRAMEWORK.md` → ворота наблюдения).
3. **Самодостаточность артефакта.** Образ или бандл запускается в изоляции, все модули на месте —
   образ, отставший от кода, ронял прод при всех зелёных тестах (это ровно EXP-0040).
4. **Инварианты домена.** До переключения выпиши числа, которые НЕ должны измениться (счётчики,
   суммы, размеры); после — сверь.
5. **Документ боевого запуска.** После выката обнови документ проекта про боевой запуск
   (`plans/04_cutover.md`) — единственный источник истины о том, как прод запускается на самом деле.
   Конфигурация прода, живущая только внутри работающего процесса, — мина для следующей сессии.

## Шаг 7. Проверь и доложи

```bash
gh release view vX.Y        # релиз существует, артефакты приложены
git log --oneline -3        # виден коммит релиза и тег
```
Доложи человеку: версия, ссылка на релиз, что приложено. Готово.

## Заметки
- Релизы бампают minor/major; обычные рабочие коммиты бампают build/patch.
- Если push отклонён (non-fast-forward) — `git pull --rebase` и повтори. На шаге 6 это критично: тег
  может уже существовать локально — проверь `git tag` и `git tag -d vX.Y` перед повтором.
- НИКОГДА не делай force-push и не удаляй чужие теги и релизы. Если во время публикации что-то пошло
  не так — остановись и покажи человеку, не «чини» вслепую.
- Не релизь в автономном режиме — только по явной просьбе человека.
